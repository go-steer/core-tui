# Changelog

All notable changes to `core-tui` are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Stability promise

The public API of `core-tui` is the exported surface of `github.com/go-steer/core-tui/tui`, and within it the plug-in surface [`docs/design.md`](./docs/design.md) §3 describes — as shipped today:

- the `Agent` interface and the `Event` type it streams,
- the optional capability interfaces a host may implement (`ModelSwapper`, `Reloader`, `PermissionController`, `PricingController`, `ToolLister`, `SubagentReporter`, `SessionSwitcher`, `RemoteInterrupter`, `StatusReporter`, `SlashProvider`, `LiveAgent`, `InjectableAgent`, …),
- the `Options` struct's field names, and
- the TUI-implemented `PermissionPrompter` / `Elicitor` pair.

Adding a field to `Options` is non-breaking by Go-module rules — the documented usage is a struct literal with explicit field names — so hosts should keep writing it that way.

Everything else exported from `tui` (render helpers, `Overlay` and the `Dialog` stack, `History`, `Styles`, `Theme` internals) is **not** covered by that promise pre-1.0, even though it is exported. Reducing that gap is [the v1.0 milestone's](https://github.com/go-steer/core-tui/milestone/1) exported-surface audit.

`tui/testagent` is a test fixture. It moves with the library and promises nothing.

Pre-1.0, breaking changes are possible at any minor version (`v0.X`). When we make one it is called out in this file under **Changed** or **Removed**, with the upgrade action spelled out. Patch versions (`v0.X.Y`) are bug fixes only.

The wire protocol in [`docs/sse-event-stream-protocol.md`](./docs/sse-event-stream-protocol.md) versions independently of the library; its own version is noted in the release that changes it.

## [Unreleased]

### Added

- **The agent can ask the operator a question of its own** ([#255](https://github.com/go-steer/core-tui/issues/255)). Every question the TUI could put up until now belonged to something other than the agent: a tool call wanting approval, an MCP server wanting a value, the operator wanting a picker. An agent that simply wanted to *ask* — which strategy, which of these three, is this branch name right, write me the release note — had no way to, and the fallback its host reached for was a tool that reads stdin, which under a full-screen TUI means two programs holding one terminal and neither of them drawing what the other put there. `Options.Asker`, satisfied by `tui.NewAsker()`, is the seam: the host hands the same value to the TUI and to its ask-the-user tool, the tool calls `Ask(ctx, AskRequest{…})` and blocks, the question opens on the overlay stack, and the operator's answer comes back as an `AskResult`. Five kinds cover it — `AskChoice` and `AskMultiChoice` over a `[]AskOption`, `AskConfirm`'s yes/no row, `AskText`'s one-line input, and `AskLongText`, which suspends the whole program into `$VISUAL` / `$EDITOR` and takes the saved buffer back as the answer. Three things about the shape are deliberate. The answer distinguishes `AskAnswered` from `AskDeclined` (ctrl+d: the operator read it and is not answering) from `AskCancelled` (escape, or the session switched out from under it), because an agent that cannot tell "no" from "not now" will re-ask the one it should drop and drop the one it should re-ask. A request the TUI cannot draw — a chooser with no choices, a long-form ask on a box where neither editor variable is set — comes back as `ErrAskUnsupported` and a transcript row, not as a decline: that is the exact bug [#209](https://github.com/go-steer/core-tui/issues/209) had just finished taking out of the elicit path, and shipping a new surface carrying it would have been no saving at all. And a long-form round trip that fails, or comes back empty, leaves the question open with the reason under it rather than sending an answer nobody wrote — the `git commit` reflex, which is the behaviour an operator who quit their editor on purpose expects. All of it is additive, so a host that sets no `Asker` sees no change; this is `requirements.md` R-PROMPT-1, which had carried "specified, not shipped" since v0.19.0, and stage 5 of the question seam [#164](https://github.com/go-steer/core-tui/issues/164) built on it. `examples/local` walks all five kinds 28 seconds in.

### Changed

- **The permission prompt is a question on the overlay stack, which moves it below the `/btw` side answer and the embedded form** ([#164](https://github.com/go-steer/core-tui/issues/164)). The approval prompt was the last modal the agent can open that was still assembled out of parts scattered across the package, and it went last on purpose: it is the highest-stakes surface in the product and it already worked, so it waited until the seam had been proved by four other migrations and until the golden corpus had a byte-level capture of both its layouts to be held against. Two fields on `Model` held its state, a 50-line arm in the key switch drove it, four functions in `view.go` drew it, and a fifth decided whether the caret was hidden. Those are one type in `tui/question_permission.go` now. The part worth naming is what happened to the six decision keys: they were three lists that had to agree by inspection — a `switch` whose arms each named a `PermissionDecision`, a legend builder that listed the same keys in the same order, and a predicate that decided which of them the input-grace window held — each of which spelled out separately that the verb-scoped grant only exists when the request carries a verb. They are one `[]permissionOption` now, so the switch is a lookup, the legend is a join over the same slice, and the grace window's answer is "is this stroke one of my options"; a prompt cannot advertise a key it will not answer or answer one it never showed, and there is a test that says so rather than a convention that hopes so. What an operator will see is z-order. The prompt used to draw above every other surface, but only Escape was routed that way: every other key checked the `/btw` side answer first, so with both up your `y` went to one surface and your Escape to the other. Both now agree on the routing's reading and the prompt sits underneath, which is where the overlay stack sits as a whole. In the same vein, a modal that opens while the default inline prompt is up now waits instead of drawing over it — before, it covered the block while the keys kept going to the block, which is the pixels-and-keys disagreement this issue exists to delete. The default layout is unchanged in every other respect: it is still a gutter block in the transcript, drawn under the streamed text that asked for the tool call, and it is still the surface the mouse wheel scrolls, because the chat viewport is what is showing it. Nothing exported changed.

- **The elicit form is a question on the overlay stack, which moves it below the `/btw` side answer** ([#164](https://github.com/go-steer/core-tui/issues/164)). The form an MCP server puts up to ask for a value was the last of the big modals still assembled out of parts scattered across the package: five fields on `Model` held its state, a 130-line arm in the key switch drove it, four functions in `view.go` drew it, and a fifth put the caret in the text field. Those are one type in `tui/question_elicit.go` now, answering the same small `question` interface the theme, model and session pickers already answer, with the `ElicitResult` dispatched from a resolver at the seam rather than from inside the widget — which is the shape the channel-based `Elicitor` lifecycle turned out to fit, and the reason the whole form can now be driven to a submitted answer in a test with no `Model`, no `Update` and no `tea.Program` anywhere in it. The one thing an operator will see is z-order: the form used to draw *above* the `/btw` side answer while being keyed *below* it, because `modalFrame` reached the elicit arm before the side-answer arm and the key router reached them the other way round. Pixels and keys disagreed, so with both up your strokes went to the surface that was not on top — the legend named the same wrong one, since `footerHint` was ordered like the renderer. Both now agree on the routing's reading and the form sits underneath, which is where the overlay stack sits as a whole; that is the layer questions live on, and hoisting it above a surface that is still inline state to preserve a stacking order nobody chose would be work spent on the arrangement this issue exists to delete. The side answer is also the more momentary of the two: it is something the operator asked for a keystroke ago, whereas an elicit is an agent's request that has been waiting and will keep waiting. Two mechanisms grew a seam apiece on the way through, both of them there so the next question inherits the behaviour instead of re-implementing it. The 300 ms input-grace window that protects an agent-opened modal from buffered keystrokes is now a property of *how a question was opened* — `Overlay.ask` takes an origin, an operator-opened picker is never stamped at all because typing `/theme`, pressing Enter and typing again is one continuous act, and an agent-opened question holds its committing keys until the window passes. Which keys those are is declared by the optional `gracedQuestion` extension; a question that does not declare holds **everything**, because a widget whose author has not said which of its keys are irreversible is not one we can assume any of them are not. Escape is exempt unconditionally either way: it dismisses, which is the fail-safe direction, and a held Escape leaves the operator pressing the one key that visibly does nothing on a modal they are trying to leave. The other seam is `scrollQuestion`, which is how the form keeps mouse-wheel scrolling by `wheelScrollLines` at a time while the pickers keep moving one row per tick. Nothing exported changed.

### Fixed

- **A pane drag keeps up with the pointer** ([#247](https://github.com/go-steer/core-tui/issues/247)). [#104](https://github.com/go-steer/core-tui/issues/104) took the whole-history Glamour pass off a width-changing `tea.WindowSizeMsg` and bounded what was left by the viewport, and [#161](https://github.com/go-steer/core-tui/issues/161) made the walk behind it flat in transcript length; what neither could do is make the bound *small*, because the bound is the window and a 40-row window is about two assistant turns — and one Glamour render of a 500-byte turn measures ~5ms, so a drag still paid ~10ms of re-wrap per event before it drew anything. End to end that is a p95 of 15–17ms from an event being enqueued to the frame carrying it reaching the screen, at every transcript length from 10 turns to 1000, against the 16ms a 60Hz frame gets: flat, which is what #161 promised, and still over budget, which is what an operator sees as the pane edge lagging behind the pointer. So the re-wrap stops being bounded and starts being **skipped**. The first width change after a quiet period reflows the visible rows synchronously, every event after it in the same gesture does not, and 40ms after the pointer stops moving (`resizeVisibleWindow`) one reflow catches the screen up — with #104's 120ms backlog settle and its eight-rows-per-tick warm running behind that exactly as before, and every tick carrying the same `resizeGen` stamp, so a superseded drag's callback is dropped rather than clobbering a newer one. **Leading edge rather than a plain trailing debounce, and that is not a detail:** a resize that arrives alone — a tmux keybind, a tiling window manager, the very first sizing of the program — is a drag of one event, and the first sizing has no previous wrap to fall back on, so a trailing-only debounce shows an unwrapped frame for 40ms at startup. The golden corpus said so before the reasoning did; all eight frames failed. What the change gives up is that for up to 40ms mid-gesture the rows on screen are wrapped for the width the terminal had a moment ago. What it does not give up is the frame: the width contract is enforced per drawn line at the *draw* site (`chatCutLine`, [#154](https://github.com/go-steer/core-tui/issues/154) and [#159](https://github.com/go-steer/core-tui/issues/159)), so a row wrapped too wide is clipped to the window it is being drawn into rather than escaping it, and cutting leaves the row's line count alone — which is the number the lazy walk budgets against. That property is what the whole suppression rests on, so it is asserted rather than argued: a mid-drag frame goes through the frame invariant, and the drag probe fails on any frame wider than its terminal, during the gesture or after it. The measurement is the other half of the work. A debounce is a statement about time, and draining a `Cmd` tree synchronously — which is how every other test on this path works, correctly, for the work it does — measures the work and skips the wait. So `tui/dragprobe_test.go` drives a real `tea.Program` with events enqueued from outside the loop every 30ms, under two accounting rules that keep the number honest: a frame is charged with the **oldest** event not yet on screen, because an operator three events behind is looking at a frame three events stale and charging the newest would report that as fast; and the clock starts when an event is **enqueued**, not when `Update` receives it, because time spent in the queue is time spent looking at the wrong frame. On that probe the p95 goes 17.1 → 7.5ms at 10 turns, 15.4 → 6.6 at 100, 15.1 → 6.9 at 400 and 16.5 → 7.8 at 1000 — still flat, and now half the budget instead of all of it. The price is convergence after the last event, ~8ms → ~22ms, paid once, after the pointer has already stopped. Under the race detector the probe keeps its correctness assertions and skips its timing ones, since the detector inflates this path about 14x and a gate on that number would be a fact about the detector rather than about the package. Two things in [`docs/decisions.md`](./docs/decisions.md) close with it. **D29's H3 clause 4** — the suppression-only arm the architecture spike never built, and the criterion that would have demoted the lazy list — is answered: suppression on top of the list clears the gate, neither mechanism does the job alone, and both are cheap. And **F4**, "the width contract belongs to the producer, so truncate on the cache-miss path", is closed as already-done somewhere better, because cutting on the way *into* the render cache is precisely what #154 had to undo once it turned out that a cached row already cut to the window has no columns left to pan to.

- **A diff no longer blows the centered permission modal out to the full width of the terminal** ([#164](https://github.com/go-steer/core-tui/issues/164)). Hosts that set `PermissionLayout: PermissionOverlay` and hand the prompt a unified diff got a box the width of the window instead of the 80-column frame every other modal wears — on a 160-column terminal, a permission dialog spanning all 160 columns while the theme picker beside it spanned 80. The body renderer took a width argument and its diff arm ignored it, reaching instead for the model's cached Glamour renderer, which is wrapped for the chat column; a diff sized for a 100-column transcript arrived inside an 80-column modal, and because a lipgloss width is a minimum rather than a maximum, the content did not clip — the box grew to fit it. Every arm renders at the width it is handed now, with the renderer cached per width and per light/dark polarity on exactly the three keys the chat-column one caches on, so the fix costs no re-render per frame. This was invisible until it was captured: there was no golden coverage of either permission layout, which is why the migration above was gated on writing some first, and the blowout was sitting in the very first frame that corpus recorded.

- **A space types a space into an elicit text field** ([#164](https://github.com/go-steer/core-tui/issues/164)). Ask for a full name, a commit message or a search phrase through an elicit form and you could not put a space in the answer: the key came out of Bubble Tea normalized to the stroke `"space"`, the form's switch claimed that stroke for the boolean checkbox toggle, and on a field that was not a boolean it fell out of that arm into a printable-character append guarded on the stroke being a single rune — which `"space"`, at five, is not. So the keystroke did nothing at all, on every field type but the one it was written for. The stroke is rewritten to a literal `" "` before it reaches that guard now, and the boolean toggle keeps the binding it was claimed for. Worth recording how it survived: the predecessor had the same hole and a test that covered the same handler, but the test fed it a raw `" "` — a stroke nothing in the key path produces — so the assertion passed against an input that could not occur, and the bug was found only by rewriting the test to go through the same normalization `Update` does. A test that constructs its own input is testing the function; a test that constructs the input the program produces is testing the program. ([#245](https://github.com/go-steer/core-tui/issues/245)). Enter on the model or session picker starts a host call, and when that call comes back with an error the list stays up — deliberately, because the operator's next move after "provider unreachable" is almost always the next row down, and closing would make them re-run the command to get back to a list they were already looking at. What they had nowhere to read is *why*. The reason went to the transcript, which is behind the modal, so from the operator's seat a failed switch was Enter, a pause, and the same list: indistinguishable from a keystroke that got dropped, and it teaches the wrong next move, since the obvious response to a dropped keystroke is to press Enter again on the row that just refused. The reason now renders as the last body row under the list, in `ErrorText` with the warn glyph — the same shape the text-input dialog's inline validation error has one layer down — and clears on the next stroke that moves the cursor or edits the filter, so what is on screen always belongs to the list in front of it. The transcript row stays rather than moving: it is the durable record, and it is the only channel `/model <id>` and `/switch <id>` have, since those reach the same reply handler with no modal in the way. Both readings of a failure now come from one helper apiece (`modelSwitchFailure`, `sessionSwitchFailure`) rather than from a condition spelled out at each site, because two accounts of the same failure that can drift apart would be worse than the silence this replaced. Three details are load-bearing rather than incidental. The reason is host-derived `err.Error()` text, so it goes through the `sanitizeLine` funnel every untrusted row in the package goes through, with newlines flattened *first* because LF is the one control that funnel deliberately passes through — it is the line separator for multi-line bodies — and a two-row reason in a one-row hole pushes the footer off the bottom edge. The row is charged to the list window at the picker's own call site rather than folded into `modalPickerChromeRows`, because those thresholds decide when a modal's margin has stopped being real and must stay a property of the terminal's height: derived from a budget that moves, a modal would change fullscreen regime because a host call failed. And it is truncated as a plain string before styling and measured against the modal's inner width rather than its body width, since it sits outside the windowed region — nothing downstream closes an SGR left open on it, and no scrollbar column is glued to its right.

### Docs

- **The architecture spike's results are in the tree instead of on a branch nobody would find** ([#247](https://github.com/go-steer/core-tui/issues/247), [#248](https://github.com/go-steer/core-tui/issues/248)). Six hypotheses about the rendering architecture were measured on a throwaway branch against kill criteria fixed in writing before any challenger code existed, and the 552-line results file sat there unreferenced by anything in `main` — a branch is not a place a decision can be found by someone who was not there. It is now [`docs/architecture-spike-results.md`](./docs/architecture-spike-results.md), moved unchanged apart from a provenance note and four relative links repointed at the archive, and the branch is archived at the tag `spike/arch-bets-2026-08-16` and deleted. The verdicts are written into [`docs/decisions.md`](./docs/decisions.md) as two entries, because they are two different kinds of decision: **D28 says do not adopt a cell-buffer compositor**, which is a door to keep shut, and **D29 says what the rewrite actually targets**, which is a direction to keep walking in. H2 is killed on every clause of its own criterion — the `strjoin+clip` control it was meant to beat scores the same 15/15 on the overflow goldens, shows *more* live content behind a floating modal (16 rows against 14), answers hit-testing from the layout rectangles the layout already computes, costs 1.27× less time and 7.0× fewer bytes, and does not drop combining marks, where the canvas backend loses a combining mark on a narrow base and so mangles the NFD filename macOS hands out of its own filesystem. The negative control, H6, is the reason there is a rewrite at all: it failed, at a p99 keystroke-to-frame latency of 84 ms at 400 turns and 154 ms at 1000 against a 25 ms gate, with an idle control flat at ~4 ms at every size that pins the whole of the growth on the stream-driven rebuild rather than on transcripts merely being big.

  The single most load-bearing sentence, and the easiest one to lose: **the target is the refresh and resize paths, not `View()`**, which is already flat at ~3.5 ms at every transcript size in both arms — a rewrite aimed at rendering would move none of these numbers. The remaining steps are filed in the order the spike gives them, with H5 already open as [#164](https://github.com/go-steer/core-tui/issues/164), H1 and H3 as a single work item ([#247](https://github.com/go-steer/core-tui/issues/247)) because H3's win *is* H1's width-keyed per-item cache and sequencing them apart would build the drag mode on top of the thing it depends on, and the 20 fps spinner as a cheap follow-on ([#248](https://github.com/go-steer/core-tui/issues/248)). Step 0 needed no issue at all: the spike's three hygiene findings were re-verified against `main` and all three had already landed in v0.21.0 after the snapshot it measured — the word-wrapper-as-padder in [#157](https://github.com/go-steer/core-tui/issues/157), [#160](https://github.com/go-steer/core-tui/issues/160) and [#203](https://github.com/go-steer/core-tui/issues/203), the panel-survival assertion beside the clip pass in [#158](https://github.com/go-steer/core-tui/issues/158), and the tab arithmetic in [#216](https://github.com/go-steer/core-tui/issues/216) and [#217](https://github.com/go-steer/core-tui/issues/217). That is worth recording rather than quietly skipping, because it is what a spike snapshot is *for*: the findings were real, they were acted on before the results file was landed, and re-measuring is cheaper than re-fixing.

### Removed

- ⚠️ **The rest of the render-extension surface: 23 symbols, including `Dialog`, `Overlay`, `Item`, `ScrollDialog`, `RenderContext`, `Scrollbar` and `Styles`** ([#257](https://github.com/go-steer/core-tui/issues/257)). The entry below took the four that [#164](https://github.com/go-steer/core-tui/issues/164)'s question seam freed; this takes the other nineteen, plus the four styling symbols [`docs/api-surface.md`](./docs/api-surface.md) §3.2 ties to them, and finishes the last of that document's unexport recommendations. The argument is unchanged and it is a reachability argument, not a taste one: `Dialog.HandleKey` and `Item.Render` take a `*Model` whose every field is unexported, so an external implementation compiled and could then do nothing with its argument; `Overlay.Open` is the only thing that accepts a `Dialog`, and the only `Overlay` in existence is an unexported field of `Model`; and `Styles`, which you *could* construct, had nowhere to go, since the only exported things consuming one were `Scrollbar` and `RenderContext`, both in the same set. An exported interface with no installation seam is a promise the library cannot keep, and 1.0 would have frozen the seam's absence along with it. Building the seams instead — an `Options.ToolRenderers` map, a dialog-registration hook — is a feature rather than a cleanup and waits for a host that wants one; adding them later is a compatible change, which is the whole reason this direction is the safe one. **Upgrade action: delete the reference.** No host could have called any of these, in this repository, in `examples/`, or in core-agent, all three checked; if your adapter names one it is in dead code. Two of the twenty-three took a name other than their own lowercase, and the reason is Go rather than taste: `Styles` became `styleSet` because 63 parameters are already spelled `styles Styles` and Go resolves a parameter's type in the scope its own name is declared in, and `Item` became `listItem` because `item := messageItem{...}` is a local in three files — renaming one type beats renaming 133 identifiers in a change whose value is that it is mechanical. One symbol was **deleted rather than unexported**: `RawRenderable`, the optional "give me unstyled text" hook on `Item`, along with the `RawRender` method `messageItem` carried for it. Unexporting it made the compiler say what a grep should have said years earlier — nothing ever type-asserted to the interface, nothing ever called the method, and the `ansi.Strip` fallback its own comment promised was never written. The copy path ([#153](https://github.com/go-steer/core-tui/issues/153)) reaches `rawMessageText` directly from the `Message`, which is what it has in hand, and always did. Nothing in §3.2's *promote to contract* groups is affected: `Theme`, `BuiltinThemes`, `ThemeByName`, `ThemeChangedMsg`, the seven transcript symbols and `SystemClipboardWriter` are all still exported and still supported.

- ⚠️ **Four dialog symbols nothing outside the package could reach: `KeyMsgDialog`, `Overlay.HandleKey`, `NewTextInputDialog` and `TextInputConfig`** ([#254](https://github.com/go-steer/core-tui/issues/254)). The first acknowledged breaks since v0.21.0, and they are breaks in the letter rather than in the spirit: building a dialog is only half of opening one, and the other half is an `Overlay`, of which the only instance in existence is an unexported field of `Model`. An external implementation of `KeyMsgDialog`, or a `TextInputConfig` filled in from another module, compiled and then had nowhere to be installed — which is the argument [`docs/api-surface.md`](./docs/api-surface.md) §3.2 makes against the whole 25-symbol render-extension set, and these four are the ones the question seam ([#164](https://github.com/go-steer/core-tui/issues/164)) freed first. `Dialog`, `DialogAction`, `ScrollDialog` and `Overlay`'s remaining methods stay exported, because the three viewers — the tool-call detail, the subagent drill-down and the `/btw` side answer — still use them. `SessionInput` is untouched in every respect: an action row still opens a text input and `SessionInput.Submit` still has the signature it always had, which is worth stating because it is the one host-facing callback in this area and the one an adapter might reasonably fear for. **Upgrade action: delete the reference.** If your adapter names one of these it is in dead code, and [`MIGRATION.md`](./MIGRATION.md) §7 says the same at more length. Two of the four are worth a word on their own. `Overlay.HandleKey` was the stroke-string half of a two-entry-point routing split; `HandleKeyMsg` does everything it did without discarding `Key.Text`, its last caller synthesizes a `tea.KeyPressMsg` rather than going the other way, and two entry points into one routing decision is one place for the two to drift. And `TextInputConfig` was going to be *reshaped* rather than removed — #164 §10.1 planned to narrow `Submit` from `func(string, *Model) DialogAction` to `func(string) error` on the assumption that the text input would become a question and its effects would move to a resolver. It did not: §13 keeps it a `Dialog`, and the narrower shape does not fit its one caller, since the action row's in-flight commit has to return a `Cmd` and has to stay open while the host's dial is out. Reshaping would also have spent a pre-1.0 break on a field of a type the §3.2 sweep takes off the surface anyway, and then spent a second one removing it. So `Submit` keeps its signature, one storey down, where it is nobody's promise.

## [0.21.0] — 2026-08-17

The exported surface stops growing and starts shrinking. Twenty optional capability interfaces are sixteen, twenty-seven incidental symbols are unexported, `Focusable` is gone entirely, `ToolRenderer` is unexported until it has a seam worth exporting, and what remains is enumerated symbol by symbol in `docs/design.md` §3 with a test that fails when the document and the code disagree. The point of writing it down is that it can now be enforced: CI diffs the exported API against the last release tag on every PR and fails on an incompatible change unless the author acknowledged it in `dev/api-breaks.txt`, in the same diff hunk the reviewer is already reading. A host's build breaking at `go get` used to depend on whether someone noticed in review.

Dialogs stop being one-off state machines. A dialog can now answer a question instead of reaching into the model to mutate it, which is what lets the model and session pickers become questions rather than special cases — and what makes a failed switch leave the list up instead of dropping the operator back into a chat with no explanation. Around that seam the modal surfaces got the treatment they had been missing: a box edge on every one of them, bodies padded by measuring rather than by word-wrapping, footers that no longer break between a key and the thing it does, floating over the frame instead of blanking it, and five host-content dialogs added to the frame-invariant grid so a panel that escapes its rectangle fails a test rather than a bug report. The elicit contract is honest in all three of its parts: a request the TUI cannot draw is announced to the operator, reported to the host as `ErrElicitUnsupported`, and no longer misattributed to an operator who was never asked — and the form's decline path, documented since it was written, is reachable at last.

Underneath, the repaint path stopped doing work it had already done. A static repaint allocates 1,026 objects where it used to allocate 5,177: the render memo answers a hit without allocating, the input box and status header are rebuilt when they change rather than on every frame, and the working directory is resolved once at construction instead of per paint. Terminal fidelity caught up in the same pass — tabs wrap where they are drawn, long unbreakable tokens stay inside the chat column, a theme with a wider prompt glyph no longer leaves the composer wrapping to the old one, and the spinner's glyph actually animates. The test harness is the last thread: the TUI is driven through a real `tea.Program`, coverage has a floor CI enforces rather than a number CI prints, macOS is compiled and tested rather than merely promised, and `examples/core-agent` doubles as a compile-time canary that breaks the build in this repository when the plug-in surface moves under its 18 asserted interfaces.

### Added

- **N-TEST's coverage floor is a check, not an aspiration** ([#83](https://github.com/go-steer/core-tui/issues/83)). The requirement has asked for ≥ 70% statement coverage in `package tui` since the first draft, and nothing measured it — CI computed a coverage summary and printed it, which is a number nobody reads until they go looking. It turns out the target has been met for a while: the issue was filed at **58.1%** against v0.19.0, and v0.20.0's 42 commits took it to **77.7%**, so the work it describes is done and what was missing was the thing that keeps it done. `dev/tools/verify-coverage` now reads the profile the test step already wrote and fails below the floor, wired as a step inside the existing required `test` job — a new top-level job would need a branch-protection edit before it could block anything, and until that happened a regression would merge green. It runs after the summary and the artifact upload so a failure still leaves both behind, and prints the worst uncovered functions on the way out. Two deliberate choices. The floor is the stated **70%** rather than today's 77.7%, because a floor pinned to the current number is a ratchet, and a ratchet makes every later PR that moves a statement into an untested branch inherit someone else's backlog. And the measurement covers `package tui` alone, excluding `examples/` (wiring sketches, 0% by construction) and `tui/testagent` (a fixture) — averaging those in measures the shape of the repo rather than the coverage of the library, and moves the number whenever an example is added. Percentages come from summing statement counts out of the profile rather than averaging `go tool cover -func`'s per-function figures, which would weight a three-line helper the same as a three-hundred-line renderer.

- **CI builds and tests on macOS** ([#84](https://github.com/go-steer/core-tui/issues/84)). N-PORTABLE has promised macOS terminals since the first requirements draft, and every job in the pipeline was `runs-on: ubuntu-latest` — darwin had never been compiled, let alone tested. That is not a theoretical gap for a TUI: capability detection, the OSC-11 background query, the clipboard helper table ([#175](https://github.com/go-steer/core-tui/issues/175)) and mouse-mode handling all diverge there. A `test (macos)` job now runs vet, build and the race-enabled unit suite on `macos-latest`. It is a separate job rather than a `matrix.os` on `test` because matrix-expanding a job renames its check to `test (ubuntu-latest)`, and `test` is a required check on `main` — the rename would park every open PR on "Expected — Waiting for status" until branch protection was edited to match. It is also not required to merge yet: a macOS runner queues slower than ubuntu, and a required check that is merely slow blocks everything. `lint`, `tidy` and `govulncheck` stay ubuntu-only, being platform-independent. N-PORTABLE now states what CI actually proves — that the code compiles and its tests pass on both kernels — and keeps the named emulators as the manual-verification claim they have always been.

- **`examples/core-agent`, and a compile-time canary on the plug-in surface** ([#82](https://github.com/go-steer/core-tui/issues/82)). core-tui has exactly one gating host and it lives in another repository, so nothing in this repo noticed when the plug-in surface moved: a rename or a signature change under `tui/` built clean here, tested green, and presented the bill weeks later when core-agent next upgraded. `docs/design.md` §7 has wanted an adapter example since the first draft; this is it, and its second job is the more valuable one. Between its two adapters the example asserts `var _ tui.X = (*adapter)(nil)` for **18 interfaces**, so a moved capability now breaks `go build ./...` in the repository that moved it.

  Two flavours, because both are shapes core-agent actually ships and they are genuinely different adapters rather than one adapter with a flag. `local.go` holds an in-process agent: `Run` drives the host's own `iter.Seq2[*Event, error]` per turn, flattens the nested `Event → Content → []Part` tree onto core-tui's flat `tui.Event`, and folds the trailing usage metadata into a host-computed per-turn cost before yielding the committed event. `attach.go` holds a *client*, not an agent: it subscribes to the remote event stream **before** injecting the prompt — the other order races the first partials against the subscription — reads SSE frames against a sequence cursor and stops on `TurnComplete`, serves observer mode through `Events` with `?since=N` resume and 1s→30s backoff reconnect, and answers status and usage out of a one-second poll cache that a `TurnComplete` frame invalidates.

  It builds against a local stand-in for core-agent's types rather than against the module, deliberately: core-agent depends on core-tui, so importing it here would be an ecosystem-level import cycle, and it would tie this repo's CI to another repo's release cadence. The stand-in is shaped after the real thing — the nested event tree, the attach frame format, the in-band tool-error key — and the attach flavour serves its canned events over a real loopback listener, so the SSE parsing and the reconnect path are exercised rather than mocked. One shared turn-shape assertion runs against both flavours, which is what proves they agree rather than merely both compiling. The issue also asked for `examples/cogo`; it is not built and nothing re-adds it, since [#76](https://github.com/go-steer/core-tui/issues/76) dropped cogo as a gating consumer and `I-COGO` is already out of `docs/requirements.md`.

  Writing it was also the excuse to measure the **"≤ 50-line adapter"** that `docs/design.md` §1 goal 4 had promised since the first draft, and the number did not survive contact. The *minimum* adapter — event translation and `Run`, zero capabilities — is 64 non-comment lines, and the two reference-shaped ones in this deliberately condensed example are 257 (local) and 380 (attach) against core-agent's real ~1,050 and ~1,630. The goal now says "small adapter" and records the measurements next to it rather than dropping the old figure quietly; `docs/requirements.md` I-CORE-AGENT is untouched, having never named a number. The gap is not in `Agent`, which is still two methods. It is capability-surface tax, and it is input for [#77](https://github.com/go-steer/core-tui/issues/77).

- **The TUI is driven through a real `tea.Program` in tests** ([#81](https://github.com/go-steer/core-tui/issues/81)). `docs/design.md` §7 describes three test layers and two of them existed. Every test under `tui/` called `Update(msg)` directly — a fine way to exercise a reducer and no way at all to notice that `Init` never fired, that the event loop deadlocked, or that quitting left the operator in a terminal still in alt-screen with mouse reporting on. The `View()` wedge and its SIGQUIT escape hatch ([#69](https://github.com/go-steer/core-tui/pull/69)) were exactly that shape of bug and exactly that invisible to the suite. Three scenarios now build a real program over an `io.Pipe`, type at it, and assert on the bytes the renderer emits. Startup through a submitted prompt, two streamed chunks and the per-turn usage footer, out through the slash palette to `/quit`, requiring `p.Run()` to return without error. The permission round trip in both layouts across allow-once, deny and allow-always, with the agent fixture blocking mid-turn inside `Prompter.AskApproval` so the test drives the real modal with the real key, asserts the decision echo *and* that the turn resumed on the correct branch, and pins `AlwaysAllow` firing with the right `ToolName` / `PersistKey` on exactly one of the three arms. And a teardown check that scans the raw output for the final state of every DEC private mode the TUI sets — `?1049` alt screen, `?1002` / `?1003` mouse tracking, `?1006` SGR mouse encoding, `?2004` bracketed paste — and requires each of them to end reset, table-driven over `Options.Mouse` and non-vacuous in both directions: with the mouse on, the modes must have been set *and* reset; with it off, never set at all.

  A layer that can hang is worse than no layer, because the failure is a five-minute stall on the package timeout with nothing to read at the end of it, so the harness is built so that a hang is a loud failure with the last frame attached. The program runs under `tea.WithContext` with a timeout and in its own goroutine; every wait is a bounded poll of the captured output with its own budget that fails with the ANSI-stripped tail of the frame on expiry; cleanup cancels, closes both pipe ends, waits, and only then kills, complaining if it had to. Input is an `io.Pipe` rather than a `bytes.Buffer` on purpose — a drained buffer returns `io.EOF` and the terminal reader treats EOF as a clean end of input, so a buffer works for one pre-loaded script and then silently stops being reactive, which is useless for a test that has to press a key *in response to* a modal. The colour profile is pinned through `tea.WithEnvironment` so an ambient `CLICOLOR_FORCE` cannot interleave SGR through the assertion tokens. There is exactly one `time.Sleep`, in the permission test, and it is commented as such: `modalInputGrace` ([#95](https://github.com/go-steer/core-tui/issues/95)) makes the decision keys inert for a fixed wall-clock window and there is no signal a test can observe to know it has elapsed. The constant is re-exported to the external test package rather than copied, because a copy rots silently the day someone retunes the window — the smoke tests would start typing `y` into the composer and failing on an assertion that says nothing about why — and the wait was confirmed load-bearing by mutating it to zero, which fails with a dump showing the `y` swallowed.

  The layer caught no live defect, which is the expected result for a net dropped under a suite already at 77.7% coverage and not an argument against having it: the bugs it exists for are the ones that cannot be reached from `Update` at all. It did surface one thing worth writing down. `promptListener` blocks on `context.Background()` rather than on the program context, so its `Cmd` goroutine outlives the program; that is harmless only because Bubble Tea leaks `Cmd` goroutines at shutdown instead of waiting on them, and the day that changes, `p.Run()` wedges. Not fixed here — this change touches no production file; [#202](https://github.com/go-steer/core-tui/issues/202), below, is where it gets fixed, and it turned out to be four other listeners as well.

- **The frame-invariant grid asserts that every panel is still in its rectangle** ([#158](https://github.com/go-steer/core-tui/issues/158)). The invariants that landed with [#101](https://github.com/go-steer/core-tui/issues/101) measure two numbers — no line wider than the terminal, no more rows than it has — and a frame that has silently lost an entire panel scores perfectly on both, because the survivors reflow into the freed rows and the dimensions still check out. The clip pass is *why*, not merely how: clipping is exactly what makes an oversized frame legal, so `assertFrameFits` cannot fail on a lost panel; it has to pass. That failure mode has already shipped twice here, the modal footer both times ([#142](https://github.com/go-steer/core-tui/issues/142), [#149](https://github.com/go-steer/core-tui/issues/149)), and the rendering spike found a third: a sidebar loop that capped at *n sessions* rather than *n lines* pushed the input row and the footer off the bottom of every frame while the whole invariant suite stayed green. It was found by running the preview binary and looking at it. A safety net should not exist without an assertion beside it that says what fell.

  The assertion is **positional**, and deliberately not `strings.Contains`. That file exists to undo 202 `Contains` assertions that proved nothing, and "the footer text appears somewhere in the frame" is the same mistake in new clothes — a sidebar collapsed to one column contains its markers, a footer composed into the middle of the chat contains its markers, and both frames are broken. The composed frame is turned into a grid of display **cells** (not bytes and not runes; box-drawing glyphs and CJK are neither), each panel is located in that grid by re-rendering the panel and matching its own text, and each is required to occupy the rectangle the layout contract gives it: status header, chat, help panel or palette, input box, toast, footer legend, the sidebar band, and the modal block when one is up — across the same width × height × layout × state matrix and the resize sequence.

  The expected row of a panel is the sum of the heights of the blocks above it, taken from the very renderers `View` joins and **never** from `m.chrome`. That is the point of the exercise. `allocateChrome` is one of the things that can break, and a test whose expected geometry came out of the allocator would cheerfully assert the bug; with the sum taken from the renderers, a budget that hands the help panel rows the input box needed shows up as a stack overflowing a terminal that `irreducibleRows` says had room for it. Three checks sit outside the block match, because a renderer that has collapsed still matches its own output perfectly: a sidebar floor of three rows and sixteen columns, an input-box floor of its border plus `textareaMinHeight` — an operator who cannot see the line they are typing cannot drive the TUI — and the requirement that the sidebar band is **blank below the sidebar's last row**, since `JoinHorizontal` pads the shorter column and anything drawn there is content the renderer did not account for. That last one is the only way to see a panel grown past its rectangle *between* the renderer and the join. One hole is stated in the file rather than papered over: below the irreducible chrome, a panel dropped past the clip point produces a byte-identical frame, so two cells of the grid are exempted through `irreducibleRows` — a helper that measures the panel renderers and the two published floors and never consults the allocator, so the exemption cannot widen when the allocator misbehaves. Verified against fourteen deliberate layout mutations, all of which it catches.

- **CI diffs the exported API against the last release tag** ([#80](https://github.com/go-steer/core-tui/issues/80)). The 1.0 promise is a claim about a surface that nothing measured. `dev/tools/verify-apidiff` now diffs the module's exported API against the nearest reachable `v*` tag on every pull request, prints the compatible additions, and fails on incompatible changes — as its own `apidiff` job and as a step in `dev/tools/ci`. It runs in **module mode** rather than over a package list, so a newly exported package cannot slip in unmeasured; apidiff itself always exits 0, since it reports rather than judges, so the gate is the emptiness of its incompatible output. Pre-1.0 an unconditional gate would be wrong — it would block the narrowing work [#77](https://github.com/go-steer/core-tui/issues/77) and [#78](https://github.com/go-steer/core-tui/issues/78) call for — but "you may break it" is not "you may break it silently". `dev/api-breaks.txt` is the hatch: copy the offending apidiff lines into it with a `#` comment naming the issue, in the same pull request that makes the break. A label or a commit trailer would not survive this repo's squash merges; a checked-in file is a reviewable diff hunk, and it doubles as the raw material for the next release's **Removed** section. Cutting a release empties it. The tool is pinned to a pseudo-version, unlike govulncheck, because here the compatible/incompatible classification *is* the gate and a floating version could turn a green pull request red with no local diff to explain it. It is deliberately **not** a required check on `main` yet: it depends on a tag being fetchable, so a mirror hiccup or a moved tag would redden unrelated pull requests — worth making required after a release cycle of clean history. Documented under "Changing the exported API" in `CONTRIBUTING.md` and as **N-COMPAT** in `docs/requirements.md`.

- **The five host-content dialogs are in the frame-invariant grid** ([#211](https://github.com/go-steer/core-tui/issues/211)), so the width contract, the panel-rectangle check and the background-survival assertion apply to them. `frameStates()` is the state axis all three assertions iterate, and the only dialog in it was the theme picker — chosen because it needs no host capability to populate itself, which is also precisely what made it unable to fail any of them: its rows are a compiled-in table of one-word theme names, so nothing it renders can overrun a width, grow past a rectangle, or spill over a background row. Meanwhile the two surfaces carrying the most untrusted text in the package were outside the grid entirely — the session picker, whose cells splice the host's `Display` and `Description` in verbatim, and the model picker, whose rows carry provider-qualified ids, which is the exact shape of content the sidebar overrun was found on. The session picker, the model picker, the pickers' filter row, the subagent drill-down and the tool-call overlay are all states of the grid now, each seeded with at least one row that overruns its dialog on its own: a gateway-qualified id rendered twice on one row, a session title and a detail line that each overrun separately, an untruncated subagent report, a tool response wider and taller than the overlay it renders in. Two of the grid's heights sit below `modalFullscreenBelow`, so the new states also drive every windowing dialog through the fullscreen regime, where the margin is gone, the body floor is off and every visible row carries a scrollbar cell — geometry no golden had ever contained. The grid grows from 9 states to 14 and from 360 to 560 cells per assertion. A companion assertion checks the fixtures themselves are wider than the dialogs that have to bound them, so a future edit cannot quietly shorten the seed content back into the case that always passes; verified against four injected width defects, one per dialog, all of which shipped green beforehand.

### Changed

- **The session picker is a question, and its action row starts another one** ([#164](https://github.com/go-steer/core-tui/issues/164), stage 3 of [`docs/design-question-dialogs.md`](./docs/design-question-dialogs.md) §12). Same asynchronous shape as the model picker below — Enter commits, the list stays up showing progress, the host's reply is the answer — and the same two `*Model` reaches leave the widget for the same reasons, the `SessionSwitcher` assertion and the `Sessions()` call the body was making *while rendering*, which was one of the three documented ways a host call had got inside `View()`. What makes this the harder of the pair is that Enter has three outcomes rather than one, and which one you get is decided entirely from the row. A plain row commits and waits. The **attached** row answers in the same keystroke, because there is no session to attach to and no call to make — and that arm has to exist, not merely as an optimisation: routing it through the attach path would wipe the transcript to re-fill it from a session the operator is already in. And an **action row** ([#56](https://github.com/go-steer/core-tui/issues/56)), the `+ Attach to endpoint…` shape, neither answers nor dismisses: it needs an address typed, which is a question this question cannot ask, so it names the row and the Update loop opens the text input on top. That indirection is forced rather than stylistic — the overlay pops the front dialog after `Key` returns, and a resolver is no better since `resolve` pops after *it* returns, so a widget that opened its own follow-up modal would watch the stack pop the thing it had just pushed. The picker deliberately does **not** seed its cursor onto the current row the way [#110](https://github.com/go-steer/core-tui/issues/110) made the model picker do: a session list is a history, the attached session is the one row an operator is least likely to be reaching for, and it is already marked `(current)`.

  The action row's text input stays a `Dialog` on purpose, because it is the one modal in the package that has to *end somebody else's* question, and it now does that through `Overlay.resolve` instead of `Overlay.Close` — closing the picker by ID would pop it with its resolver never run, which is the "torn down and nobody was told" hole the design exists to remove, reintroduced two files away from where it was fixed. The mapping is written down rather than implied: a successful attach resolves the picker with `chosen` carrying the row ID, since the operator really did pick that row and the address they typed is merely how it got resolved, and a failure resolves it as superseded, since nobody chose a session and it was the input, not the operator, that took the list down. **One behaviour change an operator will notice**, and it is the model picker's, adopted here for consistency: an attach that fails now leaves the picker open on its list instead of closing it. Two adjacent pickers behaving differently on the same failure is worse than either choice on its own. The action row is the deliberate exception — it closes both modals on failure, because the operator typed an address that did not work, the error row in the transcript is the whole report, and a modal left up would bury it. Nothing exported moved.

- **The model picker is a question, and a switch that fails leaves the list up** ([#164](https://github.com/go-steer/core-tui/issues/164), stage 3 of [`docs/design-question-dialogs.md`](./docs/design-question-dialogs.md) §12). The theme picker went first because it is synchronous — the keystroke that picks a row is also the moment the answer exists. This one is the other shape, and it is the shape the session picker, the permission prompt and the elicit form all share: Enter starts a host call, the modal stays on screen showing progress because a list that freezes for as long as the host takes reads as a hang, and the answer arrives from the Update loop several hundred milliseconds later when the reply lands. That needed a seam the first stage did not have, `Overlay.resolve`, and it exists to stop the obvious shortcut: closing the modal from the reply handler would pop it with its resolver never run, which is exactly the "torn down and nobody was told" failure the whole design is about, reintroduced by the code meant to remove it. Four reaches into `*Model` left the widget with the migration — the `ModelSwapper` type assertion, the `displayModelName()` call it was making *while rendering*, the transcript append, and building the host `Cmd` out of the live session generation — and the last of those is why Enter now names a model rather than calling the host itself: the swapper and the generation can both move while the picker is open, so they are read when the request lands rather than captured when it opened. **One behaviour change an operator will notice**: a switch that fails now leaves the picker open on its list instead of closing it. The question was never answered, the failure row is already in the transcript, and the next move after "provider unreachable" is almost always the next model down — closing would make them re-run `/model` to get back to a list they were already looking at. Two rules fell out of pop ordering and are recorded in §6.5 rather than left to be rediscovered: a resolver must not open a dialog, because `resolve` pops after the resolver returns and would pop whatever the resolver just pushed; and a committed question is not an answered one, so esc during an in-flight switch closes the modal while the call it already sent still applies. Nothing exported moved.

- **Dialogs can answer a question instead of mutating the model** ([#164](https://github.com/go-steer/core-tui/issues/164), stage 1 of [`docs/design-question-dialogs.md`](./docs/design-question-dialogs.md) §12). A dialog's `HandleKey` returns a `DialogAction`, which says how the *overlay stack* should react — consumed, close, run this `Cmd` — and says nothing about what the operator decided. So every dialog that asks a question has had to reach into a `*Model` and carry out the consequences itself, from inside the widget: the theme picker's Enter arm applied the theme, appended a transcript row, refreshed the viewport, emitted `ThemeChangedMsg` and scheduled the host's persistence callback, sixty lines away from the esc arm that is its counterpart. The cost is not tidiness. It is that a widget which mutates a model cannot be tested without one, and that a dialog torn down by something other than a keystroke — a session switch, a reload, a quit — never runs any arm at all, so whatever was waiting on the answer is simply stranded. There is now a sealed `answer` type with seven variants (`dismissed`, `declined`, `chosen`, `selected`, `text`, `fields`, `decision`), a `question` seam a widget implements with no `*Model` anywhere in it, and a `resolver` that receives the answer alongside the model and performs the effects. `dismissed` carries a reason — escape, superseded, shutdown, unrenderable — so "the operator said no" and "nobody ever got to ask" stop being the same value, and `Overlay.resolveAll` can hand every open question a reason and batch whatever their resolvers schedule, which is the mechanism the stranded-teardown case needs. The theme picker is the first and so far only caller, chosen because it is the smallest, had the most effects per line of any modal, and is the one whose host-visible message has no consumer. **Nothing exported moved**: `Dialog` and the old path are untouched, questions ride the existing stack through an adapter, and `apidiff` reports no change. Two things are worth recording as bugs the shape prevents rather than features it adds. The sealing is checked — `answer` carries `//sumtype:decl` and stage 0's linter is running — so the resolver names all seven variants and an eighth added later is a lint failure at every switch rather than a silent fall-through to "do nothing". And the live preview, the one effect a picker has to cause *before* it has an answer, is now a message the Update loop applies while the picker is still open; without that guard an operator who arrows onto a theme and immediately escapes could have the asynchronous preview land after the restore and keep a theme they explicitly cancelled.

- **Enum switches are total, and a linter keeps them that way** ([#164](https://github.com/go-steer/core-tui/issues/164), stage 0 of [`docs/design-question-dialogs.md`](./docs/design-question-dialogs.md) §12). The design for typed question dialogs turns on a sealed answer type, and its §5.3 makes an argument worth repeating outside that context: **Go type switches are never exhaustiveness-checked by the compiler**, sealed or not, so sealing buys nothing on its own — it buys the *ability* for a tool to enumerate the variants, and the tool has to be running. `gochecksumtype` and `exhaustive` are now enabled in `dev/tools/.golangci.yml`. `gochecksumtype` finds nothing today, there being no sealed interface yet; it is scaffolding, and enabling it first is what makes the sealed-vs-struct question in that design answerable rather than a preference.

  `exhaustive` found eleven switches, and they were not a mess — they were one idiom applied consistently. Every one put the enum's *zero value* on a `default:` arm: `PermissionMode.String()`, `QueueState.String()`, `queueRowStyle`, `permissionDecisionLabel`, `renderPermissionDetail`, `formatElicitValue`, `elicitCursor`, `bannerStyle`, `permissionRuleCmd`, `View`'s layout switch and the `huh.FormState` switch behind `/pricing set`. That idiom is safe and it is also exactly what makes a *new* member invisible: add one, and it routes silently to whatever the zero value does. Each switch now names every member and puts the out-of-set fallback below it, which is the same code with the two meanings separated — "this is what the zero value does" and "this is what a value we have never heard of does" were the same line and are now different ones. `default-signifies-exhaustive` is deliberately **not** set, since turning it on would have made the linter agree with all eleven and find nothing ever again.

  One behaviour change falls out. `effectiveLayout` now normalizes to a declared `StatusLayout` member instead of returning whatever it was given: `StatusLayout` is an exported int and `Options` takes it by value, so a host can hand the model `StatusLayout(7)`, and that used to reach `View` and land in the layout switch's `default:` arm, which drew the header layout by accident of arm ordering. The clamp belongs in the function whose job is clamping. Two tests pin it — the resolution itself, and that an undeclared layout still renders a frame byte-identical to the header layout, because a switch made total without a clamp ahead of it would have rendered an empty body, which is a blank terminal rather than a degraded one.

  `SA5011` is excluded in `_test.go` and the exclusion is scoped to that check. It is a harness artifact: with both new linters enabled, golangci-lint v2.12.1 loses the noreturn fact for `(*testing.common).Fatal` and reports every `if got == nil { t.Fatal(…) }` followed by a field read as a possible nil dereference. Neither linter alone provokes it, and `staticcheck -checks SA5011` run standalone over the same tree reports nothing.

- **`ctrl+x` opens the tool-call overlay on the row the cursor is on** ([#233](https://github.com/go-steer/core-tui/issues/233)). The overlay was built before the transcript had a cursor, and its own file header said so — it presents its own navigable list of every tool call in the session precisely so that nothing had to be selected first. [#152](https://github.com/go-steer/core-tui/issues/152) added a cursor and the two features never met, so selecting a tool row and pressing `ctrl+x` opened on the *newest* call and left the operator to walk back to their own choice with `←`, counting tool calls on the way. The open site now seeds the overlay's index from the selection, matching on `Message.ID` rather than counting `RoleTool` rows up to the cursor — the ID is the identity `History` already issues and the fold map already keys by, so the two cannot disagree if they ever read different snapshots. Only from focus mode: the selection marker is drawn only while the transcript holds the keyboard, so seeding from the composer would aim the binding with a cursor nobody can see. Composer focus, a selected row that is not a tool call, and an empty transcript all still open on the most recent call, which is what the binding has always done. The list is still the navigation — this only changes where it starts.

- **The session picker renders each session as a two-line cell** ([#163](https://github.com/go-steer/core-tui/issues/163)). One row carried the display name, the ID, `(current)` and the description all concatenated together, so the title — the thing actually being chosen — competed with three pieces of bookkeeping and lost the moment the dialog narrowed. Worse, most hosts leave `SessionInfo.Display` empty today, which degraded the picker to a list of opaque identifiers. A cell is now a title line and a muted detail line: `Display` on the first, falling back to the ID so line one is never blank, and on the second the ID (only when it differs from the title, and without the parentheses that existed to fence it off from a title it no longer shares a row with), `(current)`, and the description. The selected cell keeps `> ` on its title line and draws the transcript's dotted selection bar ([#152](https://github.com/go-steer/core-tui/issues/152)) down its second, so the cursor marks a *cell* rather than a line — `> ` above blanks is ambiguous the moment two cells are adjacent. Action rows ([#56](https://github.com/go-steer/core-tui/issues/56)) keep their `▸` chevron on the title line next to the label it qualifies and get no identity line; they name no session that exists. The visible cost is that roughly half as many sessions fit at a given terminal height, which is what type-to-filter ([#117](https://github.com/go-steer/core-tui/issues/117)) is for.

  Cells are exactly `sessionCellLines` (two) rows tall, always, padding the detail line when there is nothing to put on it — and that constant is what keeps the change contained, because it lets the window arithmetic convert an item cursor to a line cursor by multiplying. `d.idx` stays item-indexed, so the key handler, the index clamp, the stepper, the filter, the ranker, `scrollView` and `listWindow` are all untouched. Variable-height cells would turn that multiply into a prefix sum rebuilt on every filter keystroke and drag the shared helpers along with it; the trade is rejected explicitly in a comment on the constant. The trap is that `listWindow` keeps *one* cursor line visible and a cell is two, so a single call can only ever keep half the selected cell — pass the title and the detail line clips off the bottom while scrolling down, pass the detail and the title clips off the top while scrolling back up. Hence two calls, detail first and title second, so the title wins the tie on a one-row window; for any window of two rows or more the second call can only move the offset up to reveal the title, which cannot push the line below it back out. The offset is deliberately *not* snapped to a cell boundary — rounding an odd offset breaks the invariant those two calls establish at one edge or the other, and a half cell peeking in at an edge is the cheaper defect. Rows are appended one per line and never as one string containing a newline, because `scrollView` hands each row to `fitRow` ([#157](https://github.com/go-steer/core-tui/issues/157)) and an embedded newline would be budgeted as one row and painted as two. Populating a real title stays host work: the TUI sees an ID and whatever the host put in `Display`, and has no transcript to summarise.

- **`/switch <id>` and host slash dispatch no longer run on the event loop** ([#137](https://github.com/go-steer/core-tui/issues/137)). v0.20.0 moved the capability calls off the `Update` goroutine and deliberately left two behind, both two-stage and both needing a staleness story before they could be deferred. This finishes the issue. `/switch <id>` enumerated sessions with a synchronous `Sessions()` and then called `SwitchToSession` in the same frame, so a host that lists sessions over the network froze the UI for the whole round trip; it is a genuine two-stage path now, where a lookup command enumerates off-loop and returns the matching row, and the reply either opens the session's action-row dialog ([#56](https://github.com/go-steer/core-tui/issues/56), unchanged) or fires the existing switch command for stage two. The switch is never fired before the lookup has come back, and a superseded lookup is dropped without switching anything. `dispatchSlash`'s match loop walked `SlashCommands()` inline to decide whether a typed name was known and then called `InvokeSlash(context.Background(), …)` — synchronous *and* handed an unbounded context; match and invoke move together, and the invoke leg runs under a bounded 60s context, since `InvokeSlash` takes one. Both follow the shape `tui/host_async.go` established: capability handle resolved before the closure, generation stamped at construction, no model state touched from the goroutine, nil `tea.Cmd` when the capability is unwired.

  Deferring the name match changes the timing of the *negative* reply, and that is the one behaviour change worth knowing about. "unknown command /foo" used to be written in the same frame as the keystroke; asynchronously it arrives a frame later and could land underneath the output of whatever was typed next — type `/foo`, then `/help`, and the stale complaint about `/foo` prints below the help listing. A per-dispatch counter, `slashSeq`, is bumped for every submitted command, built-in or host, since typing a built-in is just as much the operator moving on; both new messages carry it alongside `sessionGen`, and `Update` drops any reply that has been overtaken. `sessionGen` alone is too coarse — it turns over only on a session switch, and slashes are typed back to back inside one session. After this, no capability method is called on the event loop at all. What is left in an `Update` frame is the `InvokeSlashAsync` variants, which the contract defines as returning a channel immediately, and one `SlashCommands()` read reached only from an already-off-loop command.

- **A static repaint allocates 1,026 objects instead of 5,177** ([#160](https://github.com/go-steer/core-tui/issues/160)). The issue's headline figure — around 50,000 allocations for a frame in which nothing changed — was true when it was filed and is not the number this fixes; [#161](https://github.com/go-steer/core-tui/issues/161) and [#157](https://github.com/go-steer/core-tui/issues/157) had already taken roughly 10x of it, and a re-measurement before touching anything put the same frame at 1.5ms, 194KB and 5,177 allocations. The premise survived the correction: the allocations were still concentrated in one call and still flat at every transcript size, which is what makes them a collector problem rather than a layout one. 69% of a frame sat under `chatView` and 83% of *that* under a single line — the whole visible transcript block handed to `lipgloss.NewStyle().Width(…).Height(…).Render(…)` to be squared off. `lipgloss.Wrap` pipes the block through a `WrapWriter` whose `Write` copies its input to the output **one byte at a time**, allocating a `[]byte{b}` per byte of the frame, in order to word-wrap rows that `chatCutLine` has already cut to exactly the target width — a wrap that cannot, by construction, have anything to do. It is the same defect [#157](https://github.com/go-steer/core-tui/issues/157) fixed one modal row at a time, batched over the whole visible chat and sitting on the per-frame path; #157's audit flagged this line and left it here on purpose.

  The block is measured and padded now, with the width-setting `Style` kept as a whole-block fallback because two of the things it does besides wrapping have to survive: it expands tabs to four spaces, which matters because `sanitizeLine` deliberately exempts TAB and appending spaces to a row holding one would leave the row narrow; and it closes a style still switched on at a newline and re-opens it on the next, so a row carrying escapes straight from a host — a tool result, a subagent transcript — does not bleed downward. `chatRowPlain` decides which regime applies as a byte scan, so establishing the common case costs no allocation, and the fallback is taken for the **whole block** rather than per row: mixing the two per row would mean reproducing the wrapper's cross-row style state, which is the only genuinely hard part of it. Two smaller findings from the same profile came with it. `sgrIsReset` split its parameter string to check each field, which was one slice per modal row per frame before and one per *transcript* row per frame once the new path started asking the same question — where "every field is zero or absent" is the same predicate as "every byte is `0` or `;`" and needs no slice. And `chatSeparator` returned a fresh one-element slice per non-user row per frame for a value that is a constant.

  Medians of six runs: 1.01ms, 139KB and 1,026 allocations, against 1.51ms, 194KB and 5,177 — at 10, 100 and 400 turns alike, so still flat in transcript size, which is #161's property and is preserved. Wall time is down about a third; the allocation count is the number the issue is about, since the latency it describes is the collector's rather than the frame's. Against the original headline, a static repaint has gone from 50,297 allocations to 1,026 across three changes, a factor of 49. Output is **byte-identical** and no golden moved, which is the real assertion — an allocation reduction that changes a byte is not one. `TestStaticRepaintAllocations` guards it with a **ceiling of 1,500** rather than a pinned figure, and the comment says why at length: a number pinned to today's measurement is a ratchet that every unrelated chrome change has to edit, the edit is never questioned, and after a dozen of them the assertion has tracked the regression it existed to catch. What is being defended is an order of magnitude, so the useful question is whether a frame is still in the low thousands. What remains is written down rather than guessed at: `renderInputBox` is now the largest single consumer of a frame at 60.5% — almost all of it `bubbles`' textarea re-rendering and re-wrapping itself every frame through the *placeholder* path, which means the cost is highest when the input is empty — and the header chrome is 8.8%, both of them in `view.go` and both worth their own issues.

- **`docs/design.md` §3 enumerates the frozen exported surface, symbol by symbol** ([#78](https://github.com/go-steer/core-tui/issues/78)). `package tui` exports **265 top-level symbols** — 107 types, 85 constants, 29 functions, 5 package vars and 39 methods on exported types — and nothing in the tree distinguished the §3 contract from a symbol that merely started with a capital letter, so at 1.0 all 265 would have become compatibility promises by default. The new `docs/api-surface.md` classifies every one of them into exactly one of three buckets: **156 contract**, **42 host-useful but unpromised** (each carrying an explicit promote-or-unexport recommendation), and **67 incidental** (each carrying the mechanical cost of unexporting it — call-site counts, and which entries are blocked behind files that other in-flight work holds). It is generated from `go doc -all ./tui` and cross-checked against a `go/doc` and `go/ast` walk of the 67 non-test files.

  Two things in the issue's framing turned out to be wrong, and the document says so. **174 was the wrong number**: the arithmetic holds for types, functions and methods, but it omits the 85 constants and 5 vars — including the `TurnError*` / `TurnState*` / `InboxState*` wire vocabularies a host pattern-matches against, which are promises too. And **the contract is much larger than §3 read as promising**: §3 gestured at `Agent` plus `Event` plus the capability interfaces plus `Options` field names, about forty things, where the transitive closure is 156 — `Event` alone pulls in the whole SSE payload set and its string vocabularies, and each capability interface pulls in its argument and result structs. None of it had been written down as frozen.

  The 1.0 re-check of §2.1 lands with it: **keep the flat package, do not create `tui/render`**. The render extension points are not implementable from outside the package at all — `Dialog.HandleKey` and `Item.Render` take a `*Model` whose every field is unexported, the only `Overlay` in existence is an unexported field of `Model`, and `ToolRenderer`, the one interface with a `Model`-free signature, has no registration seam whatsoever: `toolRendererFor` switches over three package-private values and `Options` has no renderer field. So the subpackage is impossible, because the `*Model` parameter makes it an import cycle, and not worth wanting, because it would move thirteen unusable interfaces into a package whose name advertises them as usable. The defect §2.1 is blamed for is not topology; it is exported interfaces with no seam, which is fixable inside a flat package and unfixable by moving files. This supersedes `docs/api-audit.md` §6.2 group 3, which recommended keeping `ToolRenderer` exported in a non-`internal` `tui/render` and was reasoned from the closure/usage cross-tab without reading the signatures. It also narrows [#115](https://github.com/go-steer/core-tui/issues/115) by one symbol: absent a seam, `ToolRenderer` has no external implementer to protect, so it can go to an internal package with the rest of `toolrender.go` — which removes the one thing that would have forced #115 to create a public subpackage. Nothing here proposes doing #115 now. Separately, **N-DOC** holds for types and functions with a single miss, and read as intended — every exported symbol — there are fourteen, all listed. Notably, all 67 incidental symbols *have* doc comments: they were not exported carelessly and left undocumented, they were exported carefully and documented, which is precisely why nothing ever flagged them.

- **The status header resolves the working directory once, at construction** ([#223](https://github.com/go-steer/core-tui/issues/223)). `displayCwd` called `os.Getwd` and `os.UserHomeDir` every time it was asked, and it is asked from two places: `renderStatusLine`, on a cache miss, and `statusLineKey`, which is assembled on *every* pass whether the memo hits or not. `allocateChrome` measures the header before `View` draws it, so that is two lookups per layout pass, at whatever rate the spinner ticks — 10 Hz for the whole of a turn since [#162](https://github.com/go-steer/core-tui/issues/162). The cost is not really the point, and the entry would be dishonest if it pretended otherwise: `getcwd(2)` is cheap and it never showed up in the frame profile. The point is that it is **I/O on a path documented as doing none** — the same contract `hostSnapshot` exists to keep for the host — and it was the last syscall pair left on `View()`. It was measured anyway, because a claim without a measurement is a guess. Assembling a `statusKey` cost **498 B and 5 allocations**, and *all five were the working directory*: it is **0 B and 0 allocations** now, so a warm header is allocation-free end to end. Wall time, medians of six on the sandboxed Linux VM this was measured on: the key falls from **9.7µs to 5.1µs** and a warm `renderHeader` from **10.1µs to 5.9µs**, with the two lookups timed in isolation at **3.8µs** — which is `getcwd(2)` under a syscall-interposing sandbox rather than on bare metal, so the ratio is the transferable part and the microseconds are not.

  Resolved **at construction** rather than cached-and-invalidated, which is the option the issue recommends and the simpler of the two. `NewModel` fills `Model.cwd` from a new `resolveDisplayCwd`, and `displayCwd` is a field read. It has to be construction-time and not lazily filled on first use: `Model` is copied by value throughout this package and `View` has a value receiver, so a field filled during a draw is written to a copy that is discarded on return — the syscalls would run on every frame exactly as before and the answer would be thrown away every time, which is the same hazard the `statusCache` pointer exists to dodge. What this gives up is that a process which `chdir`s mid-session silently stops being tracked. No host does that today; if one turns up, the fallback is the issue's other option — refresh the field on a turn boundary, the way `hostSnapshot` is refreshed — and that is a one-field write and nothing else, *because* of the decision below. `HOME` is read once per `NewModel` rather than once per process: a package-level memo would be filled by whichever `Model` was built first and stay wrong for every later one, and the golden corpus depends on the opposite, since `pinCwd` installs a synthetic `HOME` per test so the captured frames do not carry the checkout path of whoever ran `-update`. The abbreviation itself is split out as a pure `abbreviateHome(dir, home)`, unchanged in behaviour — still a textual prefix match, which is what the corpus's symlink-resolved synthetic `HOME` is arranged to line up with — plus one guard that was implicit before and is now explicit: an unresolvable `HOME` is the empty string, and the empty string is a prefix of everything, so it must not turn every path into `~/…`.

  **`statusKey.cwd` is kept, not dropped**, and that is the deliberate half of the change. Read narrowly it is dead weight: the value can no longer move under the header, so keying on it can never produce a miss it would not have produced anyway. It stays because the property the whole memo rests on is that the key **is** every value the renderer reads — not that it is every value the renderer reads minus the ones someone has argued cannot move. Dropping it would trade a self-evident invariant for exactly the sort of global claim about who-may-write-what that the version-counter design was rejected for when the memo landed ([#201](https://github.com/go-steer/core-tui/issues/201)), and the invariant now costs nothing to hold: a string header copied from a plain field, no syscall, no allocation, and a compare that short-circuits on the pointer. It is also what keeps the `chdir` fallback above to one line. The concrete payoff is in the test. `TestStatusCache_StaysFresh` is differential — one step per key field, comparing the memoized header against the same `Model` rendered with the cache off — and it carried a written-down carve-out saying the cwd leg could not be covered here because a test has no business moving the process working directory. The carve-out is gone: three steps move `m.cwd` now, and dropping the field from the key fails the first of them by name. Two new tests cover the production change, one moving the process out from under an already-built `Model` and requiring the header not to follow, one tabling the abbreviation over a directory under `HOME`, `HOME` itself, a directory outside it, an unresolvable `HOME` and the filesystem root. Each was mutation-checked against the defect it describes. No golden churn — the corpus already pins `HOME` and the working directory before it constructs a model, so every captured frame is byte-identical.

- **The render memo's hit path no longer allocates to answer a lookup** ([#204](https://github.com/go-steer/core-tui/issues/204)). `listCache.getLines` took an `Item`, and reading `Identity()` and `Version()` through that interface is opaque to escape analysis, so every caller heap-allocated the `messageItem` it had just built — a value that embeds a whole `Message`, boxed once per visible row per frame, on the one path in the renderer whose entire purpose is to do no work. A memo that allocates in order to answer "no work needed" is charging for the thing it was built to avoid. `getLinesByID(id, version, width)` takes the two scalars a lookup actually consults and leaves the box to `put`, where a render is being paid for anyway and one allocation is noise. `BenchmarkRefreshViewport` drops from 114 to 71 allocs/op and 14,448 to 3,440 B/op, `BenchmarkChatViewWarm` from 102 to 88, `BenchmarkViewCompose` from 1,026 to 1,012 — identical in every one of five interleaved rounds, and flat across 10, 100 and 400 turns, so this narrows the constant rather than changing the shape the item-addressed transcript already established. A repaint saves three times what a single walk does, because it walks the window up to three times — reflow, tail pin, warm — and each walk was paying its own row of boxes. This is not the beginning of a de-interfacing of `Item`: `Item` is the seam that transcript's addressing is built on, `put` still takes it, and `getLines` survives as a one-line spelling over the new lookup so the two cannot drift. What went with the box is `chatRowCached`'s `i` and `total` parameters, which existed only to fill in an `Item` for a lookup that no longer wants one. Rendered output is unchanged byte for byte.

- **The input box and the status header are rebuilt when they change, not on every repaint** ([#200](https://github.com/go-steer/core-tui/issues/200), [#201](https://github.com/go-steer/core-tui/issues/201)). A settled frame — nothing about the session moved since the last one — rebuilt two pieces of chrome from scratch, and between them they were **887 of the frame's 1,022 allocations**. The input box was 826 of those: every draw called `textarea.View()`, which re-wraps the buffer, re-styles the prompt rail and re-lays the placeholder, and the placeholder path is the expensive one — so the frame was at its most expensive in the state a session spends most of its time in (826 allocations and 171µs empty, against 428 and 120µs with a line of text in it). The header was the other 61, assembled from state that moves about once a turn and built *twice* per layout pass, because `allocateChrome` measures its height before `View` draws it. A new `composer` wraps the textarea and renders once per mutation, so `View()` is a field read; a `statusCache` memoizes the header on a key that **is** its inputs, 12 fields costing 5 allocations to collect against 61 to render. `BenchmarkViewCompose` goes from 1,022 allocs/op to **147** and from ~1.10ms to **~0.79ms**, flat across 10, 100 and 400 turns, and `staticRepaintAllocCeiling` drops from 1,500 to 250 with it — left at 1,500 the ceiling would sit an order of magnitude above what it measures and the composer's whole rebuild could come back unnoticed. Two design choices are load-bearing and are written down where they are made. The composer renders **eagerly**, at mutation time, because `Model.View` has a value receiver: a cache filled at draw time has to live behind a pointer to survive the copy, and a pointer holding a rendered block is only safe if two divergent `Model` copies can never collide on one key. And the header's key is the **values** rather than a version stamp: a stamp has to be bumped by every site that can move one of its inputs, which is most of the package, and a missed bump shows up as a header that has quietly stopped describing the session. Both caches are covered differentially — the cached artefact compared against the same state rendered with the cache off, one step per input — because the failure mode is staleness, not a wrong string. The CPU percentages the two issues were filed with did not survive re-profiling on current `main` and the corrections are recorded on them; the allocation claim is what held, and it is the one that mattered, since [#160](https://github.com/go-steer/core-tui/issues/160) established allocations rather than CPU as the source of the latency tail.

### Fixed

- **A request the TUI cannot draw is no longer reported as the operator's refusal** ([#209](https://github.com/go-steer/core-tui/issues/209), and the last of its three parts). Once the form gained a reachable `ctrl+d` — the entry two below this one — `ElicitActionDecline` had exactly one producer left in the package, and it was not a person: `supportedElicit` returning false, the screen that catches a schema the modal has no way to render. A host forwards the action to whoever asked, so an MCP server was told **the user declined** in precisely the case where no user was ever consulted. That is the category error the whole issue is about, one layer below where it was first noticed, and it is not a rounding difference to the server on the other end: a decline is a decision it may cache, count against a retry budget, or surface to somebody as a refusal that a named operator never made. The refusal now travels as an error — `ErrElicitUnsupported`, exported and matched with `errors.Is`, wrapping the same one-clause reason the operator sees in the transcript — paired with `ElicitActionCancel`. Three options were on the table and the reasoning is worth recording, because the obvious one is not the choice. A fourth `ElicitAction` reads best in Go and dies at the host boundary: MCP's vocabulary is three actions wide, so every host would have to collapse it back onto one of them, and the distinction would survive only as far as the first adapter — buying an exported constant and a `default:` arm in exchange for the same ambiguity one hop later. Leaving it alone was defensible, since the operator is no longer in the dark after the fix below, but it keeps a wrong statement on the wire. An error is what Go already has for "this could not be carried out", `Elicit` has returned one since it was written, and it was **already** paired with `ElicitActionCancel` for the ctx-cancelled path — the same shape, for the same reason, so this adds a case to a precedent rather than a mechanism. The `elicitResponse.err` field it travels in has existed, unset by anything, since the type was declared. **Host action:** check `err` before mapping `ElicitResult.Action` onto a wire value. A host that ignores it sees `Cancel` where it used to see `Decline`, which is the less wrong of the three — "dismissed without deciding" is nearer to "nobody was asked" than "the user said no" is — so the failure mode of not reading this note is a slightly imprecise answer rather than a false one. The operator's transcript row is corrected to match: it read "declined automatically", which told the one person who could not check that a decline had gone out over their name, and now reads "refused without asking you". Both accounts of a refusal — the operator's row and the host's error — are built from a single `elicitUnsupportedReason`, so they cannot drift into describing different failures, and a test asserts it. R-ELIC-3 is amended to specify the new answer rather than being quietly contradicted by it, and R-ELIC-2 and R-ELIC-4 are corrected alongside: the first still said Esc declines when it cancels, and the second omitted `ctrl+d` from the keys that observe the [#95](https://github.com/go-steer/core-tui/issues/95) grace window, which the code has honoured since the decline shipped.

- **Dialog footers no longer break between a key and its action** ([#230](https://github.com/go-steer/core-tui/issues/230)). `wordWrap` breaks on spaces, and the space inside `enter accept` was as good a break point as the ones around the `·` separator — so on a 40-column terminal the model picker's footer put `enter` at the end of one row and `accept` at the start of the next, which reads as a binding with no key on it. The footer is the only place a dialog says how to leave itself, so the row that had to be unambiguous was the one that was not, and it is not a narrow-terminal curiosity: the same wrap happens at any width where the legend is one word too long for the box, and the longest legends belong to the pickers, which are the dialogs an operator reaches for most. `keyLegend` already solved this for the permission renderers and the elicit modal — it binds each key to its action with a non-breaking space (U+00A0) and leaves the `" · "` separators ordinary, so a legend still wraps, between pairs, where a break carries no meaning — and the model, session and theme pickers, the text-input dialog's default footer, the subagent drill-down and the tool-call overlay are built with it now. Two things the issue left open are settled in the code rather than left to drift. The subagent and tool-call footers joined with two spaces either side of the separator where the other four used one; nothing recorded a reason for the wider gap, so they are unified on `keyLegend`'s single space. And a host-supplied `TextInputConfig.Footer` is still rendered verbatim — the helper cannot tell which of an arbitrary string's spaces hold a pair together and which merely separate two — which the field's godoc now says, along with what a host does to get the same protection for its own legend. The tests assert the binding against the composed frame and spell the U+00A0 themselves rather than borrowing it from `keyLegend`, which would have moved both sides of the assertion at once, and a companion check requires each footer row to start on a key, so neither binding every space (which slices the legend mid-word instead) nor dropping the tail could pass as a fix. Golden churn is confined to the six modal-frame entries that carry that footer, and at 60 columns it is the fix itself on the frame: `esc cancel` moves to the next row as a unit instead of splitting across the break.

- **A request the TUI cannot draw is refused out loud** ([#209](https://github.com/go-steer/core-tui/issues/209)). R-ELIC-3 asks for two things when an MCP server sends a schema the modal has no way to render — decline it automatically, and say so with a "schema unsupported" system message — and only the first was built. The screen ran inside `Elicit`, on the calling server's goroutine, which is the one place in the design that cannot reach the transcript: the reply went back and nothing was written anywhere the operator could see it. From where they sit, a server asking for something undrawable and a server never asking at all looked identical, and that is the worse of the two to be wrong about — the tool call fails, the agent reports a refusal the operator never made, and there is nothing on screen to explain either. The screen moves onto the Bubble Tea loop, into the `elicitRequestMsg` handler, where the decline and the row recording it are the same few lines; the modal still never opens. The notice names the server and which arm of the screen rejected the request — no fields, no URL, or a mode this TUI does not render — and those strings are derived from `supportedElicit`'s own arms rather than from anything the server sent, so the message cannot come to describe a failure the code does not test for. Two Cmds come back from the branch and both are pinned, because a batch is easy to get half right: the re-armed listener, without which a second undrawable request is never drained and that server blocks until its context expires, and the render kick ([#24](https://github.com/go-steer/core-tui/issues/24)), without which the row explaining the refusal waits for the operator's next keystroke — a background-delivered request being exactly the case where there is no next keystroke coming. One behavioural consequence is deliberate and worth stating: an unsupported request is now serialized behind whatever modal is already open, rather than answered instantly off to the side, which is what puts it in the transcript in the order it actually arrived.

- **The elicit form can decline, which it had been advertising all along** ([#209](https://github.com/go-steer/core-tui/issues/209)). `ElicitAction`'s godoc named `n` as form mode's decline key and there was no such case in the form handler: `n` is a printable character and types into the focused field, which is the only sane thing for it to do while a text field has the keyboard. So the form could submit, and it could cancel, and the one answer it advertised it could not give. That is not a cosmetic gap — decline and cancel are different answers and the server that asked may act on the difference. Decline is "I read this and I am saying no"; cancel is "I dismissed it without deciding". An operator who wanted the first had only the second, so a server was told the request had been dismissed when it had been refused. Form mode declines on **ctrl+d** now — a control stroke rather than a letter, because in a form every printable key belongs to whichever field has the keyboard — and both the modal's own footer and the status footer hint list it. The decline commits a result, so it is held for `modalInputGrace` like every other key that answers the host ([#95](https://github.com/go-steer/core-tui/issues/95)), and it carries no field values: half-typed input is not something the operator agreed to. It does not run Enter's required-field validation either, because a decline is a complete answer whatever the fields hold. URL mode's action row, which had never had a key test of its own, is pinned alongside it.

  What this does **not** change is the wire value the *unrenderable* case reports; that is the third #209 entry, at the top of this section, and it lands in the same release.

- **The listener goroutines end when the program does** ([#202](https://github.com/go-steer/core-tui/issues/202)). Five `Cmd`s park on a channel waiting for the next thing to happen — a permission request, an elicit request, a notice, a wake signal, an agent event — and none of them had a way out. Three blocked on `context.Background()`; one blocked on a `Notifier` channel that only `Run` closes, and only *after* `tea.Program.Run` has already returned; one blocked on an `eventCh` that nothing closes at all. Bubble Tea does not reap outstanding `Cmd` goroutines, by explicit design — `handleCommands` starts each one detached and comments that waiting would make shutdown latency unacceptable — so every one of those goroutines survived the program that started it, pinning the `Model` it had captured. In a `main` that exits immediately afterwards that is invisible. In a host that embeds the TUI in a longer-lived process, or runs it twice, it is five leaked goroutines per run and a growing set of `Model`s that can never be collected. Each listener now also selects on a lifetime context created in `NewModel`, cancelled on every `Update` path that quits and again by `Run` once the program has returned. Nothing about the exported surface changes: bubbletea v2 hands the model nothing at shutdown — its event loop intercepts `QuitMsg` in an internal switch and returns before `model.Update` is called, and context cancellation exits the loop without synthesising a message at all — so the two cancellation points above are the entire observable surface, and a lifecycle field on `Options` would have bought no coverage that they do not already have. Covered by a headless-program scenario ([#81](https://github.com/go-steer/core-tui/issues/81)) that names the parked goroutines in its failure message rather than reporting a count.

- **Every modal surface wears a box edge** ([#199](https://github.com/go-steer/core-tui/issues/199)). Since [#156](https://github.com/go-steer/core-tui/issues/156) a dialog is spliced *over* the frame rather than drawn onto a blanked one, which is the right behaviour and left the block with nothing to say where it stopped: the left and right edges of a modal were implied by wherever its content happened to end, so a short body row, or host content already occupying the columns beside it, left the operator guessing at the boundary. Every surface — the permission overlay, the elicitation, the embedded `huh` form, the side answer and everything on the `Dialog` stack — now composes through one `modalSurface` call that draws a rounded border coloured from `Theme.BorderActive`, the same token the title and footer rules already read. Drawn rather than dimmed, which was the alternative the issue put up: a box character renders on every terminal we can be asked to run on, where a dimmed backdrop needs an SGR-aware pass that has to survive host content already carrying its own colour and degrades to nothing where the terminal has no dim — and an edge is a layout change, which the frame invariants can police exactly, where a colour change is invisible to them. A dimmed backdrop stays available as an addition on top of the edge; it was never a substitute for one. The one place the edge is suppressed is a terminal so short that drawing it would push the footer key hint under `clipFrame`, because a decoration that buys its own visibility with the row saying which key closes the modal is not a decoration worth having. A fullscreen modal keeps it: fullscreen is full *height*, the block is still narrower than the terminal, and suppressing the edge exactly where the modal is hardest to distinguish — while making it flicker on a one-row resize — is the opposite of the fix.

  The edge is charged to the modal's own budget rather than added around it, so the centring, the margin and the clip pass are untouched and the two columns and two rows come out of the content. `modalChromeRows` moves 5 → 7 as a result, and `modalFullscreenBelow` 13 → 15 with it — the box is two real rows, and a height regime that does not know that is [#142](https://github.com/go-steer/core-tui/issues/142)'s defect with a new cause. Every width computation that fits content to a modal now derives from `modalInnerWidth` / `modalBodyWidth` rather than repeating a subtraction by hand, which is the shape [#157](https://github.com/go-steer/core-tui/issues/157), [#159](https://github.com/go-steer/core-tui/issues/159) and [#210](https://github.com/go-steer/core-tui/issues/210) all had; the caret paths do the same through `modalContentX` / `modalBodyTop`, since the golden corpus captures `tea.View.Content` and not `tea.View.Cursor` and would not notice the cursor drifting off the character being typed. Visible cost: two fewer columns of body and two fewer rows of list. On a 24-row terminal the theme picker — whose twelve descriptions are exactly the window the regime lends it, so they wrap rather than being cut — gives up its two blank spacer rows to pay for the edge, which is `fitModalContent` shedding in its documented order rather than a modal that no longer fits.

- **Dialogs float over the frame instead of blanking it** ([#156](https://github.com/go-steer/core-tui/issues/156)). `View` finished every modal frame with `lipgloss.Place(m.width, m.height, Center, Center, modalFrame)`, five times over — permission overlay, elicitation, the `huh` form, the side answer, the dialog stack. That reads like an overlay and is not one: `Place` does not layer. It ignores whatever was composed before it and returns a fresh block of the requested size with the modal centred in blank space, so opening any dialog wiped the transcript, the header, the input box and the footer, and dismissing it read as a mode switch rather than as a sheet lifting off. The permission prompt is the worst case, and it is not a cosmetic one: the tool call the operator is being asked to authorise is exactly the thing that disappeared when they were asked.

  The five calls are now one `compositeModal`, and it is a **splice, not a canvas**. Rows the modal does not cover are passed through by reference; only the covered rows are cut into left, block and right pieces. Measured against a full cell-buffer compositor on a 100×40 frame the splice was both cheaper and smaller — about 0.9ms and 75KB against 1.1ms and 522KB — and a cell buffer would have to re-derive SGR runs for every cell it copied. Everything works in terminal **cells**, never bytes and never runes: the background is squared to the frame first, because a modal cannot be spliced into a ragged row, and each covered row is then cut and re-fitted. `spliceRow` measures three times rather than twice because the two cut functions round a straddling double-width rune **opposite ways** — `ansi.Truncate` drops it and `ansi.TruncateLeft` keeps it — so the right-hand piece comes back either a cell short or a cell early and each case needs its own correction; without them a row of CJK shears by a column under the modal, which is the same class of bug as [#157](https://github.com/go-steer/core-tui/issues/157). The right piece also has to resume whatever colour the background was wearing at the cut, which `TruncateLeft` already does by re-emitting the SGR it passed over, and the left piece has to close its own so it cannot bleed into the modal's first cell.

  Centring goes through the same `placeCenterOffset` that `modalCursor` uses to offset the caret. The draw origin and the caret origin have to agree exactly and nothing else would catch them drifting apart — the golden corpus captures `tea.View.Content`, not `tea.View.Cursor` — so a test pins the two together over even gaps, odd gaps, an exact fit and an oversized block. One invariant had to change, and its complement is the property this is really about. The panel-survival assertion ([#158](https://github.com/go-steer/core-tui/issues/158)) required the modal's rectangle to run to the frame's right edge, which only ever held because `Place` blanked everything around it, and it now stops at the block's own edge; in its place, `assertBackgroundSurvives` walks every panel in the composed stack and requires that every row the modal does **not** cover is still exactly what the panel rendered. Reverting the compositor to draw on a blank canvas fails it on the status header, the transcript, the input box and the footer at once, across the whole grid. Six modal goldens churn; the other twenty-one are byte-identical. One thing this exposes rather than fixes: dialogs are styled as a title rule, content and a footer rule with no side or corner borders, which read fine against a blank canvas and leaves the band's left and right edges merely implied now that there is something behind them. A visible edge, or a dimmed backdrop behind the block, is a styling decision across every dialog rather than a compositing one, and belongs in its own change.

- **The spinner's glyph animates** ([#162](https://github.com/go-steer/core-tui/issues/162)). One counter indexed both the Braille glyph and the cognition verb, and it advanced once per `spinnerCadence` — three seconds. The ten-frame Braille cycle therefore ran at **0.33 Hz**: the glyph sat still for three seconds, jumped, and sat still again, which reads as a stuck character rather than as motion, i.e. as the opposite of what a progress indicator is for. The two rates are separate now. The tick fires every `spinnerFrameCadence` (100ms) and drives the glyph directly; the verb is selected by dividing the frame counter by `spinnerFramesPerVerb`, which is derived from the two cadences rather than written down, so the phrase period is still exactly 3s and the two cannot drift. `thinkingIdx` is renamed `spinnerFrame` to say what it counts. **10 fps rather than 20**, because a spinner tick rebuilds the chat tail and repaints, so the real cost tracks the frame rather than the tick — 10 fps is already past the point where a Braille cycle reads as continuous motion, and it halves a cost that is paid for as long as the model is thinking; the 1ms coalescing window is well under the tick, so nothing swallows a frame. `spinnerCadence` deliberately keeps its name and its value: `turnElapsedFloor` is defined as `spinnerCadence`, and pinning the elapsed readout ([#111](https://github.com/go-steer/core-tui/issues/111)) to the verb period is the right behaviour — it should appear with the first phrase change rather than thirty frames earlier. The side benefit is that the readout now refreshes ten times a second instead of once per three, so it is current rather than up to a cadence stale. Every other spinner test looks at one frame at a time, which is exactly why none of them could see this; the new ones walk a full Braille cycle and fail if two consecutive frames draw the same glyph, require the phrase to hold for `spinnerFramesPerVerb` frames and change on the next, and guard the integer division in the derivation. No golden churn — the fixtures leave the counter at zero, where the old and new indexing agree.

- **A modal body's rows are padded by measuring, not by word-wrapping** ([#157](https://github.com/go-steer/core-tui/issues/157)). `scrollView` squared every visible row off with `lipgloss.NewStyle().Width(contentWidth).Render(row)` before gluing on the scrollbar column. A lipgloss `Style` carrying a width is a **word-wrapper**, not a padder: handed a row the caller already knows is one line, it re-measures it, hunts for break points, allocates on the way — and on an overlong row it returns **more rows than it was given**. That last part is not a performance footnote. The extra rows push the scrollbar cell onto the wrong line and blow the height budget the modal was assembled against, which is how a scrolled theme picker came to render eight body rows as twelve, lose both its margins and start on terminal row 0. It measures, truncates and pads now. Truncation rather than wrapping is the whole point: it is the only bound that leaves the row count alone, and the row count is what the caller budgeted against. Over a picker body — forty styled rows at width 100, one in three overflowing — that is **4.5x the speed, 8.6x the bytes and 32x the allocations**, on every frame a modal is open. The issue quotes 11.7x and 52x; both are right, and the difference is the fixture rather than the machine, since its cheap arm squares off already-short rows and never truncates, and `ansi.Truncate` costs more than padding does. The 4.5x is what this package banks; the 13x is the ceiling. Both benchmarks are committed as a matched pair so the wrapper cannot creep back in unnoticed.

  `ansi.Truncate` forwards the escape sequences it finds and never synthesises a terminator, so a row that arrived with its colour still switched on would bleed its foreground and background through the gutter space and into the scrollbar glyph. The new `fitRow` closes an open style before appending the gutter, and two things about that are worth being precise about. `Style.Render` was **not** papering over it — fed a row that never resets, lipgloss pads it with bare spaces and leaks in exactly the same way, so this is a fix and not a restoration. And the check is conditional rather than an unconditional reset: it is a byte scan for the last SGR sequence, so a row that already reset itself is handed back byte for byte, where an unconditional reset would be extra bytes on every row of every frame and churn across the corpus for output that is already correct. Instrumented over the full suite, 1,173 rows went through it and the eleven that tripped the check were all synthetic fixtures from the two new tests; nothing in production leaks today, because every row reaching `scrollView` is either lipgloss-rendered and self-terminating or host content that `sanitizeContent` has already stripped. The guard is defence for the day a row builder stops stripping.

  The corpus proved nothing about any of this, which is the other finding. `TestGolden_ModalFrame` opens the theme picker at 24 rows, where twelve themes fit inside a fourteen-row body — so `scrollView` returns early and **no golden had ever contained a scrollbar column**, confirmed by mutation, since padding with interpuncts left the entire corpus green. Three new `modal_frame_scrolled_*` goldens close that gap at eighteen rows, the tallest terminal that still windows the body while staying above `modalFullscreenBelow`, so they capture the scrolled modal in the normal regime rather than the degraded one, and the test asserts a thumb glyph is present before capturing so it cannot silently stop covering the path. The audit that came with this swept every width-setting style in `tui/` and `examples/`; it found one further genuine misuse, on the per-frame transcript path, and left it for [#160](https://github.com/go-steer/core-tui/issues/160).

- **A slow paint can no longer fail the assertion that `View()` never calls the host** ([#190](https://github.com/go-steer/core-tui/pull/190)). `TestView_NeverCallsHost` checks two things: an exact host-call counter, and a wall-clock budget on the paint of `slowHostDelay / 10`, or 50ms. A loaded macOS runner took **51.6ms** to paint a populated model picker over the sidebar layout under `-race`, and the test went red on a pull request that changed no production code — while the counter on the very next line read zero. That 51.6ms was not a host call; it was glamour and lipgloss. There is no useful signal in the gap between a slow paint and half a wedged host: the counter is the discriminator and it is exact, and the clock's only remaining job is to catch a blocking call that somehow does not go through a counted capability, so it belongs where a slow machine cannot reach it. The budget is `slowHostDelay / 2` now, which leaves an inline 500ms call no way to squeeze under and leaves the paint five times clear of the ceiling.

- **The hardware cursor stays on the composer when a palette row is wider than its column** ([#203](https://github.com/go-steer/core-tui/issues/203)). In the sidebar layout `View` records where the input box will land — `origin = inputOrigin{x: 0, y: stackedHeight(leftParts)}` — from the parts, before they are joined, because which parts get emitted is a run-time decision. It then composed the column with `lipgloss.NewStyle().Width(chatWidth).Render(JoinVertical(...))`, and a width-setting lipgloss `Style` is a **word-wrapper, not a padder** — the third instance of the same substitution, after [#157](https://github.com/go-steer/core-tui/issues/157) and [#160](https://github.com/go-steer/core-tui/issues/160). Any row wider than the column comes back as two, every part below it shifts down, and the origin recorded a moment earlier is wrong by a number of rows that depends on the content.

  The issue filed this as latent coupling on the grounds that nothing is known to overflow `chatWidth`, and that is **not the case**: `renderPaletteRow` composes `marker + display + pad + description`, clamps the pad at one space and never truncates, so a host whose `SlashCommandSpec` carries a descriptive enough `Description` — or an `@`-palette entry with a long path — hands the column a row wider than it is. Measured at 100×40 with a 65-column chat: zero overlong rows puts the caret on the composer, one puts it on the input box's **top rule**, three put it **inside the palette**, two rows up. It is reachable today and it drifts rather than being off by a constant, so the test that comes with it is a live witness rather than a hypothetical.

  `stackColumn` replaces the `Style`: join, then bring each row to exactly the width by measuring, padding and truncating. The row that overflows is still a defect wherever it came from; what this guarantees is only that it stays **one row**, so the geometry around it survives. It lives beside `stackedHeight` because the two are a contract — one predicts where a part lands, the other composes the column, and the prediction is only true if the composition cannot move a row. The header layout was checked and is unaffected: its stack joins with no width-setting `Style`, so an over-wide row is left for `clipFrame` and the row count never moves; that arm is in the test as a control. One deliberate divergence from the `Style` it replaces — `fitRow` closes styling a row left open, and since `JoinHorizontal` glues the sidebar divider onto the right of every row here, a row ending with its colour still switched on used to bleed across the divider. The equivalence test exempts that one input **by name** rather than pretending the two agree, and a separate test pins the closing. No golden churn: no row in the corpus overflows its column or leaves styling open, which is exactly why this went unnoticed.

- **A tab-bearing line wraps where it is drawn rather than four cells per tab later** ([#217](https://github.com/go-steer/core-tui/issues/217)). `wordWrap` composes `ansi.Wordwrap` and `ansi.Wrap`; both bound a line against `ansi.StringWidth`, which prices a **TAB at zero cells**, and lipgloss's `Render` then expands each one to `contentTabWidth` spaces on the way out. So the wrapper fitted a line to the budget and something four cells wider per tab was drawn — a bound taken against a string that was about to change. Through `renderMessage` for a user turn at chat column 40, `strings.Repeat("a\t", 20)` drew at **93 cells** and `strings.Repeat("word\tword ", 8)` at **45**. [#216](https://github.com/go-steer/core-tui/issues/216) fixed the *pad* arithmetic the same way, with `renderedWidth`, and deliberately left the wrap; this is the other half.

  Tabs are now expanded **before** the measurement, in `wordWrap` and in `wordWrapIndent`, through a shared `expandTabs`. This is not a second expansion at a different width, which is what the note on `contentTabWidth` warns against — lipgloss's `maybeConvertTabs` is a `strings.ReplaceAll` at `tabWidthDefault`, fixed-width and *not* tab-stop aligned, and nothing in this package sets `Style.TabWidth`, so it is the same substitution at the same width moved earlier, and it leaves lipgloss's own pass with nothing to find. A test pins that against lipgloss rather than against four literal spaces, so it fails if lipgloss ever retunes the width or starts aligning to tab stops, either of which would make expanding early wrong. `wordWrapIndent` expands up front rather than leaving it to the `wordWrap` it calls, because it does width arithmetic of its own first: it pulls the leading whitespace off each source line and subtracts its **byte** length from the budget, so a tab-indented line charged the hanging indent one cell for something drawn as four. `renderedWidth` stays — it prices instead of expanding because its callers hand the same string to `Render` on the next line, and it is the measure that holds whether or not the caller wrapped first.

  The issue's preferred option was to expand in the sanitize funnel instead, and that turns out not to reach the defect: `sanitizeContent` / `sanitizeLine` are called only from the tool-preview, tool-detail and diff renderers, while every `wordWrap` / `wordWrapIndent` call site is fed a `Message.Display()`, a `ToolArgs`, a `PermissionRequest.Detail`, a `TurnError.Message` or a sub-agent report — none of which passes through either funnel. Expanding there would have left the measured user turn exactly as it was. The wrap boundary is where the measurement is taken, so that is where the expansion has to land. `helpWrap` was checked and left alone: its descriptions are compiled-in literals with no tab in them and no host input reaches it.

  **The frame-invariant grid structurally cannot witness this, which is why a suite with a width invariant did not catch it.** `chatView` cuts every drawn line with `chatCutLine` before returning, and by then lipgloss has already turned the tabs into spaces, so the cut is correct and the frame is the right width — the overrun is spent as content pushed off the right of the line rather than as a frame that overflows. That is also why the symptom reads as data loss instead of as a layout bug. The new tests therefore measure the **drawn** width, `lipgloss.Width(Style.Render(line))`, rather than `ansi.StringWidth`: a test written with the latter prices the tab at zero, agrees with the defect and passes on the broken code. They cover `wordWrap`, `wordWrapIndent`, every `renderMessage` role and the permission block in both of its detail kinds, over seven tab shapes that actually occur — a pasted table, tab-separated tool output, unfenced indented code. No golden churn, in either direction: the corpus already contained tab-indented fixtures and their bytes are unchanged, which is the same fact the equivalence test states.

- **Long unbreakable tokens stay in the chat column, and a tab in a user turn no longer overruns the card** ([#210](https://github.com/go-steer/core-tui/issues/210)). `wordWrap` was `ansi.Wordwrap` alone, which returns a token containing no space or hyphen at its natural width — a path, a URL, a base64 blob or a run of CJK came back unbounded, so the helper whose whole job is to bound a line did not bind for exactly the inputs that needed it. A hard-breaking second pass now bounds every line and leaves fitting prose untouched. Separately, the user card measured each line with `lipgloss.Width`, which prices a TAB at zero, then padded and handed the result to `Render`, which expands each tab to four spaces — putting the card four cells past the column per tab. A new internal `renderedWidth` prices the expansion the way `Render` performs it. The wrap half of the tab problem was deliberately left for [#217](https://github.com/go-steer/core-tui/issues/217), above, which is where it is fixed.

- **A theme whose prompt glyph is a different width no longer leaves the composer wrapping to the old column** ([#200](https://github.com/go-steer/core-tui/issues/200)). `bubbles` documents that changing a textarea's `Prompt` does not reach its wrap arithmetic until `SetWidth` runs again, and neither call site — both in `refreshTheme` — did it, so switching to a theme with a wider or narrower prompt rail left the buffer wrapping to the content column of the theme it replaced until the next resize happened to correct it. The width is re-applied inside the setter now, which is half the reason the setter exists. Found while memoizing the composer, above, along with the other half of the same seam: a bare `Model{}` literal — which a number of dialog tests build — holds an unconstructed textarea that `bubbles` panics on both rendering and resizing, and moving the render to mutation time turns every mutator into a potential draw, so the composer gates itself on being ready.

### Docs

- **`docs/design.md` §3.3 declares the capability surface that exists, and a test keeps it that way** ([#212](https://github.com/go-steer/core-tui/issues/212)). The section a host implementer reads to learn the capability contract described **14** of the **20** optional capabilities, gave `PermissionController` a `Snapshot() PermissionSnapshot` whose return type has never existed and an `AlwaysAllow` that is an `Options` callback rather than a gate method, dropped `Provider` from `Status`, declared `SlashResult` without the `SwitchTo` field its own prose four declarations earlier told hosts to use, and presented `MentionProvider` as shipped configuration when neither it nor `Options.MentionProviders` is in `package tui` at all. Detection is by type assertion, which is what makes a stale contract document worse than none: an adapter written against a method set that no longer matches does not fail to compile and does not error at runtime — the TUI concludes the host declined the capability, and the feature is simply missing. The reference host has already lost two features that way. All twenty capabilities are declared now, with the three that are not asserted on the `Agent` called out as such and the `SlashProvider` commentary corrected on five points where it described machinery that does not exist. It drifted because nothing checked it, so `tui/design_doc_test.go` parses the Go blocks in §3.3 and §3.5, parses `package tui`, and fails on any method set or field set that disagrees — plus a roster check against the capability list `api-surface.md` derives from the source, which is the one the six absentees would have failed. Declarations the prose marks **SPECIFIED, NOT SHIPPED** are asserted to be genuinely absent, so building one fails the test until the note comes off.

### Removed

- **Twenty optional capability interfaces are sixteen** ([#77](https://github.com/go-steer/core-tui/issues/77)). The capability set is the part of the surface a 1.0 makes permanent, and it had been growing one interface per feature with nothing ever checking whether the last one earned its place. The audit in [`docs/api-audit.md`](./docs/api-audit.md) §5 counted implementations rather than opinions and found three interfaces that **nothing anywhere implements** — not the reference host, not either adapter in `examples/core-agent`, not `tui/testagent` — and one pair that no implementation has ever satisfied separately. `ContentRunner` (with `Content` and `ContentPart`, and `R-CHAT-12` withdrawn alongside them) declared a structured-prompt entry path that `package tui` never once asserted, which made it an interface the library published so that two hosts could call each other through it; the submit path is and remains `Agent.Run(ctx, prompt)`. `SessionByModelTracker` and its `ModelTotals` row backed the per-model `/stats` breakdown and have had zero implementations since they shipped in v0.6.4 — the breakdown itself is untouched, because it has been reading the push-mode usage stream ([#38](https://github.com/go-steer/core-tui/issues/38)) in every configuration all along and the capability branch was dead code beside it. And the bare `AsyncSlashProvider` lost its name to `AsyncSlashProviderWithPreamble`: the two shared the method name `InvokeSlashAsync` and differed only in return type, so no single Go type could ever satisfy both, and the preamble form was a documented strict superset whose empty-string case behaves identically to the bare one. Three slash interfaces become two with no capability lost.

  `SubagentLister` + `SubagentEventReader` merge into **`SubagentReporter`**, which is the one merge rather than a deletion because both halves are live. The usual argument for splitting — a host that can do one and not the other says so by declining the interface — does not survive being looked at here: the roster's only affordance is drilling into a row, so a host that listed its subagents without being able to say what they did shipped a list pointing at nothing, and the code carried a `drillable` flag through five files to render exactly that degraded state. Nothing ever produced it. The flag and its plumbing are gone with the merge. The rule that came out of the exercise is written into `docs/design.md` §3.3: a capability earns a place by being something a host can plausibly do **without** doing the one next to it. §10's old mitigation for capability sprawl — promote the popular ones into the base `Agent` interface — is rewritten to say the opposite, since promotion trades a cost every host pays voluntarily for one every host pays whether it wants the feature or not, and on a sample of one host it would be making n=1 permanent.

  **Host action**, and it is small: rename `SubagentLister` / `SubagentEventReader` to `SubagentReporter` in `var _` assertions (no method signature changed — a type satisfying both still satisfies the merged interface), and an adapter that implements the bare `InvokeSlashAsync` returns `(preamble string, results <-chan SlashResultOrErr)` instead of the channel alone, with `""` reproducing the old behaviour exactly. Both flavours in `examples/core-agent` are migrated in this change, and the local one gains the drill-down it had been declining, so the example host now answers `/subagents <name>` in process. Everything removed is recorded in `dev/api-breaks.txt` with its reasoning, and `docs/api-surface.md`, `docs/requirements.md`, `docs/design.md` and `MIGRATION.md` are updated in step — `tui/design_doc_test.go` fails the build otherwise, which is how the doc drift this change would have caused got caught at all.

- **Twenty-seven incidental symbols are unexported** ([#78](https://github.com/go-steer/core-tui/issues/78)). These are the part of [`docs/api-surface.md`](./docs/api-surface.md) §3.3's incidental bucket that could be unexported without waiting on other in-flight work. The bucket is defined by four tests, and a symbol had to fail all four to be in it: not named by `docs/design.md` §3, not reachable from a §3 root, not referenced by `examples/` or the reference host, and not appearing in any doc example. Every rename is therefore confined to `package tui`. The largest group is the **thirteen named theme constructors** (`AnthropicTheme` … `GopherTheme`, `ThemeForProvider`), each of which is already reachable by name through `BuiltinThemes()` / `ThemeByName()` — so what goes is thirteen redundant spellings, not a capability. Then the **five `Brand*` seed colors**, superseded by `Theme.Primary` / `.Secondary` / `.Accent` and by `Options.Branding`; three of the five turned out to have no caller at all once the export stopped hiding them from the `unused` linter, and are deleted rather than unexported. Then **four of the seventeen `Glyph*` constants** — the four with no call site in a file other work currently holds, with the remaining thirteen left exported for now. Then `DefaultChromaStyleName` / `DefaultPromptGlyph`, read only by the theme constructors beside them. Then **`DetectCapabilities` / `TerminalCapabilities`**: no `Options` field accepts a capability set, so a host cannot override detection, which is the only thing exporting the probe would have been for. And **`LipglossFormatter`**, whose exported signature returned a `chroma.Formatter` and so leaked `github.com/alecthomas/chroma/v2` into this library's API and pinned its major version for every host that never called it. The reason to do this now rather than after 1.0 is arithmetic: `package tui` exports 265 top-level symbols, the freeze turns all of them into promises by default, and unexporting one afterwards costs a major version. **Host action:** none is expected, by construction — the bucket's four tests are what "no host could be using this" looks like when it is checked rather than assumed. A host that reached past them anyway substitutes `ThemeByName("gopher")` for `GopherTheme()`, `Options.Branding` for a `Brand*` constant, and has no substitute for `DetectCapabilities`, which never had a seam to install its result through. This entry is written retroactively: the change landed in [#195](https://github.com/go-steer/core-tui/pull/195) without a CHANGELOG hunk, which is the gap the stability promise at the top of this file exists to prevent, and it was caught cutting the release.

- **`Focusable`, an interface with nothing behind it** ([#213](https://github.com/go-steer/core-tui/issues/213)). `tui.Focusable` (`SetFocused(bool)`) had no implementor and no consumer anywhere in the tree — no type in `tui/`, `examples/` or `tui/testagent` satisfied it, and nothing type-asserted to it, so the bit it described was never set and never read. Its doc comment named a real design — "the selected row sets it before render", items styling themselves off the flag "without inline `if focused` branches in every `Render` method" — and that design shipped, without the interface. Keyboard focus is a region enum in `tui/focus.go` ([#151](https://github.com/go-steer/core-tui/issues/151)), which is explicit about being two states rather than a focus ring, and the selected row is marked by a gutter the *list* draws in `chatGutterPrefixes` ([#152](https://github.com/go-steer/core-tui/issues/152)) — outside `Item.Render` entirely, which is also what keeps it compatible with the render cache: a `SetFocused` call is a mutation the cache cannot see, since `Version()` is what invalidates an entry and a focus bit is not part of it, so a focused row would have been served its unfocused render out of a frozen entry. **No host action.** A host type that happens to have a `SetFocused(bool)` method still compiles; only the name `tui.Focusable` is gone, and nothing could have been done with it.

- **`ToolRenderer` is unexported until it has a seam** ([#213](https://github.com/go-steer/core-tui/issues/213)). It is the one render interface with a `Model`-free signature — `RenderCall(msg Message, head string, width int, styles Styles) string` — which makes it the one a host could plausibly implement, and there was nowhere to hand the result in: `toolRendererFor` dispatches over three package-private values and `Options` has no renderer field. An exported extension point with no installation seam is a promise the library cannot keep, and the asymmetry is what makes this pre-freeze work rather than someday work — adding the seam later is a compatible change, deleting the interface later costs a major version. So the interface becomes `toolRenderer`, and an `Options.ToolRenderers map[string]ToolRenderer` consulted ahead of the built-in switch can re-export it the day a host asks for one. This is what [`docs/api-surface.md`](./docs/api-surface.md) §3.2 recommended for the whole render-extension set; the contrary suggestion in [`docs/api-audit.md`](./docs/api-audit.md) §6.2 group 3 — keep them exported and move them to a `tui/render` subpackage — was already superseded in writing by §4 of the same document, which found the move impossible while `*Model` is in those signatures. Nothing else moves with it: the three concrete renderers, the dispatch and the output are untouched, no golden churns, and `Styles` / `NewStyles` / `NewStylesWithTheme` stay exported even though §3.2 ties their fate to this interface, because they are reachable from more than the render set and narrowing them is its own decision. **No host action** unless a host named `tui.ToolRenderer` in its own source, which it could only have done to declare a value it had no way to install.

## [0.20.0] — 2026-08-17

The transcript stops being a thing you scroll and becomes a thing you drive. `tab` hands it the keyboard, a cursor selects one item at a time, `space` folds the one you are on, `y` / `c` copy it, and `shift+←` / `shift+→` pan across the content that does not wrap — a table, a diff, a stack trace. Under all of it the render path is addressed by item instead of by one concatenated blob, which is what makes item-at-a-time navigation affordable at session length rather than an O(session) walk per keystroke.

The other half of the release is the quality backlog that had been queued behind a rendering-architecture spike and did not need to wait for it: the frame is measured and clipped to the terminal in both dimensions, modals fit a short window, the pickers filter and open on the right row, markdown and syntax highlighting follow the active theme, every remaining host call is off the event loop, and untrusted tool output can no longer write escape sequences to the operator's terminal.

### Added

- **`Options.ClipboardWriter`, and a copy notice that stops claiming what it cannot observe** ([#175](https://github.com/go-steer/core-tui/issues/175)). [#153](https://github.com/go-steer/core-tui/issues/153) shipped `y` / `c` over OSC 52, which is the right default — it is the only mechanism that reaches the clipboard of the machine the operator is *sitting at* rather than the one the process runs on, and that is the whole LiveAgent-over-SSH case. What it did not reckon with is how many terminals decline the escape: Terminal.app has never implemented it, iTerm2 keeps it behind a preference that is off by default, and several remote and web terminals strip it in the relay. On those the key did nothing at all, and since the protocol has no acknowledgement, the footer said `copied 24 lines` regardless. Claiming a result we cannot observe was the worse half of the defect, because it sends the operator looking for the bug in the wrong place.

  So there are now two writes and one honest sentence about them. `Options.ClipboardWriter func(text string) error` is host code called **in addition to** the escape, never instead of it — the two target different machines, so neither is a fallback for the other, and a host that is local wants both. `tui.SystemClipboardWriter()` supplies one out of `os/exec` (`pbcopy`, `wl-copy`, `xclip`, `xsel`, `clip.exe`) so a desktop host needs one line and no dependency; core-tui deliberately takes no clipboard library of its own, because a library that did would put windowing-system bindings in every host's module graph whether or not that host ever copies anything. It resolves a helper once, at construction, and returns **nil** when there is none — including on a Unix box with no display, where xclip is often installed and has no X server to reach. That nil is load-bearing rather than a failure: it is indistinguishable from leaving the field unset, so hosts assign it unconditionally, and a machine that was never going to have a clipboard does not report a failure per keystroke.

  The notice is the part an operator actually sees. It now names the mechanism — `copied 24 lines · osc52` — for as long as the escape is the only write, and drops the qualifier only when a host writer comes back clean, which is the one case where a copy has been confirmed rather than merely attempted. A host writer that fails says `· osc52 only` and quotes the error, capped so it cannot push the rest of the legend off the line. Deliberately *not* a `RoleError` row, which is how the other host callbacks report failure: a row appends to the transcript and scrolls it, and this key is pressed by an operator parked on a selection they are reading. The reply carries the notice's own generation (`Model.copyGen`, bumped wherever the notice is set, replaced or cleared) rather than the session's, because a notice turns over many times inside one session and a verdict that arrives after the operator has moved on has lost the right to speak — though not, of course, the right to have happened. The help panel says the terminal has to allow clipboard writes, which is the sentence that would have saved the trip through this paragraph.

- **`shift+←` / `shift+→` pan the transcript sideways over content that does not wrap** ([#154](https://github.com/go-steer/core-tui/issues/154)). Most of a transcript wraps, and wrapped text needs no panning — but the things an agent produces most of do not wrap: a table, a unified diff, a stack trace, one very long line of tool output. Those were cut at the right edge and the rest was simply gone. No scrollbar, no ellipsis, no key, no indication that anything had been removed. The reason it was gone is that it was never kept: rows were truncated to the viewport width on their way **into** the render cache, so by the time anything could have panned, the columns to pan to had already been thrown away. The cut now happens at the last possible moment — in the view walk, per drawn line — and the cache holds rows at their natural width. That is a strictly *stronger* version of the same contract rather than a weaker one: "no line reaches the frame wider than the window" used to hold for cached rows and had to be re-applied by hand to everything that was not one (the live tail, [#152](https://github.com/go-steer/core-tui/issues/152)'s fold summary), and now it holds for every line the frame contains, because there is exactly one place a line can reach the frame from. Nothing about heights changes — cutting a line does not split it, which is why the lazy walk's line budget ([#161](https://github.com/go-steer/core-tui/issues/161)) is untouched — and the unpanned case still cuts with `ansi.Truncate` rather than a zero-origin `ansi.Cut`, so an unpanned frame is byte-identical to what it was before this existed and the golden corpus does not move.

  Panning is **not** the old viewport's `xOffset`, which is what makes this worth describing at all. The predecessor of this change was a one-line patch that unpinned that field, and it produced corrupted output: `xOffset` made `ansi.Cut` remove cells from the **left** of every line and keep the window's width from there, so the text slid left and the right edge stayed exactly where it was. #161 deleted that viewport; this cuts the window `[x, x+width)` out of a line that is still full width, which is the operation the name implies, and it goes through `ansi.Cut` rather than a byte slice so the SGR sequences opened before the cut survive it — a diff's colour lives in escapes that are off-screen to the left. The step is **8 cells**: one column at a time is forty presses to reach a table's second column, a full window at a time throws away the overlap the eye needs to carry a row across the jump, and a fixed number rather than a fraction of the width means a pan lands in the same place on a narrow terminal as on a wide one. The right-hand limit is the widest line **in the window**, less the window — measured over the window rather than the transcript, which is the rule the whole item-addressed path lives by, and an over-estimate only for a partly scrolled row whose off-screen lines are measured too. That is the harmless direction: the operator can pan to a blank column and press the other arrow, which is not true of a limit that stops short of real content.

  The offset **resets on purpose**, and what resets it is the point. Moving the cursor drops it, because a pan is a way of reading one wide thing and carrying it to the next item would leave the operator looking at column 40 of a paragraph — which reads as a broken frame, not a scrolled one. Leaving focus mode drops it, since nothing in the composer's keymap could bring it back. A width-changing resize drops it, because the limit it was clamped against no longer exists. Line scrolling deliberately does **not** — reading a forty-row table a row at a time while panned is the case this exists for — and neither does a height-only resize, which would otherwise make a mouse drag's stream of same-width events unusable. The selection gutter does not pan either: the marker says which item the cursor is on, so it is frame furniture and stays at the left edge however far the text under it has slid. And because a pan is invisible in a frame with no left edge to compare against, the focus legend carries `panned 8 cols` alongside `shift+←→ pan` for as long as the offset is non-zero.
- **`y` copies the selected transcript item, `c` copies just the code in it** ([#153](https://github.com/go-steer/core-tui/issues/153)). The only way to get text out was the terminal's own mouse selection, which selects what is on the *screen*: the tool glyphs, the box rules, the selection gutter ([#152](https://github.com/go-steer/core-tui/issues/152)), the soft line breaks word wrap inserted, and every ANSI escape in between. Paste that into an editor and it is not the text the operator pointed at — a wrapped command comes back with a newline in the middle of it, which is the failure mode that turns a copy into a bug report. So this path never reads the frame. It reads the history entry under the cursor and reconstructs what the renderer was **given**: the markdown source of an assistant turn, the prompt as it was typed, and — for a tool row, which has no `Text` at all — the name, the structured args and the structured response, through the same `json.MarshalIndent` the detail overlay uses, which brings [#108](https://github.com/go-steer/core-tui/issues/108)'s escaping with it. One consequence worth stating: the copy does not depend on the width the terminal happened to be, so the same keystroke gives the same bytes at 60 columns and at 200. The single rendered fallback is a tool row whose host reported neither a response nor an error — the pre-rendered preview is all that exists for it, and it is stripped of ANSI on the way out. `RawRenderable` (the optional `Item` hook that has been sitting in `listcache.go` since the lazy list landed) is what carries this, so a future non-`Message` row type opts into copy by implementing one method.

  `c` is the narrower half: every fenced block in the item, joined by a blank line, fences and info strings excluded. Every block rather than the first or the biggest, because a turn that answers with a config file *and* the command that reads it means both, and picking one would be guessing — a second cursor for choosing between them is a whole navigation model for a case that is usually "there is exactly one". When the item has no code at all `c` copies **nothing** and says so, rather than falling back to the whole item: a key that copies something else when it cannot do what it says is worse than one that declines, because the clipboard is not inspectable from the TUI and the operator finds out on paste. The scanner is a small one — open fence, close fence, an unterminated fence still yields a block because the turn may still be streaming — and deliberately not `markdown.go`'s `insideOpenCodeFence`, which answers "does this prefix end inside a fence" by counting backticks and is documented as approximate because the cost of being wrong *there* is one extra re-render.

  The write goes out as **OSC 52** (`tea.SetClipboard`), which puts the text on the clipboard of the machine the operator is sitting at rather than the one the process runs on — which matters more here than in most TUIs, since a LiveAgent host is routinely on the far side of an SSH connection and a native clipboard call would have copied to the wrong computer. The caveat is that terminals cap the escape they will accept (8KB in some, 100KB in others; a few refuse it outright) and the protocol has no acknowledgement to detect that with, so a very long item can be reported copied here and dropped there. Truncating to the smallest known cap would silently corrupt the common case to protect the rare one, so this sends the whole thing and reports how much it sent. That report is the other half of the feature: a copy leaves the frame exactly as it found it, so the focus legend carries `copied 24 lines` / `copied 2 code blocks, 6 lines` / `no code block in this item` until the next transcript keystroke. No timer, no toast — a tick would need a generation stamp to keep two copies from fighting and a repaint nobody asked for, and "it says so until you do the next thing" can never be describing the wrong copy.
- **A cursor over transcript items, and `space` to fold the selected one** ([#152](https://github.com/go-steer/core-tui/issues/152)). Every item rendered at full height, so one 300-line tool result or one long assistant answer buried the rest of the scrollback and the only way past it was to scroll — which is the wrong instrument, because scrolling moves the window and what the operator wants is to make the item small and leave everything else where it is. The transcript now carries a **selection cursor**: while it holds the keyboard ([#151](https://github.com/go-steer/core-tui/issues/151)) a dotted `┊` bar runs down the left edge of the selected item for its whole height, rule and blank line included, so "which block am I on" is answered by looking rather than by pressing a key to find out. The glyph is dotted on purpose — `GlyphColumn` is already a solid bar and reads as structure; a cursor has to read as *transient*, and the dotted stem is the one that does not look like part of the layout. `space` folds the selected item to its first three lines plus a muted `▸ N more lines`, and folds it back. Items of four lines or fewer are left alone: a fold that saves nothing still costs a keystroke to undo, and having `space` do visible nothing on a short row is better than having it produce a summary longer than what it replaced.

  Two decisions are the whole implementation. **The gutter is reserved on every row, not borrowed under the cursor.** The tempting version draws the bar only where the cursor is and gives the two columns back everywhere else — and it is wrong, because an item's wrap width would then depend on where the cursor is, so every press of `↓` re-wraps two items, evicts their cache entries and shifts the text of both under the operator's eyes while they are trying to read it. The cursor has to be free; the price is two columns of transcript width, charged once, and eleven golden files that shift right by two. **A fold is a view of the cached render, not a second render.** Folding slices the lines the memo already holds rather than re-running `renderMessage` with a "collapsed" flag, so the cache key does not grow a dimension, folding and unfolding render nothing at all, and a folded item that later streams more content picks the new lines up through the ordinary version bump.

  This is where [#161](https://github.com/go-steer/core-tui/issues/161) pays for itself. A fold changes an item's height, and under the flat line offset the viewport used to keep, changing the height of anything above the window moved the window: fold something twenty rows back and the text the operator was reading jumps. With the position held as `(row, line)` the top of the window is *line n of item i*, which does not know or care what the items above it measure, so a fold anywhere outside the window is byte-for-byte invisible — pinned by a test that folds above the window and compares the whole frame. Inside the window the window stays put unless it has to move, and if the transcript is following the stream the tail stays pinned to the bottom as it shrinks. Revealing the cursor is bounded in both directions — it walks from the current top or from the end, never over the session — so the cursor cannot reintroduce the O(session) the item-addressed list just removed.

  The keymap shifts to make room. With the transcript focused, `↑`/`↓` and `k`/`j` now move the cursor **an item at a time** rather than a line, `shift+↑`/`shift+↓` scroll a line inside a long one, and `g`/`home` and `G`/`end` jump to the first and last item (`G` still re-arms following the stream). Item-at-a-time is the right default because the item is what the operator is looking for and a line is not; line scrolling is what you reach for once you have found the item, which is exactly when a modifier is cheap. The focus legend moves with the keys — `↑↓ select` and `space fold` take the two slots that `↑↓ scroll` and `pgup/pgdn page` had, because the legend exists precisely so the mode does not have to be probed by pressing something, and paging is the one binding nobody guesses wrong. Selection state is deliberately **not** a render input while the composer holds the keyboard — the marker is drawn by the list, not by the item, so an unfocused transcript renders precisely what it rendered before. Taking focus seeds the cursor on the item it was already on if that is still on screen, and otherwise on the last visible one, so entering focus mode scrolls nothing. Folds are keyed by message ID and survive scrolling, resize and re-theming; they are dropped on `/clear`, a session switch and a resume, and cannot be misapplied across any of those because `History.Reset` does not rewind the ID counter.
- **The transcript can take the keyboard from the composer, and the arrow keys scroll it** ([#151](https://github.com/go-steer/core-tui/issues/151) / [#155](https://github.com/go-steer/core-tui/issues/155)). Every keystroke the modal cascade did not claim was forwarded to *both* the textarea and the chat viewport, so the transcript could only be driven by keys nobody would ever type into a prompt. That is why `NewModel` strips the viewport's KeyMap to four non-letter chords — the vim defaults would have made `b` page up and space page down mid-sentence — why the arrows belong to prompt-history recall, and why `Right` is unusable at all (it sets `xOffset`, after which `ansi.Cut` eats characters off the **left** of every line). One constraint, four blocked affordances: line scrolling, select-and-expand ([#152](https://github.com/go-steer/core-tui/issues/152)), copy ([#153](https://github.com/go-steer/core-tui/issues/153)) and horizontal scroll ([#154](https://github.com/go-steer/core-tui/issues/154)), each of which would otherwise have had to invent its own chord. **`tab` now moves the keyboard between the composer and the transcript**, and while the transcript holds it the letter and arrow space is free in one move: `↑`/`↓` and `k`/`j` scroll a line, `home`/`g` and `end`/`G` jump to either end, and `G` re-arms following the stream — the same contract `ctrl+l` and `end` already had from the composer side, and read back off `AtBottom()` by the existing `syncFollow` rather than asserted per key. `tab` is the one navigation key bubbles' textarea does not claim, so taking it costs the composer nothing; with exactly two regions forward and backward are the same move, which is why it carries this alone and `shift+tab` keeps the permission-mode chip. Three things are deliberately **not** bound: `pgup` / `pgdn`, which already page from either focus because unclaimed keys still reach the viewport and a second paging implementation would be one more thing to keep in step with the first; `space`, held for #152; and the viewport's `ctrl+d` / `ctrl+u` half-page pair, because `ctrl+d` quits unconditionally and a half-page keymap with one working half is worse than none. Keys the transcript declines **fall through** to the global switch, so `ctrl+b`, `ctrl+g`, `ctrl+x`, `ctrl+l`, `shift+tab` and `?` all still fire — those belong to the frame, not to the composer, and having to leave the mode to reach them would defeat it. (`?`'s empty-input guard exists to protect typing, so it lapses here, where there is no typing to protect.) There are three ways back — `tab`, `enter`, and `esc`, which enters the cascade below every open surface and above the two cancel arms, so interrupting a turn from focus mode costs a second press; `enter` deliberately does not also submit, because the caret is invisible from here and firing a half-written prompt is not undoable. A mode that swallows typing has to be visible without pressing a key to find out, so it carries **three signals**: the footer legend names it (placed above the streaming arm, since reading back through a live turn is the case the mode exists for), the composer's top border drops from the active border token to the quiet one — the theme's own vocabulary, so it needs no new style field and follows all twelve palettes — and the hardware cursor goes away with the textarea's focus, since `textareaCursor` returns nil for a blurred widget. Blurring is load-bearing rather than cosmetic: bubbles drops every message a blurred textarea gets, which is what keeps stray letters out of a prompt nobody is looking at, and it is also why a bracketed paste — which never goes through `handleKey` — takes the keyboard back before landing, rather than vanishing silently. A turn ending no longer re-arms the textarea unconditionally: that would yank focus out of a transcript the operator deliberately moved it to. A session switch does reset the mode, because the transcript they focused is gone. Golden-neutral except for the two help frames, which gain the new `Transcript focus` section (and one more page at 60 columns); the input border's other state is unreachable from a corpus captured at rest.
- **Markdown and syntax highlighting follow the active theme** ([#116](https://github.com/go-steer/core-tui/issues/116)). Switching themes repainted the chrome and left the majority of the pixels on screen untouched, so the surface read as two unrelated designs: `tui/syntax_cache.go` pinned inline highlighting to a package-level `styles.Get("github")` fixed at init, and `newMarkdownRenderer` built its Glamour config from a `dark bool`, collapsing all twelve themes into exactly two markdown styles whose only theme-adjacent patch was five hardcoded 256-color heading indices. Pick Matrix or Christmas and the headings stayed Glamour-blue, the code fences stayed GitHub-gray, and only the frame around them moved — on the largest surface the operator looks at. `tuiStyleConfig` now takes the `Theme`: body prose is `FgBase` instead of Glamour's `252`, H1 reverses `OnPrimary` out of a `Primary` fill, H2–H6 walk a derived `Accent`→`FgMuted` ramp, and rules / links / list bullets / block quotes / inline code take `BorderQuiet` / `Secondary` / `Accent` / `FgMuted` / `BgElevated`. Two additive `Theme` fields carry it: `OnPrimary` (the foreground for text painted on a `Primary` fill — `Primary` alone cannot answer "what is legible on top of this?") and `ChromaStyleName` (the Chroma style, now shared by Glamour fences *and* the inline diff / tool-preview highlighter, which previously painted from two unrelated palettes). Both are **derived, not required**: `NewStylesWithTheme` normalizes every `Theme` on its way to a `Styles`, filling a nil `OnPrimary` from a WCAG luminance check on `Primary` and an empty `ChromaStyleName` with `github`, so the twelve builtins, the golden corpus's bare `Theme{…}` literal and any host-constructed theme all keep working untouched — and because both `Branding` override sites mutate `Primary` and *then* call `NewStylesWithTheme`, an accent override re-derives its own contrast foreground for free. The builtins each name a Chroma style in both polarities (Dracula for the house palette it is named after, gruvbox for Anthropic clay, tokyonight for Gemini, swapoff for Matrix's phosphor, rrt's red/green/gold for Christmas, …). Heading tiers are computed from the two endpoints rather than added as five more tokens — `Theme` is being narrowed for v1.0, not grown.
- **Type-to-filter in the model, session and theme pickers** ([#117](https://github.com/go-steer/core-tui/issues/117)). Typing a letter into any of the three did nothing at all: each `HandleKey` was a four-case switch over ↑ / ↓ / Enter / Esc with a catch-all that consumed everything else so it could not leak into the chat textarea behind the modal. On a host advertising forty models, or a project with a hundred saved sessions, the arrow keys were the whole navigation story. All three now carry a one-line filter input as the first row of their body, with a `matched/total` count beside it and the matched span picked out on each row. The ranking is the slash palette's, lifted out of `palette.filtered` into a shared `rankNames` helper so the two surfaces cannot drift: case-insensitive, four tiers — exact basename, basename prefix, whole path segment, substring anywhere — tiebroken by shorter name. No new dependency; see [decisions.md D27](./docs/decisions.md) for why not `sahilm/fuzzy`, and note the consequence — matching is on contiguous substrings, so a highlight is one span and `mgo` does not find `main.go`. Model and session rows match on their display name *and* their ID, since both are printed on the row. Input arrives as real `tea.KeyPressMsg` values through `KeyMsgDialog`, so `Key.Text` and bracketed pastes reach the filter, and each picker implements `DialogCursor` so the filter row owns the terminal caret — without it `modalCursor` would answer `(nil, true)` and the surface people type CJK into would have no IME anchor ([#105](https://github.com/go-steer/core-tui/issues/105) / [#123](https://github.com/go-steer/core-tui/issues/123)). A filter that matches nothing keeps the picker open with the row still editable; a host that advertises an empty list still reports that in the chat and closes, as before. The filter row's cost is one body row, paid for by passing `modalChromeRows+1` at the three picker call sites rather than by changing a constant four other modals share. The three dialogs had no test files of their own; they do now, covering the shrinking-list cursor clamp that used to be `(idx ± 1 + len) % len`, and the theme picker is in the frame-invariant grid.
- **A frame-invariant test harness, a golden corpus, and committed render benchmarks** ([#101](https://github.com/go-steer/core-tui/issues/101)). `package tui` carried 202 `strings.Contains` assertions and exactly five tests that called `View()` at all — a combination that proves a token is present *somewhere* in the output and says nothing about where it landed or how wide it is, which is precisely the defect class the layout work ahead is about. Three pieces close the gap. A **frame-invariant grid** drives a real `Model` across widths 40 / 80 / 100 / 120 / 200 × heights 4 / 10 / 24 / 50, in both `StatusHeader` and `StatusSidebar`, with the base chat, a seeded transcript, the permission overlay, the elicitation modal and the help panel open — 200 cells, each asserting `ansi.StringWidth(line) <= width` for every line and a total line count `<= height` — plus a resize-sequence variant that walks one model through seven successive `WindowSizeMsg`s, so cache- and geometry-carried state is exercised too. A **golden corpus** under `tui/testdata/` pins the composed frame at three widths and the seven `Model`-free renderers (`renderToolPreview`, `renderToolPreviewWithResult`, `renderToolDetail`, `renderDiffInline`, `renderCodeInline`, `renderLatencyBadge`, `renderReadPreview`) byte for byte, ANSI escapes included; `go test ./tui -update` regenerates it. Every golden renders through one explicit `Theme` literal owned by the test file and a fixed named chroma style — never `m.styles`, never the background-detected theme — so a later palette change churns zero files, and `.gitattributes` marks `*.golden -diff` so escape-heavy fixtures don't drown a review. **Benchmarks** cover `refreshViewport` (warm and cold cache), a width-changing `WindowSizeMsg` and its height-only control, and `View()` end to end, each swept over 10 / 100 / 400-turn transcripts; the width-change / height-only pair is the measurement [#104](https://github.com/go-steer/core-tui/issues/104) needs, since only a width change invalidates the lazy-render cache.
- **The terminal's real cursor is parked on whichever text surface owns input** ([#105](https://github.com/go-steer/core-tui/issues/105)). `tea.View.Cursor` was set nowhere — `grep -rn 'tea.Cursor' tui/*.go` outside the tests returned zero hits. Every text surface drew its own caret instead, a reverse-video block painted into the frame, and the hardware cursor stayed wherever the last write happened to leave it. Three things break when that happens, none of them visible to a sighted operator typing ASCII: an IME's candidate window follows the *hardware* cursor, so composing CJK or emoji opened it in the wrong place; the operator's configured cursor shape and blink were never consulted, because a painted block has neither; and assistive technology, which tracks the terminal cursor, had nothing to follow. The chat textarea and the text-input dialog now run with `bubbles`' virtual cursor off and report a real position, which `View()` translates into absolute frame coordinates. The translation is per layout — `StatusHeader` stacks a status row above the chat, `StatusSidebar` drops it and puts the input inside a `chatWidth`-wide left column — and per modal, where a centered overlay's origin is derived from its own measured size using the same gap split `lipgloss.Place` performs, never a guess. Modals that own input take the cursor with them: the text-input dialog through the new `CursorDialog` extension, and the elicitation form's focused field, whose caret follows Tab and the form's scroll window and is measured in terminal **cells** so a wide label or a `日` in the value doesn't shift it. Surfaces with no caret to offer leave it nil, so the terminal hides it rather than parking it somewhere arbitrary: a permission prompt answered with `y`/`n`, the `/btw` viewer, the arrow-nav pickers, an elicitation boolean or enum, a blurred input. The position is resolved *after* the frame-clipping post-pass ([#102](https://github.com/go-steer/core-tui/issues/102)) and clamped against it — a row that clipping removed yields no cursor at all rather than a stale one, while a column past the right edge is pulled back to the last cell, because a caret legitimately sits one cell past the final glyph. One visible change comes with it: the painted block on the first character of the input placeholder is gone, and that cell is now where the terminal draws its own caret.
- **`CursorDialog`** — an opt-in extension to the `Dialog` surface for dialogs whose body owns a text-editing widget (`DialogCursor(width int, m *Model) *tea.Cursor`, returning a position relative to the dialog's own top-left cell), plus **`Overlay.Cursor(width int, m *Model)`** which routes to the front-most dialog. Both are additive; a `Dialog` that doesn't implement the extension gets no cursor, which is the right answer for the arrow-nav pickers. It is shaped as an extension rather than a contract method deliberately — folding "where does the cursor go" into `Dialog` itself belongs with the contract work in [#115](https://github.com/go-steer/core-tui/issues/115), and when that lands the change is to move the method and delete one type assertion.
- **The thinking line says how long the turn has been running** ([#111](https://github.com/go-steer/core-tui/issues/111)). It showed a rotating verb and a moving spinner, which together answer "is anything happening" and nothing else — so the single most common question an operator has while waiting, *is this a big turn or is it wedged*, had no answer on screen. The line now carries a muted elapsed suffix: `Thinking... 12s`, then `1m04s`, then `1h02m`. Three deliberate properties in that format, all of them about a string that re-renders under an already-moving spinner. There is **no sub-second component** — `0.4s → 1.2s → 2.7s` is noise on a line whose job is a rough magnitude. The minor unit is **zero-padded**, because `1m9s → 1m10s` shifts the tail of the line a column mid-turn and `1m04s → 1m10s` does not; the width changes only at 10s, 10m and 10h, once each per turn. And the readout **coarsens as it grows**, dropping seconds past the hour where they are pure churn. It stays hidden below one spinner cadence (3s): the spinner tick is the repaint that advances the number, so anything shown sooner is a value the operator cannot watch move, and short turns never flash a `0s` on their way past. No new timer is involved — `spinnerTickMsg` already fires every 3s and already marks the viewport dirty. The origin is stamped at exactly the two sites that take a new `spinnerGen` ([#112](https://github.com/go-steer/core-tui/issues/112)): `submitTurn` for the per-turn `Run` path, and `applyStreamChunk`'s `spinnerActive` false→true flip for a LiveAgent stretch, which has no `submitTurn` to hang off. That second site is what keeps the feature from shipping its own worst bug — an unstamped origin on the LiveAgent path would have measured from the zero time and rendered a fifty-five-year turn — and *stamping* it, rather than merely suppressing the zero value, is also what makes a second stretch measure from its own start instead of the first one's. The field is zeroed wherever the animation stops (`finalizeTurn`, the LiveAgent commit, a session switch), so the invariant is "non-zero iff a spinner animation is live" and no render-path gate is load-bearing for correctness. A backwards clock — NTP step, suspend/resume — clamps to absent rather than to a negative. Tested against an injected clock rather than a golden, for the obvious reason; the golden corpus is byte-for-byte unchanged, since its model is idle and renders no spinner line at all.

### Changed

- **The transcript renders the rows on screen, not the whole session** ([#161](https://github.com/go-steer/core-tui/issues/161)). Every repaint concatenated the entire history into one string and handed it to a `viewport` that sliced a screenful back out of it, so the cost of showing forty rows was set by how long the session had been running rather than by how big the window is. At 400 turns a warm repaint was 6.89ms and 1.98MB, and a pane drag — which is a stream of width-changing events, not one — spent **105ms per event**, 2.20GB across a thirty-event drag. The transcript now holds items. The scroll position is a pair, `(row, line)`: the window's top row is line *n* of row *i*, because a flat line offset cannot be resolved to a position in the transcript without knowing the height of everything above it, and knowing that is the O(session) nobody wanted to pay. From a pair the walk starts at a row it already knows and stops when the height budget is spent, so rows past the fold are never rendered and never even measured. The per-item render memo that already existed (keyed by message ID, version and width, from [#104](https://github.com/go-steer/core-tui/issues/104)) now stores the split lines alongside the text, since a row's HEIGHT is what every offset calculation actually asks for and re-splitting a cached string per query would put the cost straight back. Two rules keep it honest. Nothing on the frame path may ask for a global total: *are we at the bottom* is answered by a walk UP from the end that stops after one screenful, and the exhaustive flat-offset conversion survives only as the inverse a test needs. And the resize pass re-wraps a row and then measures it, one row at a time, so the window it stops at is the window the operator will see rather than a screenful-shaped over-estimate. At 400 turns a warm repaint is now **164µs and 14.8KB** (42x faster, 134x less memory, 867 allocations down to 135), a width-change event **7.9ms** rather than 105ms, and the drag that allocated 2.20GB allocates 55.7MB. All of them are flat in transcript size — 100 turns and 400 turns measure the same, to the noise — which is the property that actually matters, because a session only ever gets longer. Two pieces of machinery went with it: the chat's `bubbles` viewport, whose vim-convention KeyMap `NewModel` had to overwrite binding by binding and whose `xOffset` cut characters off the **left** of every line, and [#104](https://github.com/go-steer/core-tui/issues/104)'s carried-over "approximate" renders, which existed so a drag could serve rows the operator could not see — a window that only asks for the rows it draws never requests them at all. The frame itself did not change: the golden corpus is byte-for-byte identical.

### Fixed

- **A submission in LiveAgent mode shows a waiting indicator before the first token arrives** ([#148](https://github.com/go-steer/core-tui/issues/148)). On the `LiveAgent` path there is no `submitTurn`, so the only site that opened a spinner stretch was `applyStreamChunk`'s `msg.partial` branch — which by construction cannot run until the host has already produced output. The window the operator most needs an indicator for, between pressing enter and the first token coming back, was the one window with none, and a host that emits only committed messages (`Partial=false`, a perfectly legal adapter shape) got a spinner *never*. `InjectableAgent.Inject` returning nil now opens the stretch itself: the submit is the start of the turn, so it is where the animation starts and where `turnStarted` is stamped, which also means the elapsed readout ([#111](https://github.com/go-steer/core-tui/issues/111)) measures the wait the operator actually experienced rather than starting the clock at the host's first token. The two arming sites are folded into one idempotent `beginLiveStretch` so the ordinary case — operator injects, host answers — is a single stretch: the first partial finds `spinnerActive` already set and does not restart the animation, bump `spinnerGen` out from under the live tick chain ([#112](https://github.com/go-steer/core-tui/issues/112)), or move the elapsed origin. Arming the spinner in a place no chunk necessarily follows makes three previously unreachable stalls reachable, so its counterpart `endLiveStretch` now also runs on disconnect (both the permanent-error and iterator-returned arms) and on a *successful* `/interrupt` — but deliberately not a failed one, where the remote turn is still running and the spinner is telling the truth. A rejected `Inject` arms nothing. The tick chain needs no separate teardown: `spinnerTickMsg` re-arms only while `turnInFlight`, which on this path is exactly `spinnerActive`.
- **The tool-call, subagent and text-input dialogs keep their footer on a short terminal** ([#149](https://github.com/go-steer/core-tui/issues/149)). [#142](https://github.com/go-steer/core-tui/issues/142) made `fitModalContent` the single place the modal chrome is joined and gave it one guarantee — spacing goes before content, and the footer key hint, the row that says which key closes the thing, is never shed. That pass is gated on `RenderContext.Height`, which means "the geometry is known"; a zero disables it, because a bare `Model{}` in a test or a pre-resize frame has no height to fit to. **Four `RenderContext` literals never set it.** The tool-call detail overlay (`Ctrl+X`, both its populated and its empty state), the subagent overlay (`/subagents <name>`) and the shared text-input dialog therefore composed exactly as they had before #142 and fell through to `clipFrame`, which keeps the FIRST `height` rows — so what they lost was the bottom: the footer rule and `esc close`. The three pickers set `Height` and were fine, which is the whole reason the regime looked like it had landed. Underneath that, the tool-call overlay's body allowance predated the height regime and did its own arithmetic — terminal height minus a chrome constant of `8`, minus a further `6` nothing explained, floored at `6` rather than at `minModalBodyRows` and never going fullscreen. On a twelve-row terminal that floor handed back a six-row body against seven rows of chrome: a thirteen-row modal in twelve rows. At the roomy end it was wrong in the other direction, composing 17 rows of a 24-row terminal's 20-row allowance and 13 rows of a 14-row terminal's 10 — three rows wasted in the first case, three rows into the margin in the second. Both dialogs now go through `modalBodyHeight` like every other modal, but through **two** helpers rather than the one they shared: `toolCallBodyHeight` pays `modalChromeRows + 2`, counting the header banner and the blank line the overlay puts *inside* `Body`, and `subagentBodyHeight` pays `modalChromeRows`, because that one puts nothing extra there. The chrome figure is derived from `modalChromeRows` rather than restated as a literal, so the next change to the shared chrome reaches both. One shared helper could not have been right for both surfaces at once, and the hardcoded `8` it used was a guess against a six-item list — which is how it stayed wrong straight through #142. Covered by extending #142's own table: it named five modal surfaces and neither of these two, so the three new cases (tool-call, subagent, text-input) sweep both widths and all eleven heights for "the block fits" and "the close key is still on it", and a new assertion pins the allotment directly — an overflowing modal occupies exactly the terminal minus the margin, which fails against the predecessor arithmetic in both directions and is the half a shedding pass cannot detect, since a dialog that over-budgets still *looks* right while its own scroll geometry describes a modal nobody is looking at.
- **The spinner line no longer double-punctuates** ([#141](https://github.com/go-steer/core-tui/issues/141)). `renderSpinnerLine` appended `GlyphTruncate` to the rotating cognition verb unconditionally, and every entry in both built-in verb pools already ended in `...` — so the shipped bytes were `Thinking...…`, three ASCII dots and then the ellipsis glyph on top. It had presumably looked like that since the pools were written; nothing goldened a spinner line until the live-mode fixtures landed in [#139](https://github.com/go-steer/core-tui/issues/139), because the spinner only renders mid-turn and the rest of the frame corpus is captured idle. The fix normalizes rather than edits the data: `trimTrailingEllipsis` strips a trailing ellipsis — ASCII `...`, the `…` glyph, or any mix and repetition of the two, plus the whitespace around it — from the verb before the append. Dropping the dots from the defaults would have fixed the defaults and left the same defect reachable through `Options.ThinkingPhrases` / `Options.WorkingPhrases`, which are the pools a real host ships; normalizing fixes both, keeps `GlyphTruncate` as the single authority for the trailing affordance (as it already is for the truncated-diff marker in `renderDiffInline`), and changes no documented contract. Only a *trailing* run is removed, so `"Wait... then more"` keeps its mid-phrase ellipsis, and a run has to read as an ellipsis to qualify — a phrase ending in one sentence period keeps it. The three `live_frame_*` goldens churn by the three dropped dots each, which is the proof the fix reaches the frame.
- **A modal fits the terminal instead of having its footer clipped off** ([#142](https://github.com/go-steer/core-tui/issues/142)). `modalBodyHeight` subtracted a four-row `modalMarginRows` margin and then floored the result at `minModalBodyRows`, so every modal composed to at least eleven rows no matter how short the terminal was — measured on the theme picker, eleven rows at heights 4, 8 and 10 alike. `clipFrame` ([#102](https://github.com/go-steer/core-tui/issues/102)) kept the frame legal by keeping the FIRST `height` rows, so what an overflowing modal lost was its bottom: the body, the footer rule, and the footer key hint — the one row that says which key closes the thing. The margin exists so the operator keeps a sliver of chat visible above and below and the overlay reads as an overlay; on a terminal too short to hold the modal at all, that sliver was being bought with `esc cancel`, which is a bad trade. Modals now degrade to fullscreen below `modalFullscreenBelow`, a threshold derived rather than picked: it is `modalChromeRows+1` (the pickers' chrome, one row taller than everyone else's since the filter row landed in [#117](https://github.com/go-steer/core-tui/issues/117)) plus the margin plus the body floor, i.e. exactly the height at which the floor engages and the subtraction stops reflecting what fits. Below it the margin contributes zero and the floor is relaxed — a two-row window is worth having when the alternative is a clipped one — so chrome 5 + body 3 fits an eight-row terminal exactly, where it used to compose eleven. Above it nothing moved: the margin, the floor and the composed bytes are unchanged, which `TestGolden_ModalFrame` now pins at 100 and 160 columns. Separately, the row budget was only ever counted in LOGICAL rows, so a body line wider than the modal wrapped to two or three terminal rows and blew a budget that looked met — which is why the theme picker overflowed a perfectly ordinary 24-row terminal at 60 columns. The six chrome rows are now joined in one place, `fitModalContent`, which measures the wrap and sheds rows cheapest-first: the two blank spacers, then the footer rule, then body rows from the bottom, then the title. The footer key hint is never shed. Below the height that hint itself wraps to there is no honest answer left — the close key is at the END of the hint, so no truncation of it keeps the useful part — and the modal degrades to the hint alone for `clipFrame` to trim, which cannot produce a negative height and cannot panic. The scroll engine is untouched in the degraded mode: the window is smaller, not absent.
- **Shift+Tab no longer writes to disk from the event loop, and the rest of the `/cmd` host calls moved off it too** ([#137](https://github.com/go-steer/core-tui/issues/137)). [#114](https://github.com/go-steer/core-tui/issues/114) moved the hot-path capability calls into `tea.Cmd`s and left the ones behind an explicit `/cmd` for a follow-up, on the reasoning that an operator who has just typed a command reads a brief stall as the command working. The item that did not fit that reasoning was not on its list at all: **`Options.PermissionMode.Set` and `.Persist` fired on Shift+Tab**, a bare keystroke, from inside `Update` — `Persist` writes the mode to the host's config file, so cycling the permission chip did **disk I/O on the event loop**, and both return values were discarded into `_`. It was outside #114's inventory only because `PermissionMode` is a `func` field on `Options` rather than one of the §3.3 capability interfaces, which is a distinction about how core-tui declares the seam, not about who runs the code or how long it takes. The chip still flips on the keystroke — a bare-keystroke indicator has to track the key, not the host — but the two callbacks ride a Cmd now, and `permissionModeAppliedMsg` **rolls the chip back** when `Set` fails, because a chip reading `bypassPermissions` while the gate is still asking for every call is a safety claim the library cannot back; a rollback that arrives after a second Shift+Tab has already moved the chip is discarded, the same ownership check the pickers apply to a superseded switch. A failing `Persist` keeps the mode and says so — the session is in the new mode, it just will not survive a restart. The other three `Options` persistence callbacks go with it for the same reason: `PersistStatusLayout` was inline on **Ctrl+B**, also a bare keystroke and also with its error thrown away, and `PersistModelChoice` / `PersistThemeChoice` were inline in the two picker commit paths. Behind `/cmd`: `ToolLister.Tools` (`/tools`), `PermissionController.SessionApprovals` (`/permissions`) and its three mutators (`/allow`, `/deny`, `/allow bundle:<name>`), `SubagentLister.Subagents` (`/subagents`), `PricingController.Set` — from both the positional form and the `huh` form's submit handler — and `SlashProvider.SlashCommands` from `/help`, which now paints the built-in catalogue on the keystroke and appends the host's section when it answers. `/subagents <name>` stopped calling `Subagents()` to resolve its argument and reads the `hostSnapshot` roster that the sidebar already refreshes off-loop; a name that is not in a one-second-old roster falls through to the existing "ask the host anyway" branch, which is what happened for an unknown name before. Each new message type carries `gen` and is dropped on a mismatch like the ~26 existing `sessionGen` guards, and each `/cmd` posts an immediate acknowledgement row and renders its result when the reply lands — `remoteInterruptCmd`'s call-site shape. **Still synchronous, tracked on [#137](https://github.com/go-steer/core-tui/issues/137):** `/switch <id>`, which needs a genuine two-stage enumerate-then-switch flow rather than a mechanical move, and `SlashProvider.SlashCommands` in `dispatchSlash`'s name-match loop, which is not worth splitting on its own while the synchronous `SlashProvider.InvokeSlash` immediately below it is still inline — the two belong in one change. Verified by extending #114's `slowAgent`, whose capability methods sleep 500ms: every rewritten call site is asserted to return from `Update` in under a tenth of that with the host's call counter still at zero, `View()` still makes provably zero host calls after each of them, and the stale-generation drop is covered per message type.
- **The syntax cache and the `/btw` modal survive a theme swap** ([#116](https://github.com/go-steer/core-tui/issues/116)). Two latent defects that only became reachable once highlighting and markdown were theme-derived. `highlightLine`'s never-evicted `sync.Map` keyed on `lang \x00 bg \x00 line`, which was complete only while the Chroma style was a package-level constant; the key now carries the style name, so a `/theme` swap cannot replay the previous palette's bytes for the rest of the process. And `refreshTheme` cleared `m.markdown` but not `m.modalMarkdown`, so swapping themes with a `/btw` answer open would have kept the modal body on the old palette until its width happened to change.
- **LiveAgent mode shows the stream while it is streaming** ([#135](https://github.com/go-steer/core-tui/issues/135)). `renderInProgress` gated the whole in-progress block on `m.state == stateStreaming`, and `stateStreaming` is assigned in exactly one place — `submitTurn`. The `LiveAgent` path ([#22](https://github.com/go-steer/core-tui/issues/22)) never calls `submitTurn`: it is driven from `applyStreamChunk`, which accumulates `m.inProgressText` and flips `m.spinnerActive` but leaves `m.state` at `stateIdle`. So the one mode whose entire purpose is watching an agent work autonomously rendered neither the streamed prose nor the spinner verb line — the operator saw an idle-looking TUI for the whole stretch and then the finished message in one lump when the commit chunk landed. The gate now asks the question it means to ask, through a `turnInFlight` predicate shared with the spinner-tick handler: something is in flight when a Run-driven turn is streaming *or* a live stretch has the spinner up. It is one predicate rather than two conditions because `renderInProgress` asks twice — once to bail out, once to emit the body — and widening only the first leaves the body skipping the text for the same invisible result. `m.state` keeps meaning "a Run-driven turn is in flight", so the nine other reads of it that gate interrupt and submit behaviour are untouched. Two changes written against this path and dead on arrival now paint: the per-stretch spinner tick chain ([#112](https://github.com/go-steer/core-tui/issues/112)) and the per-stretch elapsed readout ([#111](https://github.com/go-steer/core-tui/issues/111)), which counts from the start of the current stretch rather than inheriting the previous one's origin. The live path had no frame coverage at all, which is how this survived; it now has a `live-stretch` cell in the frame-invariant grid and a three-width golden capturing prose, spinner and elapsed suffix together, rendered through the injected clock so the corpus is not a function of when it was taken.
- **The dialog text-input caret lands on the right cell for CJK and emoji** ([#125](https://github.com/go-steer/core-tui/issues/125)). `textinput.Cursor()` in the pinned `charm.land/bubbles/v2 v2.1.0` computes its column as `m.Position() + promptWidth` — a **rune index** added to a **cell width** — so every double-width rune before the caret loses it a cell, and typing `日本語` into a text-input dialog left the terminal cursor three columns short of the glyph it belongs on. That is exactly the IME anchoring [#105](https://github.com/go-steer/core-tui/issues/105) set `tea.View.Cursor` to get right, still wrong on the one surface people compose CJK into. `textarea.Cursor()` measures `LineInfo().CharOffset` and has always been correct, which is why the chat input was unaffected. The new `textInputCursor` helper recomputes the column from `Value()` and `Position()` with `ansi.StringWidth`, and `textInputDialog.DialogCursor` goes through it. **Partial by necessity:** the same upstream function also ignores `m.offset`, its horizontal scroll position, so a value wider than the box reports a column computed against the unscrolled string and the clamp pins the caret to the right edge — reachable with pure ASCII. `m.offset` has no exported accessor, so correcting it downstream would mean reimplementing `handleOverflow`'s scroll arithmetic against state we cannot observe. `handleOverflow` zeroes the offset whenever the value fits, so the fitting case is corrected exactly and the scrolled case falls through to upstream unchanged, with a test pinning that split so it stays deliberate. The complete fix has to come from upstream, where both halves are already reported and open — [charmbracelet/bubbles#906](https://github.com/charmbracelet/bubbles/issues/906) for the rune-vs-cell measurement and [#1001](https://github.com/charmbracelet/bubbles/issues/1001) for the ignored scroll offset. `textinput.go` is byte-identical in v2.1.1, so a version bump is not it; our correction self-neutralises to zero once theirs lands.
- **The model picker opens on the model you are using** ([#110](https://github.com/go-steer/core-tui/issues/110)). `newModelPickerDialog` hardcoded `idx: 0`, so `/model` and `Ctrl+G` highlighted whichever model the host happened to list first and the operator had to find their current one before they could navigate relative to it — on a host advertising forty models, with no type-to-filter yet, that is the difference between a picker and a list you scroll. The theme picker had solved this since v0.1.0 by seeding on the active theme; the model picker now does the same. The seed lands in `applyModels` rather than the constructor because [#114](https://github.com/go-steer/core-tui/issues/114) made the list arrive asynchronously — there is nothing to seed against until the host answers. Matching is on ID first and then the display name, the same predicate `Render` already uses to paint its `(current)` tag, so the cursor and the tag cannot disagree; a model the host does not list in its own catalogue still lands on row 0.
- **The help panel is laid out to the terminal in both dimensions** ([#119](https://github.com/go-steer/core-tui/issues/119)). `renderHelpPanel` emitted the same 38 rows at every terminal size: its `width` argument reached the `<= 0` guard and the horizontal rule and nothing else, so each key row was a constant `"    " + key(padded to a hardcoded 24) + description` — 81 cells at the widest, in an 80-column terminal, and twice the terminal in a 40-column one. It also made the chrome budget wrong, because `lipgloss.Height` counts a row that visually wraps as one row. **Width** is now a derivation rather than a constant: the key column comes from the widest key actually present, capped so one 29-cell key row cannot push all 22 descriptions five columns right, and never allowed past half a narrow panel; descriptions **wrap** into the remainder with a hanging indent, and below the point where the aligned form stops being readable the panel switches to a **stacked** one — key on its own row, description full-width underneath. **Height** is pagination, on the panel's own key. `m.chrome.helpCap` is the row ceiling the budget ([#121](https://github.com/go-steer/core-tui/issues/121)) hands the panel, and laying out *to* it beats being elided *by* it, which is what the `… N more rows` marker was doing: `?` now opens the panel, walks it a page at a time, and closes it after the last page, with the title row saying which page is on screen and which key advances it. Paging on the key that opened the panel is what keeps `pgup` / `pgdn` with the chat — the panel's own Navigation section advertises them as chat scroll, and a scroll mechanism would have had to take them away and make it lie again. Pages break on section boundaries wherever they can, so a page usually comes in under the cap and the rows it does not spend go back to the chat viewport; one page always beats two, so a panel that would fit without the blank rows between sections is rendered compactly instead of split. Gated by a width × height grid asserting no rendered row exceeds its column and no page exceeds its cap, a content check that walking the pages still reaches all 22 documented keys, help-open frame goldens at 60 / 100 / 160 columns (the corpus had none — `goldenModel` never set `helpOpen`), and paged-panel cells in both the frame-invariant and the row-budget grids.
- **The input box grows again, and variable-height chrome can no longer push the frame past the terminal** ([#121](https://github.com/go-steer/core-tui/issues/121)). `syncInputHeight()` clamps the textarea to its line count between `textareaMinHeight` and `textareaMaxHeight`, and every one of its call sites follows the grow with a `resize()` — which opened with an unconditional `m.input.SetHeight(textareaMinHeight)`. The grow was computed and thrown away before it could be rendered, so the auto-growing box those doc comments describe ("multi-line paste / typed newlines grow the box visibly") survived **zero frames** and `textareaMaxHeight = 15` was unreachable dead configuration. Two adjacent gaps in the same feature go with it, both invisible while the clobber hid them: the newline arm of `handleKey`'s switch (`shift+enter` / `ctrl+j` / `alt+enter`) returns early and so never reached the reconciliation at the bottom of that function, and a bracketed paste never goes through `handleKey` at all — it falls out of `Update`'s switch to the shared forward-to-the-widgets tail. The two gestures whose entire purpose is to add rows were the two that did not grow the box, until some unrelated later keystroke reconciled the layout for them. The one-line clobber is gone, but on its own it would only have moved the damage: `resize()` had no notion of variable-height chrome yielding rows to fixed elements, so a 15-row box on a short terminal would overflow the frame exactly the way the **help panel** already did — `renderHelpPanel` emits 38 rows at every width ([#119](https://github.com/go-steer/core-tui/issues/119)), which on an 80×24 terminal composed a 48-row frame, and since `clipFrame` keeps the *first* `m.height` rows, pressing `?` clipped away the input box and the footer entirely: the operator lost the box they were typing into and the only row that says how to quit. The **palette** (`maxPaletteRows` + its own chrome) is the third instance. `resize()` now allocates the terminal's rows through an explicit chrome budget (`tui/budget.go`) instead of subtracting-and-flooring: unshrinkable chrome (footer, header, toast) is reserved off the top, then the input box's *minimum*, the chat viewport's `chatMinHeight` floor and one row per open panel, then — in priority order — the input box's *growth*, the palette, the help panel, with everything unspent going to the chat. Splitting the input box across two priorities is what resolves the conflict the issue names: a `textareaMaxHeight`-tall box wins against the palette and the help panel, but **not** against the chat floor, because watching the transcript vanish while typing is worse than typing into a box that scrolls internally past its height — which is what the textarea already does. Elements below the cut shrink rather than overflow: the palette narrows its scrolling window, and the help panel is elided with a `… N more rows` marker until #119 makes its content fit a column. Every term is still a measurement of the string `View()` will render, at the width it will render at, so `clipFrame` is back to being a safety net that does not fire — the only case left is a terminal shorter than the irreducible chrome (a 4-row pane, where the header, the input box and the footer are already taller than the screen), which the budget now reports as a number rather than discovering by accident. Two verification gaps closed with it. `assertBudgetExact` used to **skip** whenever the viewport bottomed out at `chatMinHeight` — which is exactly what the help panel causes, so every cell that would have caught the 48-row frame skipped silently; it now asserts the exhausted case as a checkable size instead. And the row-budget grid had no state in which the textarea was ever taller than three rows, because `resize()` guaranteed it could not be; it sweeps a tall textarea (alone and against the help panel) in both layouts across the full width × height matrix now. Golden-neutral: the frame corpus types nothing into the box, so its `LineCount()` is 1 and every golden is byte-identical. `BenchmarkResizeHeightOnly` and `BenchmarkResizeDrag400` are unmoved.
- **A key that jumps to the tail and resumes following the stream** ([#113](https://github.com/go-steer/core-tui/issues/113)). `ctrl+l` jumps to the top of the transcript and had no counterpart. Once following became explicit state ([#93](https://github.com/go-steer/core-tui/issues/93)), the only way back to a live stream was holding `PgDn` until `AtBottom()` re-armed the flag on its own — so an operator who had read back through a long session paid one keypress per screen to resume watching it, and on a session long enough to be worth reading back through, that is the whole cost of following in the first place. `end` now does it in one: `m.follow = true` plus `viewport.GotoBottom()`, the same pair `refreshAndScroll` uses, but without the `syncInputHeight` / `resize` that helper also runs — a jump to the tail changes no geometry, so it has no business re-resolving the layout. The binding is claimed **only while the input is empty**. bubbles' textarea binds `end` to `LineEnd`, and "end goes to end-of-line" is too strong a convention to shadow in a box the operator is composing in — the more so because `syncInputHeight` grows that box to `textareaMaxHeight` rows, where line-end is the whole point. With nothing typed there is no line to end, so the key is free and the chat takes it; with a prompt in progress it falls through to the textarea. `ctrl+e` reaches end-of-line in either state. `ctrl+d` and `ctrl+u` keep their existing shadows — recovering the viewport's half-page scroll bindings is not worth making the primary quit key scroll the transcript.

- **The help panel no longer advertises two keys that do nothing** ([#113](https://github.com/go-steer/core-tui/issues/113)). `renderHelpPanel`'s Navigation section listed `home / end` as "top / bottom". Neither key was bound anywhere: `grep -n '"home"\|"end"' tui/update.go` returned nothing, and bubbles v2's viewport binds neither — `handleKey`'s own fall-through comment said as much, a few lines below the switch that would have had to claim them. It is the same defect class as the truncated-diff marker naming `ctrl+o` ([#94](https://github.com/go-steer/core-tui/issues/94)): the one surface a new operator opens to learn the keymap was naming keys the package does not handle. `end` is bound now. `home` deliberately is **not** — `ctrl+l` already does exactly what it would, and a second binding for one action would spend the textarea's `LineStart` to buy nothing. So the rows name what exists instead: `ctrl+l` "jump to top (stops following the stream)" and `end` "jump to bottom (resumes following)". `ctrl+l`, the real goto-top key, was not listed at all before. A new test parses the rendered Navigation rows, presses every key they name, and asserts each one moves the viewport — so the section cannot quietly drift back out of sync with the switch that implements it.
- **CI no longer decides required checks by a race** ([#124](https://github.com/go-steer/core-tui/issues/124)). `ci.yml` carried `paths-ignore: ['**/*.md']` and a twin `ci-docs.yml` carried the inverse `paths: ['**/*.md']`, each emitting four **identically named** check runs. Because GitHub path filters match "any changed file", a PR touching both Go and Markdown satisfied both filters and ran both workflows — and since every PR here carries a CHANGELOG entry, that was the normal case rather than a corner case. Which of the two same-named results counted was then decided by whichever finished last, an ordering the old `ci-docs.yml` header admitted to relying on. Re-running the 3-second stub after a red pipeline produced four green required checks on a red commit. `ci.yml` now has no path filters and always reports; a `changes` job classifies the diff once and the four jobs short-circuit their expensive steps when it is docs-only. `ci-docs.yml` is deleted. The fast path also widened from `**/*.md` to include `docs/`, which the old filter missed entirely — `docs/site` carries `hugo.yaml`, `package.json`, its own `go.mod` and an `.scss`, so editing the published site's stylesheet used to run the whole Go pipeline. And `changes` now asserts the invariant the fast path rests on: no `//go:embed` may reference Markdown or `docs/`, since an embedded `.md` would let a docs-only PR skip the tests for a change that alters the built binary.
- **The context-fill ramp follows the active theme** ([#109](https://github.com/go-steer/core-tui/issues/109)). The `<used> / <size>` segment in the status header and in the sidebar's spend block is the one piece of chrome carrying real semantic weight — a three-tier ramp that shows the operator how close the context window is to overflowing before it bites — and it was the one piece that ignored the palette. `contextFillStyle` picked from three hex literals baked into the function (`#5FD787` / `#FFD75F` / `#FF5F5F`), so the ramp rendered identically across all twelve builtin themes and across the light and dark variant of each. Those three values are the *default* theme's `Success` / `Warning` / `Error`, which is why the defect was invisible on the house palette and worst everywhere else: on a light terminal the 85%-and-above tier is a pale coral on white — the tier the operator most needs to be able to read is the one that falls out of contrast. The three tiers now resolve `Theme.Success` / `Theme.Warning` / `Theme.Error` off the active theme, tokens that already existed, so no theme gained a field and no host action is required. Christmas gets pine / gold / cardinal, Google gets its brand green / orange / red, and the default palette renders byte for byte what it did before. The doc comment above the function had claimed a themed ramp all along; it is accurate now. Golden-neutral by construction — the frame corpus wires no `UsageTracker`, so neither usage summary reaches a golden.
- **A filename in a tool event no longer costs a full Chroma lexer sweep** ([#106](https://github.com/go-steer/core-tui/issues/106)). `detectLang` mapped a path to a lexer name by calling `lexers.Match` and nothing else — no memoization, on a function whose own upstream doc comment warns that it runs hundreds of `filepath.Match` calls per lookup. It is reached from four call sites on the tool-display path (`tool_preview.go` twice, `tool_preview_read.go`, `tool_preview_result.go`), which is to say once for every tool event that carries a filename, and the same handful of paths in a session re-paid the sweep every single time. Measured on this repo's usual CI hardware (AMD EPYC 7B12), one uncached lookup costs **4.89ms** for a path that matches a lexer and **2.42ms** for one that doesn't — a millisecond-scale stall on the UI goroutine per event, for an answer that cannot change. The result is now memoized in a `sync.Map` alongside the existing per-line `syntaxCache` and `lexerCache` in the same file, taking a hit to **19.8ns** and a miss to **19.5ns** (**247x** and **123x**), with zero allocations where the matcher's priority sort previously allocated on every hit. One deliberate divergence from the neighbouring `getLexer`, which does *not* cache its nil result: `detectLang` **does** cache the empty-string miss. `""` is the ordinary answer for the paths a session touches most — `README`, `LICENSE`, `Makefile`, extensionless notes, plain text — so leaving negative results out would have left the hotter half of the path uncached, on the branch that is the more expensive of the two to be wrong about at scale. There is no invalidation to get wrong: `detectLang` is a pure function of its label, so an entry stays correct for the life of the process, and the working set is bounded by the number of distinct paths one session touches. The render benchmarks are unmoved — `BenchmarkRefreshViewport` at 400 turns 6.90ms → 6.70ms, its cold-cache variant 19.1ms → 19.3ms, allocation counts identical — so nothing was borrowed from the repaint path to pay for this.
- **The thinking spinner can no longer end up running two tick chains at once** ([#112](https://github.com/go-steer/core-tui/issues/112)). `spinnerTick()` returned a bare `tea.Tick` carrying no identity — `spinnerTickMsg` was an empty struct — and the handler re-arms on every tick, so any path that armed while a chain was already live produced two independent chains, each re-arming the other's replacement forever. The visible symptom is the thinking/working verb pool rotating at 2x (3x after another overlap) for the rest of the session; the underlying one is `tea.Tick` accumulation that nothing ever reclaims. The existing level gate (`m.state != stateStreaming && (!m.liveMode || !m.spinnerActive)`) does not catch it, and cannot: it answers "should *a* spinner be running right now", not "which chain is this tick from", and the turn-chaining paths flip `m.state` back to `stateStreaming` well inside one 3s cadence — a queue drain or an auto-continue re-enters `submitTurn` from the same `turnDoneMsg` handler that just finalized the previous turn, so the superseded chain's next tick arrives to a streaming model, passes the gate and re-arms. Every tick now carries a `spinnerGen` stamp and the handler drops one that doesn't match, which terminates the superseded chain instead of doubling it. The generation is bumped where a new animation *begins* — `submitTurn` for a per-turn spinner, `applyStreamChunk`'s false→true `spinnerActive` flip for a LiveAgent stretch, which has no `submitTurn` to hang off — and all seven arming sites go through one `armSpinner()` helper so the stamp can't be forgotten at one of them. Deliberately a new per-turn counter rather than the existing `sessionGen`: that one only moves in `applySwitchTarget`, i.e. on a session switch, so the two overlapping turns *inside* one session that produce this bug would share a generation and the guard would be a no-op on the reported path. Same shape as the `resizeGen` stamp on `resizeReflowMsg` ([#104](https://github.com/go-steer/core-tui/issues/104)). No render path changed — the golden corpus is untouched.
- **The layout row budget is measured rather than guessed** ([#103](https://github.com/go-steer/core-tui/issues/103)). `resize()` sizes the chat viewport by subtracting the chrome around it from the terminal height, and three of its terms were wrong. The **header** was pinned at a literal `2 // status line + a blank row` while every sibling term called `lipgloss.Height` — but `renderHeader` word-wraps the status line, so on a 20-column terminal it occupies four rows and the frame came out a row taller than the terminal; the clipping post-pass from [#102](https://github.com/go-steer/core-tui/issues/102) then quietly ate the bottom of the footer, which is the row that tells a new operator how to quit. The **toast** had no term at all: `View()` slots the wake banner between the input box and the footer, so a visible toast pushed the frame over budget too, and only a spare row left over from an unexplained `- 2 // input top border + spacer` (there is no spacer) kept that from showing on a wide terminal. The **prompt-queue panel** was charged in the opposite direction — it is appended by `renderInProgress` into the viewport's *content*, not joined beside the viewport the way the footer, help panel and palette are, so subtracting it shrank the viewport by the panel's height and then spent that height drawing the panel inside the smaller viewport: a four-row queue cost the operator four rows of chat and left the frame four rows short of the terminal. Every term is now measured from the string `View()` will actually render, at the width it will render at, and only siblings of the viewport are charged. The composed frame is now exactly as tall as the terminal across the full width × height × layout matrix, so the height cap in `clipFrame` stops firing in normal use — which is what [#102](https://github.com/go-steer/core-tui/issues/102) said should happen once this landed. The new `tui/resize_budget_test.go` asserts that exactness directly, because the frame-invariant grid only checks that the frame does not *overflow* and is therefore satisfied by clipping.
- **The rendered frame is clamped to the terminal in both dimensions** ([#102](https://github.com/go-steer/core-tui/issues/102)). Nothing clamped it. Chrome is composed with `lipgloss.JoinVertical` / `JoinHorizontal` / `Place` and plain string concatenation, so overflow was possible at every join and nothing caught it at the end — the frame-invariant grid landing alongside this fix found 83 of its 200 cells overflowing, up to 82 columns of output in a 40-column terminal and 62 rows in a 24-row one. The height case was the nastier of the two, because Bubble Tea drops the **top** lines when a frame is too tall: the status header simply disappeared, with no indication anything had been cut. `View()` now ends with a clipping post-pass that truncates every line to the terminal width with `ansi.Truncate` — escape-aware, so an SGR sequence is never sliced in half the way byte-level cutting would — and caps the frame at the terminal's row count, keeping the *first* rows so the header is the part that survives. A frame that already fits comes back byte-identical; a not-yet-known geometry passes through untouched. This is a safety net, not a layout step: the row *budget* is [#103](https://github.com/go-steer/core-tui/issues/103), and once that lands the height cap should stop firing. It stays regardless — a compositor sizes its canvas to the union of its layer bounds, not to the terminal, so it would reproduce this same bug.
- **Dragging a terminal pane no longer freezes the UI** ([#104](https://github.com/go-steer/core-tui/issues/104)). A width-changing `tea.WindowSizeMsg` re-rendered *every* assistant message in the transcript through Glamour, synchronously, inside the message handler — and a pane drag emits a stream of those events, one per column crossed, so the cost was paid dozens of times over a single gesture while the UI sat unresponsive. The render memo made it worse: it pinned one width and dropped every entry the moment the width changed, so the re-assembly that followed the Glamour pass was fully cold too, on every event and again on the way back when the operator dragged the pane to a width already rendered at. The whole-history pass is now debounced behind a 120ms settle tick (generation-stamped, so a superseded drag's callback can never clobber a newer resize): a resize event reflows only the messages actually on screen — bounded by viewport height, not by session length — and the backlog warms after the drag stops, eight rows per tick rather than in one synchronous burst. Cache entries are keyed per `(message, width)` instead of behind a single width pin, so a row already rendered at the incoming width survives; rows off screen mid-drag are carried over from the previous width and retired by the warm pass before they can be scrolled into view. Measured with the repo's own `BenchmarkResizeWidthChange` (AMD EPYC 7B12), one width-changing event costs **3.63ms → 2.32ms** at 10 turns, **32.2ms → 3.97ms** at 100, and **126ms → 9.27ms** at 400 — and its allocation count, 47.3K / 463K / 1.84M before, is now 28.4K / 28.5K / 29.3K, i.e. flat in transcript length rather than linear in it. The `BenchmarkResizeHeightOnly` control (6.89ms → 6.84ms at 400 turns) and the steady-state repaint (`BenchmarkRefreshViewport`, 6.52ms → 6.60ms) are unmoved, so nothing was borrowed from the paths a resize is not on. Over a whole 30-event drag on richer turns (`tui/resize_drag_bench_test.go`, prose + list + fenced code): **8.48s → 0.72s** at 100 turns and **32.4s → 2.16s** at 400, with the deferred settle adding 0.30s and 1.19s respectively — 8.3x and 9.7x for the entire gesture. What remains per event is the transcript concat and `viewport.SetContent`, which are O(history) no matter what is on screen; removing those needs a windowed list, which this fix deliberately does not reach for. Follow state (#93) is untouched by any of it — a drag leaves an operator pinned to the tail pinned, and one reading scrollback where they were.
- **A permission prompt can no longer be answered by input the operator was already typing** ([#95](https://github.com/go-steer/core-tui/issues/95)). Permission requests arrive asynchronously and the modal was decision-live from the frame it appeared, so buffered keystrokes were consumed as the answer: typing `say` while prompts landed dispatched allow-session, allow-always and allow-once — three grants, one of them persistent, from a word aimed at the prompt. The six decision keys are now inert for 300ms after the modal appears, and keystrokes inside that window are routed to the prompt instead of being dropped. `esc` is exempt: it denies, which is the fail-safe direction. The elicitation modal gets the same window on the keys that dispatch a result (accept / decline / submit), while field editing and navigation stay live. New **R-PERM-8** / **R-ELIC-4** in `docs/requirements.md`.
- **Auto-follow survives a resize mid-stream** ([#93](https://github.com/go-steer/core-tui/issues/93)). Following the live tail was inferred from `viewport.AtBottom()` at repaint time, and the resize handler applied the new height *before* that sample — shrinking the terminal by a row (or typing enough to wrap the textarea onto a second line) made a pinned viewport report "not at bottom", so the re-pin was skipped and the rest of the turn streamed away below the visible region with no indication. Following is now tracked as explicit state on the model: scrolling up releases it, scrolling back to the bottom re-arms it, operator-initiated jumps (submit, slash output, session switch, `ctrl+l`) set it outright, and geometry changes leave it alone.
- **The elicitation form accepts non-ASCII input** ([#91](https://github.com/go-steer/core-tui/issues/91)). Two byte-vs-rune defects made the form ASCII-only: the append guard measured `len(stroke)` in bytes, so every printable character with a multi-byte encoding (`é`, `ü`, `日`, `😀`) was silently dropped — typing `café` yielded `caf` — and backspace sliced one *byte* off the value, leaving invalid UTF-8 in both the rendered frame and the `ElicitResult` handed to the host. Both sites are rune-aware now, and the append guard additionally rejects unprintable runes.
- **Truncated diffs no longer advertise a keybinding that doesn't exist** ([#94](https://github.com/go-steer/core-tui/issues/94)). The marker under a clipped diff read `… +N more lines · ctrl+o to expand (todo)`. `ctrl+o` is bound nowhere in the package, so the one key the transcript named was the one key that did nothing — and the note-to-self shipped to operators. The marker is now just `… +N more lines`. Row-level diff expansion needs a message cursor first; when it lands, the affordance comes back with a key behind it.
- **The scrollbar thumb no longer vanishes at the bottom of long content** ([#92](https://github.com/go-steer/core-tui/issues/92)). `Scrollbar` computed one more thumb position than it drew rows, so at maximum scroll the thumb landed one row past the end of the track: clipped short for a multi-row thumb, and gone entirely for the one-row thumb any content much longer than the viewport produces. The thumb now rests flush on the final row at maximum offset.
- **CRLF line endings no longer diff as "every line changed", and the per-line cap counts a tab as the four cells it renders as** ([#107](https://github.com/go-steer/core-tui/issues/107)). Nothing normalized line endings on the way into the diff. `computeUnifiedDiff` compared a CRLF file's contents against the model's LF replacement string, so `udiff` saw two strings that differ at the end of every line and produced a whole-file diff for a two-line edit — and each rendered row then carried its trailing `\r` **inside** the background-tinted `+` / `-` span, which is a cursor-to-column-0 with the tint still active: the row repaints over itself in the middle of the strip. CRLF is now collapsed at the three points where a payload becomes rows — the `strings.Split` in `renderDiffInline`, the one in `renderCodeInline`, and both sides of `computeUnifiedDiff` before `udiff.Unified` sees them. Normalizing before the equality short-circuit rather than after is what makes a CRLF file against a byte-identical LF string come back as **no diff at all** instead of a full rewrite. Deliberately **not** inside the per-line funnel: the `\r` sits at end-of-line and the cap can slice the body before ever reaching it. A **lone** `\r` is not a line ending and is not treated as one — it is a cursor control, and it is escaped like the rest of them. The tab half of the issue turned out to be already solved and worth **not** re-solving: lipgloss expands tabs at `tabWidthDefault = 4` on every styled path, which is why the golden corpus holds zero tab bytes despite tab-indented fixtures, so adding a second expansion at some other width would only have desynchronized the two. What was actually broken is the arithmetic. The per-line cap charged a tab one byte against a 200-byte budget while the terminal drew four cells, so a tab-indented line could render four times wider than the cap allowed and a 200-tab line — comfortably "under" the cap — was 800 columns of output. The budget is counted in cells now, with a tab costing `contentTabWidth`, and the cut lands on a rune boundary instead of mid-rune. Byte-for-byte golden-neutral on all 24 existing fixtures, which is the check that the tab decision went the right way: with tab exempt the pass is the identity function on clean ASCII, so any movement in the corpus would have been the signal that it had not.
- **Host capability methods no longer run on the Bubble Tea event loop** ([#114](https://github.com/go-steer/core-tui/issues/114)). `Update` and `View` share one goroutine, so anything slow inside either freezes the whole TUI — the spinner that is supposed to signal liveness, the cursor blink, and Ctrl+C, since those all arrive as messages the frozen loop cannot read. core-tui is a library: the capability interfaces are host-implemented, so it cannot assume any of them are fast, and roughly two dozen call sites were calling them inline. The worst were on bare keystrokes. `ModelSwapper.SwitchModel` ran on Enter in the model picker — a host that validates credentials or opens a connection there hung the UI for the whole round trip with no spinner and no way out. `AvailableModels()` and `SessionSwitcher.Sessions()` were re-pulled on *every keystroke* while their picker was open, and again from `Render`, i.e. from `View()`, which `host_snapshot.go` documents as provably never touching the host; the sidebar's `SubagentLister.Subagents()` was the third such violation. The `@` palette ran a full `filepath.WalkDir` on the `@` keypress, defaulting to the entire working directory when `PathScope` is unset, and `SlashProvider.SlashCommands()` ran on the `/` keypress. `Reloader.Reload` and `PricingController.Refresh` were the worst by contract: both take a `context.Context` — the host has been *told* it may be slow — and both were handed `context.Background()`, no deadline, no cancellation. Every one of those now returns a `tea.Cmd` following the four properties `host_snapshot.go` established (capability handle resolved before the closure, `sessionGen` captured at construction, no model state touched from the goroutine, nil Cmd when the capability is unwired), and the two ctx-taking methods get bounded contexts. The pickers pull their list **once when the dialog opens**, into a snapshot on the dialog that `Render` reads, and show a loading line while it is in flight; the `@` palette opens instantly and populates when the walk finishes. `modelSwitchedMsg` carries the generation stamp because `SwitchModel` replaces `Options.Agent`, so a reply that left under the previous session must not attach the outgoing session's agent to the incoming one — and replies route through `overlayStack.Get`, since an async reply for a dialog another modal has since covered still belongs to it. Remaining synchronous calls all sit behind an explicit `/cmd` rather than a bare keystroke (`ToolLister.Tools`, `PricingController.Set`, the `PermissionController` mutators, `SubagentLister.Subagents` from `/subagents`, and `/switch <id>`) and are tracked as a follow-up.

### Security

- **Untrusted tool output can no longer write escape sequences to the operator's terminal** ([#108](https://github.com/go-steer/core-tui/issues/108)). Tool args (the model writes them), tool responses, file content and bash stdout/stderr (the filesystem and the host write them), and tool error text (anything in the stack writes it) all reached the renderers unescaped. A file the agent was pointed at — a dependency's source, a fixture in a cloned repo, a log — could therefore emit control bytes straight at the terminal: `ESC[2J` to erase the display, `ESC]0;…` to retitle the window, cursor positioning to draw outside the row it was given, `CR` and `BS` to overwrite text that was already on screen, SGR to recolor everything after it. The last two are the interesting ones, because together they let content forge output — UI chrome, a permission prompt, a success line — that appears to come from `core-tui` itself. The escaping is one pass in one place. `sanitizeLine` (`tui/sanitize.go`) is the per-line funnel every renderer of untrusted content already routed through for length capping, so it was the natural home and needed no new call sites; `trimToolArg` is the second, rune-based funnel for arg hints and queue rows, where the caller supplies the width. Both run `ansi.Strip` from `github.com/charmbracelet/x/ansi` — no byte-level slicing — which removes CSI, OSC, DCS, SOS, PM and APC in both their 7-bit `ESC [` and 8-bit `0x9B` introducer forms, and then escape what `Strip` leaves behind to a visible `\xNN`: C0 (0x00–0x1F), DEL (0x7F), the C1 range `U+0080`–`U+009F` when it survives as a UTF-8 rune, and any byte that is not valid UTF-8. Stripping ANSI rather than escaping it is deliberate — SGR in captured build output is common and benign, and rendering it as visible litter would be worse than dropping it — and `\xNN` is chosen over the Control Pictures block because pure ASCII cannot itself need escaping. **TAB and LF are exempt**: LF is the line separator, and TAB is already expanded to four spaces by lipgloss before it reaches the terminal, so escaping it would have churned the chroma goldens to make tab-indented Go read as `\x09`. Escaping runs **before** the cap, not after, so the budget bounds what the terminal is actually asked to draw. Two paths that were not the funnel got folded in: `renderResultError` had rolled its own `errCap = 200` byte slice — the same number the shared cap already held, maintained twice and escaping nothing — and `renderDetailSection` turned out **not** to be safe behind `json.MarshalIndent` after all. The encoder escapes C0 and a short list of HTML-sensitive ASCII, but passes DEL and the entire C1 range through verbatim, and `U+009B` is the 8-bit CSI introducer that a UTF-8 terminal acts on; the marshaled body takes the same pass now. A table of hostile payloads drives every renderer, and nine new adversarial goldens under `tui/testdata/hostile_*` pin what a terminal receives when a tool hands the TUI something that is trying to draw on it. The goldens are paired with an assertion rather than trusted alone — a golden can only prove the bytes did not change, not that they are safe — so regenerating the corpus cannot quietly bless an escape sequence.

### Removed

- **The vestigial enum-driven overlay path** ([#90](https://github.com/go-steer/core-tui/pull/90), closing [#79](https://github.com/go-steer/core-tui/issues/79)). `Model` carried an unexported `overlay` enum (`overlayNone` / `overlayModelPicker`) left over from the visual-preview slice, along with the `modelPickerIdx` field, `renderOverlay`, the `case m.overlay != overlayNone` arm in `View`'s modal cascade, the matching `footerHint` case, and a second copy of the model-picker key handling in `Update`. A write-set analysis over `tui/*.go` **and** the test suite (`docs/api-audit.md` §4) found no assignment of any non-`overlayNone` value anywhere, so `m.overlay` was provably always `overlayNone` and every consumer of it was unreachable. Real picker state has lived in the `Dialog` stack since v0.1.0; `Ctrl+G` and `/model` both open `modelPickerDialog`. No exported symbol changed and **no host action is required** — this is dead-code removal ahead of the v1.0 freeze, so the paths don't become permanent maintenance obligations.

The `usageMsg` bullet on that issue was a **false positive and nothing changed for it**: `usageMsg` is not legacy, it is still fed from `Event.Usage` / `Event.Model` in `tui/agentcmd.go`, and `turnSummaryMsg` is an additional push-mode path (v0.9.0), not a replacement. Deleting it would have broken per-turn usage rendering for every pull-mode host.

## [0.19.0] — 2026-08-14

A bug-fix release with one small piece of new plug-in surface: modal windows scroll now.

### Fixed

- **Every modal scrolls** ([#75](https://github.com/go-steer/core-tui/pull/75)). A modal body taller than the terminal was clipped, and the mouse wheel never reached a modal at all — `tea.MouseWheelMsg` fell through `Update` to the chat viewport *behind* the overlay, so the wheel scrolled something the operator couldn't see. Every modal surface now scrolls with `↑`/`↓`, `PgUp`/`PgDn`, `Home`/`End` and the wheel: the `/btw` side answer, the permission overlay, the elicitation form, the tool-call and subagent detail overlays, and the theme / model / session pickers. A body that overflows grows a scrollbar column and an `↑↓ scroll` footer hint; one that fits shows neither. Four deliberate refinements: the **inline** permission layout keeps handing the wheel to the chat (that *is* the surface showing the prompt — only the centered `PermissionOverlay` layout captures it); **pickers move one row per wheel tick**, not the three-row wheel step, because a nudge that jumps three models past the one you wanted is worse than no wheel at all; the elicitation form **follows focus only when focus moves**, so scrolling away to read something else isn't yanked back on the next repaint; and the subagent log keeps its follow-the-tail pin, with wheel-up releasing it exactly as `↑` does and `End` re-pinning. No bare `j`/`k` bindings anywhere — those belong to the field being typed into.
- Two latent bugs fell out of the same work. `PgDn` had **never** worked in the tool-call or subagent overlays — bubbletea renders `KeyPgDown` as `"pgdown"`, not the `"pgdn"` they matched on. And `/btw` rendered at roughly double height, because it wrapped its markdown to the ~100-column chat viewport and then rendered that into a 72-column modal frame, re-wrapping every line.

### Added

## [0.17.0] — 2026-08-11

Hang-proof TUI event loop. Attach-mode `core-agent-tui` could wedge after sitting idle — no typing, dead Ctrl+C, and a `kill -QUIT` left the terminal garbled. Root cause: bubbletea runs Update and View on a single event-loop goroutine, so anything that blocks there freezes the whole TUI, and SIGINT/SIGTERM only arrive as messages the frozen loop can't read.

### Changed

- ⚠️ **`StatusReporter` / `UsageTracker` implementations must now be safe for concurrent, non-blocking reads.** The TUI pulls them off its event loop.
- **Non-blocking `View()`** ([#69](https://github.com/go-steer/core-tui/pull/69)). The status-header helpers (`displayModelName`, `displayProvider`, `usageSummaryOneLine`/`Stacked`) called the host's `StatusReporter`/`UsageTracker` on every paint, so a slow or wedged host froze the loop. They now read a `hostSnapshot` cache refreshed **off** the event loop via a self-perpetuating, generation-guarded cycle (kicked in `Init`, re-armed on a tick, restarted in `applySwitchTarget`). Push-mode overlays (`currentModel`/`pushedProvider`) still win where fresher, and `AutoProviderTheme` re-resolves when the cached provider changes. Precedence is otherwise unchanged; the only new behavior is a brief placeholder in the pre-first-refresh window — correct when the host is exactly the slow case this fixes.

### Added

- **SIGQUIT (`Ctrl-\`) wedge-recovery hatch.** A dedicated signal goroutine, independent of the event loop, dumps every goroutine's stack, restores the terminal (termios + ANSI resets for alt-screen, cursor, bracketed paste, mouse, SGR), and exits `128+SIGQUIT`. This replaces the Go runtime's default SIGQUIT handler, which dumps and then exits **without** restoring the TTY. No-op when stdin isn't a terminal; Windows gets a stub via build tags. Net effect: `Ctrl-\` is a reliable "unwedge and hand my shell back" key.

### Security

- `golang.org/x/text` v0.24.0 → v0.39.0 ([GO-2026-5970](https://pkg.go.dev/vuln/GO-2026-5970)).

### Docs

- SSE event-stream protocol **v1.4.0** ([#68](https://github.com/go-steer/core-tui/pull/68)) — `capabilities.{features, slash_commands, agent, caller_id}`, status-update merge semantics, and slash-response conventions.

## [0.16.1] — 2026-07-18

### Fixed

- **Fast attach to long remote sessions** ([#67](https://github.com/go-steer/core-tui/pull/67)). Attaching to a remote session with a long history rendered oldest-to-newest and took many seconds before the tail was visible. The bottleneck was per-event `refreshViewport`: each incoming SSE event walked the whole history, concatenated every rendered message, and called `viewport.SetContent` on the ever-growing buffer — O(N) per event, **O(N²)** over catch-up, even at a 100% `listCache` hit rate. Event-driven refreshes are now coalesced: handlers flip a dirty flag instead of refreshing synchronously, and a single ~1 ms `tea.Tick` fires one `refreshViewport` for every event that landed in the window. State mutation stays synchronous (the `sessionGen` stale-drop guards continue to hold) — only the paint is deferred. Total work over an N-event catch-up drops to **O(N × batch-size)**. Applies to `streamChunkMsg`, `toolCallMsg`, `toolResultMsg`, `usageMsg`, `statusUpdateMsg`, `usageUpdateMsg`, `inboxStateMsg`, `turnSummaryMsg`, `spinnerTickMsg`, `liveStreamStartedMsg`, `liveStreamErrMsg`, and `liveStreamEndedMsg`; user-input paths and dialog handlers keep refreshing immediately.
- `WindowSizeMsg` short-circuits when the dimensions haven't changed (bubbletea can emit initial + terminal-negotiated sizes back-to-back), and skips `rerenderHistoryMarkdown` on height-only resizes since Glamour wrapping is width-pinned.

The per-turn full-text Glamour render on commit remains a smaller constant (~10 ms × M turns) and was left for a later release.

- **`examples/notifier-smoke/`** — a standalone binary exercising the full `Notifier` contract: a producer goroutine pushing one realistic notice every ~7 s from a 10-item rotation, plus a 25-notice burst every ~50 s to demonstrate the `(+N dropped)` coalescence marker.

### Docs

- **SSE event-stream wire protocol v1.0.0** ([#41](https://github.com/go-steer/core-tui/pull/41)) — `docs/sse-event-stream-protocol.md` ships as a **specification only**, no client subscriber yet, so core-agent's server-side work could target a stable contract while the consumer side was built. Six event types: `capabilities` (handshake), `status-update`, `usage-update` (with per-model breakdown), `inbox` (queued/dequeued), `turn-complete` (per-turn cost), `turn-error` (structured error). SemVer evolution rules: additive is MINOR/PATCH; rename / remove / retype is MAJOR.

### Upgrading

- `RoleNotice` was added to the `Role` enum. Downstream code that switches on `Role` exhaustively should add a case — most renderers already have a default branch.

## [0.7.0] — 2026-06-06

First release with formal release notes.

### Added

- **`/theme` picker with live preview on cursor** — `↑`/`↓` applies the focused theme so you can see the palette without committing, `enter` commits, `esc` restores the original. `/theme <name>` switches directly without opening the picker (unknown names fall back to `default` with a recoverable system message and skip persistence); `/themes` is an alias.
- **Eight new themes** alongside the original four (`default`, `anthropic`, `gemini`, `openai`): `google`, `gke`, `gopher`, `matrix`, `pride`, `cyberpunk`, `vaporwave`, `christmas`. Signatures rather than palette transcriptions — `google`'s wordmark cycles B-R-Y-B-G-R in logo letter order, `gke`'s cycles the icon's clockwise quadrants and its textarea prompt is `⎈` (Unicode HELM SYMBOL), `gopher` fades Gopher Blue → Aqua from the Go brand book, `pride` cycles the flag over calm violet chrome so it reads as a signature rather than an assault.
- Two reusable mechanisms behind those themes, available to any future one: **multicolor wordmarks** via `Theme.WordmarkSequence []color.Color` (nil keeps the existing single-color path) and **themed textarea prompt glyphs** via `Theme.PromptGlyph` (empty keeps the house default `▎ `, exported as `DefaultPromptGlyph`).
- Host surface: `Options.InitialThemeName` (case-insensitive; unknown names fall back to `DefaultTheme`), `Options.PersistThemeChoice func(string) error` (mirrors `PersistModelChoice`), `ThemeChangedMsg{Name string}` for hosts with custom `Update` wrappers, `BuiltinThemes() []BuiltinTheme` for hosts building their own picker, and `ThemeByName(name, dark) Theme`. Minimum integration to get the picker is **zero lines**; persisting across restarts is two.

### Changed

- ⚠️ **`Overlay.HandleKey`'s signature changed** from `(consumed bool)` to `(consumed bool, cmd tea.Cmd)` so dialogs can emit msgs. `Overlay` is exported but is internal modal plumbing; if you call it directly, append a `_` to ignore the new return.
- `Options.Branding.AccentColor` still overrides whichever theme is active — same precedence as before.

## [0.1.0] — 2026-05-26

Initial release: `package tui` extracted from the duplicated `internal/tui` trees in [`go-steer/cogo`](https://github.com/go-steer/cogo) and [`go-steer/core-agent`](https://github.com/go-steer/core-agent), generalized so neither host is favored.

### Added

- **The plug-in surface** — the `Agent` interface and `Event` type, the §3.3 optional capability interfaces, `Options`, and the TUI-implemented `PermissionPrompter` / `Elicitor` pair. Capabilities are feature-detected by type assertion, and a missing one degrades to a "not available in this host" message rather than an error.
- **The chat loop** — streaming assistant tokens rendered incrementally through Glamour, inline tool-call rows, the per-turn footer, prompt history, `/clear` with confirmation, transcript save/`/resume`, and the `Esc`-interrupts-turn / `Ctrl+C`-quits split.
- **Prompt queueing during streaming** (R-CHAT-10) with the four-state queue panel, plus `InjectableAgent` + `MidTurnInjectionMode` (R-CHAT-11), `WakeRequester` + its toast banner (R-WAKE-1), `ContentRunner` + the `Content` type (R-CHAT-12), and `SlashResult.ModalAnswer` + the side-answer modal (R-CMD-5).
- **Live `/` and `@` palettes** (R-PAL-1/2), a real model picker and file palette, real `/mcp` `/tools` `/skills`, `/stats` with cost, `/allow` and `/deny`, `Options.PersistModelChoice` (R-MOD-3), the status header/sidebar with a persisted layout choice, the bottom-anchored help panel on `?`, and the 3-tier color context indicator.
- **Performance and terminal-fidelity work** — incremental Glamour streaming, an auto-growing textarea, hanging-indent word wrap that preserves source leading whitespace, and the viewport's `h`/`j`/`k`/`l`/arrow bindings disabled with `xOffset` pinned to 0 so a wide line can't shift the whole chat sideways.
- **The docs that govern all of it** — `docs/requirements.md`, `docs/design.md`, `docs/decisions.md`, `docs/style.md`, `docs/ui-references.md`, and `MIGRATION.md`.
