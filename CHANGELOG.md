# Changelog

All notable changes to `core-tui` are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Stability promise

The public API of `core-tui` is the exported surface of `github.com/go-steer/core-tui/tui`, and within it the plug-in surface [`docs/design.md`](./docs/design.md) §3 describes — as shipped today:

- the `Agent` interface and the `Event` type it streams,
- the optional capability interfaces a host may implement (`ModelSwapper`, `Reloader`, `PermissionController`, `PricingController`, `ToolLister`, `SubagentLister`, `SubagentEventReader`, `SessionSwitcher`, `RemoteInterrupter`, `StatusReporter`, `SlashProvider`, `LiveAgent`, `InjectableAgent`, …),
- the `Options` struct's field names, and
- the TUI-implemented `PermissionPrompter` / `Elicitor` pair.

Adding a field to `Options` is non-breaking by Go-module rules — the documented usage is a struct literal with explicit field names — so hosts should keep writing it that way.

Everything else exported from `tui` (render helpers, `Overlay` and the `Dialog` stack, `History`, `Styles`, `Theme` internals) is **not** covered by that promise pre-1.0, even though it is exported. Reducing that gap is [the v1.0 milestone's](https://github.com/go-steer/core-tui/milestone/1) exported-surface audit.

`tui/testagent` is a test fixture. It moves with the library and promises nothing.

Pre-1.0, breaking changes are possible at any minor version (`v0.X`). When we make one it is called out in this file under **Changed** or **Removed**, with the upgrade action spelled out. Patch versions (`v0.X.Y`) are bug fixes only.

The wire protocol in [`docs/sse-event-stream-protocol.md`](./docs/sse-event-stream-protocol.md) versions independently of the library; its own version is noted in the release that changes it.

## [0.20.0] — 2026-08-17

The transcript stops being a thing you scroll and becomes a thing you drive. `tab` hands it the keyboard, a cursor selects one item at a time, `space` folds the one you are on, `y` / `c` copy it, and `shift+←` / `shift+→` pan across the content that does not wrap — a table, a diff, a stack trace. Under all of it the render path is addressed by item instead of by one concatenated blob, which is what makes item-at-a-time navigation affordable at session length rather than an O(session) walk per keystroke.

The other half of the release is the quality backlog that had been queued behind a rendering-architecture spike and did not need to wait for it: the frame is measured and clipped to the terminal in both dimensions, modals fit a short window, the pickers filter and open on the right row, markdown and syntax highlighting follow the active theme, every remaining host call is off the event loop, and untrusted tool output can no longer write escape sequences to the operator's terminal.

### Added

- **`Options.ClipboardWriter`, and a copy notice that stops claiming what it cannot observe** ([#175](https://github.com/go-steer/core-tui/issues/175)). [#153](https://github.com/go-steer/core-tui/issues/153) shipped `y` / `c` over OSC 52, which is the right default — it is the only mechanism that reaches the clipboard of the machine the operator is *sitting at* rather than the one the process runs on, and that is the whole LiveAgent-over-SSH case. What it did not reckon with is how many terminals decline the escape: Terminal.app has never implemented it, iTerm2 keeps it behind a preference that is off by default, and several remote and web terminals strip it in the relay. On those the key did nothing at all, and since the protocol has no acknowledgement, the footer said `copied 24 lines` regardless. Claiming a result we cannot observe was the worse half of the defect, because it sends the operator looking for the bug in the wrong place.

  So there are now two writes and one honest sentence about them. `Options.ClipboardWriter func(text string) error` is host code called **in addition to** the escape, never instead of it — the two target different machines, so neither is a fallback for the other, and a host that is local wants both. `tui.SystemClipboardWriter()` supplies one out of `os/exec` (`pbcopy`, `wl-copy`, `xclip`, `xsel`, `clip.exe`) so a desktop host needs one line and no dependency; core-tui deliberately takes no clipboard library of its own, because a library that did would put windowing-system bindings in every host's module graph whether or not that host ever copies anything. It resolves a helper once, at construction, and returns **nil** when there is none — including on a Unix box with no display, where xclip is often installed and has no X server to reach. That nil is load-bearing rather than a failure: it is indistinguishable from leaving the field unset, so hosts assign it unconditionally, and a machine that was never going to have a clipboard does not report a failure per keystroke.

  The notice is the part an operator actually sees. It now names the mechanism — `copied 24 lines · osc52` — for as long as the escape is the only write, and drops the qualifier only when a host writer comes back clean, which is the one case where a copy has been confirmed rather than merely attempted. A host writer that fails says `· osc52 only` and quotes the error, capped so it cannot push the rest of the legend off the line. Deliberately *not* a `RoleError` row, which is how the other host callbacks report failure: a row appends to the transcript and scrolls it, and this key is pressed by an operator parked on a selection they are reading. The reply carries the notice's own generation (`Model.copyGen`, bumped wherever the notice is set, replaced or cleared) rather than the session's, because a notice turns over many times inside one session and a verdict that arrives after the operator has moved on has lost the right to speak — though not, of course, the right to have happened. The help panel says the terminal has to allow clipboard writes, which is the sentence that would have saved the trip through this paragraph.

- **`shift+←` / `shift+→` pan the transcript sideways over content that does not wrap** ([#154](https://github.com/go-steer/core-tui/issues/154)). Most of a transcript wraps, and wrapped text needs no panning — but the things an agent produces most of do not wrap: a table, a unified diff, a stack trace, one very long line of tool output. Those were cut at the right edge and the rest was simply gone. No scrollbar, no ellipsis, no key, no indication that anything had been removed. The reason it was gone is that it was never kept: rows were truncated to the viewport width on their way **into** the render cache, so by the time anything could have panned, the columns to pan to had already been thrown away. The cut now happens at the last possible moment — in the view walk, per drawn line — and the cache holds rows at their natural width. That is a strictly *stronger* version of the same contract rather than a weaker one: "no line reaches the frame wider than the window" used to hold for cached rows and had to be re-applied by hand to everything that was not one (the live tail, [#152](https://github.com/go-steer/core-tui/issues/152)'s fold summary), and now it holds for every line the frame contains, because there is exactly one place a line can reach the frame from. Nothing about heights changes — cutting a line does not split it, which is why the lazy walk's line budget ([#161](https://github.com/go-steer/core-tui/issues/161)) is untouched — and the unpanned case still cuts with `ansi.Truncate` rather than a zero-origin `ansi.Cut`, so an unpanned frame is byte-identical to what it was before this existed and the golden corpus does not move.

  Panning is **not** the old viewport's `xOffset`, which is what makes this worth describing at all. The predecessor of this change was a one-line patch that unpinned that field, and it produced corrupted output: `xOffset` made `ansi.Cut` remove cells from the **left** of every line and keep the window's width from there, so the text slid left and the right edge stayed exactly where it was. #161 deleted that viewport; this cuts the window `[x, x+width)` out of a line that is still full width, which is the operation the name implies, and it goes through `ansi.Cut` rather than a byte slice so the SGR sequences opened before the cut survive it — a diff's colour lives in escapes that are off-screen to the left. The step is **8 cells**: one column at a time is forty presses to reach a table's second column, a full window at a time throws away the overlap the eye needs to carry a row across the jump, and a fixed number rather than a fraction of the width means a pan lands in the same place on a narrow terminal as on a wide one. The right-hand limit is the widest line **in the window**, less the window — measured over the window rather than the transcript, which is the rule the whole item-addressed path lives by, and an over-estimate only for a partly scrolled row whose off-screen lines are measured too. That is the harmless direction: the operator can pan to a blank column and press the other arrow, which is not true of a limit that stops short of real content.

  The offset **resets on purpose**, and what resets it is the point. Moving the cursor drops it, because a pan is a way of reading one wide thing and carrying it to the next item would leave the operator looking at column 40 of a paragraph — which reads as a broken frame, not a scrolled one. Leaving focus mode drops it, since nothing in the composer's keymap could bring it back. A width-changing resize drops it, because the limit it was clamped against no longer exists. Line scrolling deliberately does **not** — reading a forty-row table a row at a time while panned is the case this exists for — and neither does a height-only resize, which would otherwise make a mouse drag's stream of same-width events unusable. The selection gutter does not pan either: the marker says which item the cursor is on, so it is frame furniture and stays at the left edge however far the text under it has slid. And because a pan is invisible in a frame with no left edge to compare against, the focus legend carries `panned 8 cols` alongside `shift+←→ pan` for as long as the offset is non-zero.
- **`y` copies the selected transcript item, `c` copies just the code in it** ([#153](https://github.com/go-steer/core-tui/issues/153)). The only way to get text out was the terminal's own mouse selection, which selects what is on the *screen*: the tool glyphs, the box rules, the selection gutter ([#152](https://github.com/go-steer/core-tui/issues/152)), the soft line breaks word wrap inserted, and every ANSI escape in between. Paste that into an editor and it is not the text the operator pointed at — a wrapped command comes back with a newline in the middle of it, which is the failure mode that turns a copy into a bug report. So this path never reads the frame. It reads the history entry under the cursor and reconstructs what the renderer was **given**: the markdown source of an assistant turn, the prompt as it was typed, and — for a tool row, which has no `Text` at all — the name, the structured args and the structured response, through the same `json.MarshalIndent` the detail overlay uses, which brings [#108](https://github.com/go-steer/core-tui/issues/108)'s escaping with it. One consequence worth stating: the copy does not depend on the width the terminal happened to be, so the same keystroke gives the same bytes at 60 columns and at 200. The single rendered fallback is a tool row whose host reported neither a response nor an error — the pre-rendered preview is all that exists for it, and it is stripped of ANSI on the way out. `RawRenderable` (the optional `Item` hook that has been sitting in `listcache.go` since the lazy list landed) is what carries this, so a future non-`Message` row type opts into copy by implementing one method.

  `c` is the narrower half: every fenced block in the item, joined by a blank line, fences and info strings excluded. Every block rather than the first or the biggest, because a turn that answers with a config file *and* the command that reads it means both, and picking one would be guessing — a second cursor for choosing between them is a whole navigation model for a case that is usually "there is exactly one". When the item has no code at all `c` copies **nothing** and says so, rather than falling back to the whole item: a key that copies something else when it cannot do what it says is worse than one that declines, because the clipboard is not inspectable from the TUI and the operator finds out on paste. The scanner is a small one — open fence, close fence, an unterminated fence still yields a block because the turn may still be streaming — and deliberately not `markdown.go`'s `insideOpenCodeFence`, which answers "does this prefix end inside a fence" by counting backticks and is documented as approximate because the cost of being wrong *there* is one extra re-render.

  The write goes out as **OSC 52** (`tea.SetClipboard`), which puts the text on the clipboard of the machine the operator is sitting at rather than the one the process runs on — which matters more here than in most TUIs, since a LiveAgent host is routinely on the far side of an SSH connection and a native clipboard call would have copied to the wrong computer. The caveat is that terminals cap the escape they will accept (8KB in some, 100KB in others; a few refuse it outright) and the protocol has no acknowledgement to detect that with, so a very long item can be reported copied here and dropped there. Truncating to the smallest known cap would silently corrupt the common case to protect the rare one, so this sends the whole thing and reports how much it sent. That report is the other half of the feature: a copy leaves the frame exactly as it found it, so the focus legend carries `copied 24 lines` / `copied 2 code blocks, 6 lines` / `no code block in this item` until the next transcript keystroke. No timer, no toast — a tick would need a generation stamp to keep two copies from fighting and a repaint nobody asked for, and "it says so until you do the next thing" can never be describing the wrong copy.
- **A cursor over transcript items, and `space` to fold the selected one** ([#152](https://github.com/go-steer/core-tui/issues/152)). Every item rendered at full height, so one 300-line tool result or one long assistant answer buried the rest of the scrollback and the only way past it was to scroll — which is the wrong instrument, because scrolling moves the window and what the operator wants is to make the item small and leave everything else where it is. The transcript now carries a **selection cursor**: while it holds the keyboard ([#151](https://github.com/go-steer/core-tui/issues/151)) a dotted `┊` bar runs down the left edge of the selected item for its whole height, rule and blank line included, so "which block am I on" is answered by looking rather than by pressing a key to find out. The glyph is dotted on purpose — `GlyphColumn` is already a solid bar and reads as structure; a cursor has to read as *transient*, and the dotted stem is the one that does not look like part of the layout. `space` folds the selected item to its first three lines plus a muted `▸ N more lines`, and folds it back. Items of four lines or fewer are left alone: a fold that saves nothing still costs a keystroke to undo, and having `space` do visible nothing on a short row is better than having it produce a summary longer than what it replaced.

  Two decisions are the whole implementation. **The gutter is reserved on every row, not borrowed under the cursor.** The tempting version draws the bar only where the cursor is and gives the two columns back everywhere else — and it is wrong, because an item's wrap width would then depend on where the cursor is, so every press of `↓` re-wraps two items, evicts their cache entries and shifts the text of both under the operator's eyes while they are trying to read it. The cursor has to be free; the price is two columns of transcript width, charged once, and eleven golden files that shift right by two. **A fold is a view of the cached render, not a second render.** Folding slices the lines the memo already holds rather than re-running `renderMessage` with a "collapsed" flag, so the cache key does not grow a dimension, folding and unfolding render nothing at all, and a folded item that later streams more content picks the new lines up through the ordinary version bump.

  This is where [#161](https://github.com/go-steer/core-tui/issues/161) pays for itself. A fold changes an item's height, and under the flat line offset the viewport used to keep, changing the height of anything above the window moved the window: fold something twenty rows back and the text the operator was reading jumps. With the position held as `(row, line)` the top of the window is *line n of item i*, which does not know or care what the items above it measure, so a fold anywhere outside the window is byte-for-byte invisible — pinned by a test that folds above the window and compares the whole frame. Inside the window the window stays put unless it has to move, and if the transcript is following the stream the tail stays pinned to the bottom as it shrinks. Revealing the cursor is bounded in both directions — it walks from the current top or from the end, never over the session — so the cursor cannot reintroduce the O(session) the item-addressed list just removed.

  The keymap shifts to make room. With the transcript focused, `↑`/`↓` and `k`/`j` now move the cursor **an item at a time** rather than a line, `shift+↑`/`shift+↓` scroll a line inside a long one, and `g`/`home` and `G`/`end` jump to the first and last item (`G` still re-arms following the stream). Item-at-a-time is the right default because the item is what the operator is looking for and a line is not; line scrolling is what you reach for once you have found the item, which is exactly when a modifier is cheap. The focus legend moves with the keys — `↑↓ select` and `space fold` take the two slots that `↑↓ scroll` and `pgup/pgdn page` had, because the legend exists precisely so the mode does not have to be probed by pressing something, and paging is the one binding nobody guesses wrong. Selection state is deliberately **not** a render input while the composer holds the keyboard — the marker is drawn by the list, not by the item, so an unfocused transcript renders precisely what it rendered before. Taking focus seeds the cursor on the item it was already on if that is still on screen, and otherwise on the last visible one, so entering focus mode scrolls nothing. Folds are keyed by message ID and survive scrolling, resize and re-theming; they are dropped on `/clear`, a session switch and a resume, and cannot be misapplied across any of those because `History.Reset` does not rewind the ID counter.
- **The transcript can take the keyboard from the composer, and the arrow keys scroll it** ([#151](https://github.com/go-steer/core-tui/issues/151) / [#155](https://github.com/go-steer/core-tui/issues/155)). Every keystroke the modal cascade did not claim was forwarded to *both* the textarea and the chat viewport, so the transcript could only be driven by keys nobody would ever type into a prompt. That is why `NewModel` strips the viewport's KeyMap to four non-letter chords — the vim defaults would have made `b` page up and space page down mid-sentence — why the arrows belong to prompt-history recall, and why `Right` is unusable at all (it sets `xOffset`, after which `ansi.Cut` eats characters off the **left** of every line). One constraint, four blocked affordances: line scrolling, select-and-expand ([#152](https://github.com/go-steer/core-tui/issues/152)), copy ([#153](https://github.com/go-steer/core-tui/issues/153)) and horizontal scroll ([#154](https://github.com/go-steer/core-tui/issues/154)), each of which would otherwise have had to invent its own chord. **`tab` now moves the keyboard between the composer and the transcript**, and while the transcript holds it the letter and arrow space is free in one move: `↑`/`↓` and `k`/`j` scroll a line, `home`/`g` and `end`/`G` jump to either end, and `G` re-arms following the stream — the same contract `ctrl+l` and `end` already had from the composer side, and read back off `AtBottom()` by the existing `syncFollow` rather than asserted per key. `tab` is the one navigation key bubbles' textarea does not claim, so taking it costs the composer nothing; with exactly two regions forward and backward are the same move, which is why it carries this alone and `shift+tab` keeps the permission-mode chip. Three things are deliberately **not** bound: `pgup` / `pgdn`, which already page from either focus because unclaimed keys still reach the viewport and a second paging implementation would be one more thing to keep in step with the first; `space`, held for #152; and the viewport's `ctrl+d` / `ctrl+u` half-page pair, because `ctrl+d` quits unconditionally and a half-page keymap with one working half is worse than none. Keys the transcript declines **fall through** to the global switch, so `ctrl+b`, `ctrl+g`, `ctrl+x`, `ctrl+l`, `shift+tab` and `?` all still fire — those belong to the frame, not to the composer, and having to leave the mode to reach them would defeat it. (`?`'s empty-input guard exists to protect typing, so it lapses here, where there is no typing to protect.) There are three ways back — `tab`, `enter`, and `esc`, which enters the cascade below every open surface and above the two cancel arms, so interrupting a turn from focus mode costs a second press; `enter` deliberately does not also submit, because the caret is invisible from here and firing a half-written prompt is not undoable. A mode that swallows typing has to be visible without pressing a key to find out, so it carries **three signals**: the footer legend names it (placed above the streaming arm, since reading back through a live turn is the case the mode exists for), the composer's top border drops from the active border token to the quiet one — the theme's own vocabulary, so it needs no new style field and follows all twelve palettes — and the hardware cursor goes away with the textarea's focus, since `textareaCursor` returns nil for a blurred widget. Blurring is load-bearing rather than cosmetic: bubbles drops every message a blurred textarea gets, which is what keeps stray letters out of a prompt nobody is looking at, and it is also why a bracketed paste — which never goes through `handleKey` — takes the keyboard back before landing, rather than vanishing silently. A turn ending no longer re-arms the textarea unconditionally: that would yank focus out of a transcript the operator deliberately moved it to. A session switch does reset the mode, because the transcript they focused is gone. Golden-neutral except for the two help frames, which gain the new `Transcript focus` section (and one more page at 60 columns); the input border's other state is unreachable from a corpus captured at rest.
- **Markdown and syntax highlighting follow the active theme** ([#116](https://github.com/go-steer/core-tui/issues/116)). Switching themes repainted the chrome and left the majority of the pixels on screen untouched, so the surface read as two unrelated designs: `tui/syntax_cache.go` pinned inline highlighting to a package-level `styles.Get("github")` fixed at init, and `newMarkdownRenderer` built its Glamour config from a `dark bool`, collapsing all twelve themes into exactly two markdown styles whose only theme-adjacent patch was five hardcoded 256-color heading indices. Pick Matrix or Christmas and the headings stayed Glamour-blue, the code fences stayed GitHub-gray, and only the frame around them moved — on the largest surface the operator looks at. `tuiStyleConfig` now takes the `Theme`: body prose is `FgBase` instead of Glamour's `252`, H1 reverses `OnPrimary` out of a `Primary` fill, H2–H6 walk a derived `Accent`→`FgMuted` ramp, and rules / links / list bullets / block quotes / inline code take `BorderQuiet` / `Secondary` / `Accent` / `FgMuted` / `BgElevated`. Two additive `Theme` fields carry it: `OnPrimary` (the foreground for text painted on a `Primary` fill — `Primary` alone cannot answer "what is legible on top of this?") and `ChromaStyleName` (the Chroma style, now shared by Glamour fences *and* the inline diff / tool-preview highlighter, which previously painted from two unrelated palettes). Both are **derived, not required**: `NewStylesWithTheme` normalizes every `Theme` on its way to a `Styles`, filling a nil `OnPrimary` from a WCAG luminance check on `Primary` and an empty `ChromaStyleName` with `github`, so the twelve builtins, the golden corpus's bare `Theme{…}` literal and any host-constructed theme all keep working untouched — and because both `Branding` override sites mutate `Primary` and *then* call `NewStylesWithTheme`, an accent override re-derives its own contrast foreground for free. The builtins each name a Chroma style in both polarities (Dracula for the house palette it is named after, gruvbox for Anthropic clay, tokyonight for Gemini, swapoff for Matrix's phosphor, rrt's red/green/gold for Christmas, …). Heading tiers are computed from the two endpoints rather than added as five more tokens — `Theme` is being narrowed for v1.0, not grown.
- **Type-to-filter in the model, session and theme pickers** ([#117](https://github.com/go-steer/core-tui/issues/117)). Typing a letter into any of the three did nothing at all: each `HandleKey` was a four-case switch over ↑ / ↓ / Enter / Esc with a catch-all that consumed everything else so it could not leak into the chat textarea behind the modal. On a host advertising forty models, or a project with a hundred saved sessions, the arrow keys were the whole navigation story. All three now carry a one-line filter input as the first row of their body, with a `matched/total` count beside it and the matched span picked out on each row. The ranking is the slash palette's, lifted out of `palette.filtered` into a shared `rankNames` helper so the two surfaces cannot drift: case-insensitive, four tiers — exact basename, basename prefix, whole path segment, substring anywhere — tiebroken by shorter name. No new dependency; see [decisions.md D27](./docs/decisions.md) for why not `sahilm/fuzzy`, and note the consequence — matching is on contiguous substrings, so a highlight is one span and `mgo` does not find `main.go`. Model and session rows match on their display name *and* their ID, since both are printed on the row. Input arrives as real `tea.KeyPressMsg` values through `KeyMsgDialog`, so `Key.Text` and bracketed pastes reach the filter, and each picker implements `DialogCursor` so the filter row owns the terminal caret — without it `modalCursor` would answer `(nil, true)` and the surface people type CJK into would have no IME anchor ([#105](https://github.com/go-steer/core-tui/issues/105) / [#123](https://github.com/go-steer/core-tui/issues/123)). A filter that matches nothing keeps the picker open with the row still editable; a host that advertises an empty list still reports that in the chat and closes, as before. The filter row's cost is one body row, paid for by passing `modalChromeRows+1` at the three picker call sites rather than by changing a constant four other modals share. The three dialogs had no test files of their own; they do now, covering the shrinking-list cursor clamp that used to be `(idx ± 1 + len) % len`, and the theme picker is in the frame-invariant grid.
- **A frame-invariant test harness, a golden corpus, and committed render benchmarks** ([#101](https://github.com/go-steer/core-tui/issues/101)). `package tui` carried 202 `strings.Contains` assertions and exactly five tests that called `View()` at all — a combination that proves a token is present *somewhere* in the output and says nothing about where it landed or how wide it is, which is precisely the defect class the layout work ahead is about. Three pieces close the gap. A **frame-invariant grid** drives a real `Model` across widths 40 / 80 / 100 / 120 / 200 × heights 4 / 10 / 24 / 50, in both `StatusHeader` and `StatusSidebar`, with the base chat, a seeded transcript, the permission overlay, the elicitation modal and the help panel open — 200 cells, each asserting `ansi.StringWidth(line) <= width` for every line and a total line count `<= height` — plus a resize-sequence variant that walks one model through seven successive `WindowSizeMsg`s, so cache- and geometry-carried state is exercised too. A **golden corpus** under `tui/testdata/` pins the composed frame at three widths and the seven `Model`-free renderers (`renderToolPreview`, `renderToolPreviewWithResult`, `renderToolDetail`, `renderDiffInline`, `renderCodeInline`, `renderLatencyBadge`, `renderReadPreview`) byte for byte, ANSI escapes included; `go test ./tui -update` regenerates it. Every golden renders through one explicit `Theme` literal owned by the test file and a fixed named chroma style — never `m.styles`, never the background-detected theme — so a later palette change churns zero files, and `.gitattributes` marks `*.golden -diff` so escape-heavy fixtures don't drown a review. **Benchmarks** cover `refreshViewport` (warm and cold cache), a width-changing `WindowSizeMsg` and its height-only control, and `View()` end to end, each swept over 10 / 100 / 400-turn transcripts; the width-change / height-only pair is the measurement [#104](https://github.com/go-steer/core-tui/issues/104) needs, since only a width change invalidates the lazy-render cache.
- **The terminal's real cursor is parked on whichever text surface owns input** ([#105](https://github.com/go-steer/core-tui/issues/105)). `tea.View.Cursor` was set nowhere — `grep -rn 'tea.Cursor' tui/*.go` outside the tests returned zero hits. Every text surface drew its own caret instead, a reverse-video block painted into the frame, and the hardware cursor stayed wherever the last write happened to leave it. Three things break when that happens, none of them visible to a sighted operator typing ASCII: an IME's candidate window follows the *hardware* cursor, so composing CJK or emoji opened it in the wrong place; the operator's configured cursor shape and blink were never consulted, because a painted block has neither; and assistive technology, which tracks the terminal cursor, had nothing to follow. The chat textarea and the text-input dialog now run with `bubbles`' virtual cursor off and report a real position, which `View()` translates into absolute frame coordinates. The translation is per layout — `StatusHeader` stacks a status row above the chat, `StatusSidebar` drops it and puts the input inside a `chatWidth`-wide left column — and per modal, where a centered overlay's origin is derived from its own measured size using the same gap split `lipgloss.Place` performs, never a guess. Modals that own input take the cursor with them: the text-input dialog through the new `CursorDialog` extension, and the elicitation form's focused field, whose caret follows Tab and the form's scroll window and is measured in terminal **cells** so a wide label or a `日` in the value doesn't shift it. Surfaces with no caret to offer leave it nil, so the terminal hides it rather than parking it somewhere arbitrary: a permission prompt answered with `y`/`n`, the `/btw` viewer, the arrow-nav pickers, an elicitation boolean or enum, a blurred input. The position is resolved *after* the frame-clipping post-pass ([#102](https://github.com/go-steer/core-tui/issues/102)) and clamped against it — a row that clipping removed yields no cursor at all rather than a stale one, while a column past the right edge is pulled back to the last cell, because a caret legitimately sits one cell past the final glyph. One visible change comes with it: the painted block on the first character of the input placeholder is gone, and that cell is now where the terminal draws its own caret.
- **`CursorDialog`** — an opt-in extension to the `Dialog` surface for dialogs whose body owns a text-editing widget (`DialogCursor(width int, m *Model) *tea.Cursor`, returning a position relative to the dialog's own top-left cell), plus **`Overlay.Cursor(width int, m *Model)`** which routes to the front-most dialog. Both are additive; a `Dialog` that doesn't implement the extension gets no cursor, which is the right answer for the arrow-nav pickers. It is shaped as an extension rather than a contract method deliberately — folding "where does the cursor go" into `Dialog` itself belongs with the contract work in [#115](https://github.com/go-steer/core-tui/issues/115), and when that lands the change is to move the method and delete one type assertion.
- **The thinking line says how long the turn has been running** ([#111](https://github.com/go-steer/core-tui/issues/111)). It showed a rotating verb and a moving spinner, which together answer "is anything happening" and nothing else — so the single most common question an operator has while waiting, *is this a big turn or is it wedged*, had no answer on screen. The line now carries a muted elapsed suffix: `Thinking... 12s`, then `1m04s`, then `1h02m`. Three deliberate properties in that format, all of them about a string that re-renders under an already-moving spinner. There is **no sub-second component** — `0.4s → 1.2s → 2.7s` is noise on a line whose job is a rough magnitude. The minor unit is **zero-padded**, because `1m9s → 1m10s` shifts the tail of the line a column mid-turn and `1m04s → 1m10s` does not; the width changes only at 10s, 10m and 10h, once each per turn. And the readout **coarsens as it grows**, dropping seconds past the hour where they are pure churn. It stays hidden below one spinner cadence (3s): the spinner tick is the repaint that advances the number, so anything shown sooner is a value the operator cannot watch move, and short turns never flash a `0s` on their way past. No new timer is involved — `spinnerTickMsg` already fires every 3s and already marks the viewport dirty. The origin is stamped at exactly the two sites that take a new `spinnerGen` ([#112](https://github.com/go-steer/core-tui/issues/112)): `submitTurn` for the per-turn `Run` path, and `applyStreamChunk`'s `spinnerActive` false→true flip for a LiveAgent stretch, which has no `submitTurn` to hang off. That second site is what keeps the feature from shipping its own worst bug — an unstamped origin on the LiveAgent path would have measured from the zero time and rendered a fifty-five-year turn — and *stamping* it, rather than merely suppressing the zero value, is also what makes a second stretch measure from its own start instead of the first one's. The field is zeroed wherever the animation stops (`finalizeTurn`, the LiveAgent commit, a session switch), so the invariant is "non-zero iff a spinner animation is live" and no render-path gate is load-bearing for correctness. A backwards clock — NTP step, suspend/resume — clamps to absent rather than to a negative. Tested against an injected clock rather than a golden, for the obvious reason; the golden corpus is byte-for-byte unchanged, since its model is idle and renders no spinner line at all.

### Changed

- **The transcript renders the rows on screen, not the whole session** ([#161](https://github.com/go-steer/core-tui/issues/161)). Every repaint concatenated the entire history into one string and handed it to a `viewport` that sliced a screenful back out of it, so the cost of showing forty rows was set by how long the session had been running rather than by how big the window is. At 400 turns a warm repaint was 6.89ms and 1.98MB, and a pane drag — which is a stream of width-changing events, not one — spent **105ms per event**, 2.20GB across a thirty-event drag. The transcript now holds items. The scroll position is a pair, `(row, line)`: the window's top row is line *n* of row *i*, because a flat line offset cannot be resolved to a position in the transcript without knowing the height of everything above it, and knowing that is the O(session) nobody wanted to pay. From a pair the walk starts at a row it already knows and stops when the height budget is spent, so rows past the fold are never rendered and never even measured. The per-item render memo that already existed (keyed by message ID, version and width, from [#104](https://github.com/go-steer/core-tui/issues/104)) now stores the split lines alongside the text, since a row's HEIGHT is what every offset calculation actually asks for and re-splitting a cached string per query would put the cost straight back. Two rules keep it honest. Nothing on the frame path may ask for a global total: *are we at the bottom* is answered by a walk UP from the end that stops after one screenful, and the exhaustive flat-offset conversion survives only as the inverse a test needs. And the resize pass re-wraps a row and then measures it, one row at a time, so the window it stops at is the window the operator will see rather than a screenful-shaped over-estimate. At 400 turns a warm repaint is now **164µs and 14.8KB** (42x faster, 134x less memory, 867 allocations down to 135), a width-change event **7.9ms** rather than 105ms, and the drag that allocated 2.20GB allocates 55.7MB. All of them are flat in transcript size — 100 turns and 400 turns measure the same, to the noise — which is the property that actually matters, because a session only ever gets longer. Two pieces of machinery went with it: the chat's `bubbles` viewport, whose vim-convention KeyMap `NewModel` had to overwrite binding by binding and whose `xOffset` cut characters off the **left** of every line, and [#104](https://github.com/go-steer/core-tui/issues/104)'s carried-over "approximate" renders, which existed so a drag could serve rows the operator could not see — a window that only asks for the rows it draws never requests them at all. The frame itself did not change: the golden corpus is byte-for-byte identical.

### Fixed

- **A submission in LiveAgent mode shows a waiting indicator before the first token arrives** ([#148](https://github.com/go-steer/core-tui/issues/148)). On the `LiveAgent` path there is no `submitTurn`, so the only site that opened a spinner stretch was `applyStreamChunk`'s `msg.partial` branch — which by construction cannot run until the host has already produced output. The window the operator most needs an indicator for, between pressing enter and the first token coming back, was the one window with none, and a host that emits only committed messages (`Partial=false`, a perfectly legal adapter shape) got a spinner *never*. `InjectableAgent.Inject` returning nil now opens the stretch itself: the submit is the start of the turn, so it is where the animation starts and where `turnStarted` is stamped, which also means the elapsed readout ([#111](https://github.com/go-steer/core-tui/issues/111)) measures the wait the operator actually experienced rather than starting the clock at the host's first token. The two arming sites are folded into one idempotent `beginLiveStretch` so the ordinary case — operator injects, host answers — is a single stretch: the first partial finds `spinnerActive` already set and does not restart the animation, bump `spinnerGen` out from under the live tick chain ([#112](https://github.com/go-steer/core-tui/issues/112)), or move the elapsed origin. Arming the spinner in a place no chunk necessarily follows makes three previously unreachable stalls reachable, so its counterpart `endLiveStretch` now also runs on disconnect (both the permanent-error and iterator-returned arms) and on a *successful* `/interrupt` — but deliberately not a failed one, where the remote turn is still running and the spinner is telling the truth. A rejected `Inject` arms nothing. The tick chain needs no separate teardown: `spinnerTickMsg` re-arms only while `turnInFlight`, which on this path is exactly `spinnerActive`.
- **The tool-call, subagent and text-input dialogs keep their footer on a short terminal** ([#149](https://github.com/go-steer/core-tui/issues/149)). [#142](https://github.com/go-steer/core-tui/issues/142) made `fitModalContent` the single place the modal chrome is joined and gave it one guarantee — spacing goes before content, and the footer key hint, the row that says which key closes the thing, is never shed. That pass is gated on `RenderContext.Height`, which means "the geometry is known"; a zero disables it, because a bare `Model{}` in a test or a pre-resize frame has no height to fit to. **Four `RenderContext` literals never set it.** The tool-call detail overlay (`Ctrl+X`, both its populated and its empty state), the subagent overlay (`/subagents <name>`) and the shared text-input dialog therefore composed exactly as they had before #142 and fell through to `clipFrame`, which keeps the FIRST `height` rows — so what they lost was the bottom: the footer rule and `esc close`. The three pickers set `Height` and were fine, which is the whole reason the regime looked like it had landed. Underneath that, the tool-call overlay's body allowance predated the height regime and did its own arithmetic — terminal height minus a chrome constant of `8`, minus a further `6` nothing explained, floored at `6` rather than at `minModalBodyRows` and never going fullscreen. On a twelve-row terminal that floor handed back a six-row body against seven rows of chrome: a thirteen-row modal in twelve rows. At the roomy end it was wrong in the other direction, composing 17 rows of a 24-row terminal's 20-row allowance and 13 rows of a 14-row terminal's 10 — three rows wasted in the first case, three rows into the margin in the second. Both dialogs now go through `modalBodyHeight` like every other modal, but through **two** helpers rather than the one they shared: `toolCallBodyHeight` pays `modalChromeRows + 2`, counting the header banner and the blank line the overlay puts *inside* `Body`, and `subagentBodyHeight` pays `modalChromeRows`, because that one puts nothing extra there. The chrome figure is derived from `modalChromeRows` rather than restated as a literal, so the next change to the shared chrome reaches both. One shared helper could not have been right for both surfaces at once, and the hardcoded `8` it used was a guess against a six-item list — which is how it stayed wrong straight through #142. Covered by extending #142's own table: it named five modal surfaces and neither of these two, so the three new cases (tool-call, subagent, text-input) sweep both widths and all eleven heights for "the block fits" and "the close key is still on it", and a new assertion pins the allotment directly — an overflowing modal occupies exactly the terminal minus the margin, which fails against the predecessor arithmetic in both directions and is the half a shedding pass cannot detect, since a dialog that over-budgets still *looks* right while its own scroll geometry describes a modal nobody is looking at.
- **The spinner line no longer double-punctuates** ([#141](https://github.com/go-steer/core-tui/issues/141)). `renderSpinnerLine` appended `GlyphTruncate` to the rotating cognition verb unconditionally, and every entry in both built-in verb pools already ended in `...` — so the shipped bytes were `Thinking...…`, three ASCII dots and then the ellipsis glyph on top. It had presumably looked like that since the pools were written; nothing goldened a spinner line until the live-mode fixtures landed in [#139](https://github.com/go-steer/core-tui/issues/139), because the spinner only renders mid-turn and the rest of the frame corpus is captured idle. The fix normalizes rather than edits the data: `trimTrailingEllipsis` strips a trailing ellipsis — ASCII `...`, the `…` glyph, or any mix and repetition of the two, plus the whitespace around it — from the verb before the append. Dropping the dots from the defaults would have fixed the defaults and left the same defect reachable through `Options.ThinkingPhrases` / `Options.WorkingPhrases`, which are the pools a real host ships; normalizing fixes both, keeps `GlyphTruncate` as the single authority for the trailing affordance (as it already is for the truncated-diff marker in `renderDiffInline`), and changes no documented contract. Only a *trailing* run is removed, so `"Wait... then more"` keeps its mid-phrase ellipsis, and a run has to read as an ellipsis to qualify — a phrase ending in one sentence period keeps it. The three `live_frame_*` goldens churn by the three dropped dots each, which is the proof the fix reaches the frame.
- **A modal fits the terminal instead of having its footer clipped off** ([#142](https://github.com/go-steer/core-tui/issues/142)). `modalBodyHeight` subtracted a four-row `modalMarginRows` margin and then floored the result at `minModalBodyRows`, so every modal composed to at least eleven rows no matter how short the terminal was — measured on the theme picker, eleven rows at heights 4, 8 and 10 alike. `clipFrame` ([#102](https://github.com/go-steer/core-tui/issues/102)) kept the frame legal by keeping the FIRST `height` rows, so what an overflowing modal lost was its bottom: the body, the footer rule, and the footer key hint — the one row that says which key closes the thing. The margin exists so the operator keeps a sliver of chat visible above and below and the overlay reads as an overlay; on a terminal too short to hold the modal at all, that sliver was being bought with `esc cancel`, which is a bad trade. Modals now degrade to fullscreen below `modalFullscreenBelow`, a threshold derived rather than picked: it is `modalChromeRows+1` (the pickers' chrome, one row taller than everyone else's since the filter row landed in [#117](https://github.com/go-steer/core-tui/issues/117)) plus the margin plus the body floor, i.e. exactly the height at which the floor engages and the subtraction stops reflecting what fits. Below it the margin contributes zero and the floor is relaxed — a two-row window is worth having when the alternative is a clipped one — so chrome 5 + body 3 fits an eight-row terminal exactly, where it used to compose eleven. Above it nothing moved: the margin, the floor and the composed bytes are unchanged, which `TestGolden_ModalFrame` now pins at 100 and 160 columns. Separately, the row budget was only ever counted in LOGICAL rows, so a body line wider than the modal wrapped to two or three terminal rows and blew a budget that looked met — which is why the theme picker overflowed a perfectly ordinary 24-row terminal at 60 columns. The six chrome rows are now joined in one place, `fitModalContent`, which measures the wrap and sheds rows cheapest-first: the two blank spacers, then the footer rule, then body rows from the bottom, then the title. The footer key hint is never shed. Below the height that hint itself wraps to there is no honest answer left — the close key is at the END of the hint, so no truncation of it keeps the useful part — and the modal degrades to the hint alone for `clipFrame` to trim, which cannot produce a negative height and cannot panic. The scroll engine is untouched in the degraded mode: the window is smaller, not absent.
- **Shift+Tab no longer writes to disk from the event loop, and the rest of the `/cmd` host calls moved off it too** ([#137](https://github.com/go-steer/core-tui/issues/137)). [#114](https://github.com/go-steer/core-tui/issues/114) moved the hot-path capability calls into `tea.Cmd`s and left the ones behind an explicit `/cmd` for a follow-up, on the reasoning that an operator who has just typed a command reads a brief stall as the command working. The item that did not fit that reasoning was not on its list at all: **`Options.PermissionMode.Set` and `.Persist` fired on Shift+Tab**, a bare keystroke, from inside `Update` — `Persist` writes the mode to the host's config file, so cycling the permission chip did **disk I/O on the event loop**, and both return values were discarded into `_`. It was outside #114's inventory only because `PermissionMode` is a `func` field on `Options` rather than one of the §3.3 capability interfaces, which is a distinction about how core-tui declares the seam, not about who runs the code or how long it takes. The chip still flips on the keystroke — a bare-keystroke indicator has to track the key, not the host — but the two callbacks ride a Cmd now, and `permissionModeAppliedMsg` **rolls the chip back** when `Set` fails, because a chip reading `bypassPermissions` while the gate is still asking for every call is a safety claim the library cannot back; a rollback that arrives after a second Shift+Tab has already moved the chip is discarded, the same ownership check the pickers apply to a superseded switch. A failing `Persist` keeps the mode and says so — the session is in the new mode, it just will not survive a restart. The other three `Options` persistence callbacks go with it for the same reason: `PersistStatusLayout` was inline on **Ctrl+B**, also a bare keystroke and also with its error thrown away, and `PersistModelChoice` / `PersistThemeChoice` were inline in the two picker commit paths. Behind `/cmd`: `ToolLister.Tools` (`/tools`), `PermissionController.SessionApprovals` (`/permissions`) and its three mutators (`/allow`, `/deny`, `/allow bundle:<name>`), `SubagentLister.Subagents` (`/subagents`), `PricingController.Set` — from both the positional form and the `huh` form's submit handler — and `SlashProvider.SlashCommands` from `/help`, which now paints the built-in catalogue on the keystroke and appends the host's section when it answers. `/subagents <name>` stopped calling `Subagents()` to resolve its argument and reads the `hostSnapshot` roster that the sidebar already refreshes off-loop; a name that is not in a one-second-old roster falls through to the existing "ask the host anyway" branch, which is what happened for an unknown name before. Each new message type carries `gen` and is dropped on a mismatch like the ~26 existing `sessionGen` guards, and each `/cmd` posts an immediate acknowledgement row and renders its result when the reply lands — `remoteInterruptCmd`'s call-site shape. **Still synchronous, tracked on [#137](https://github.com/go-steer/core-tui/issues/137):** `/switch <id>`, which needs a genuine two-stage enumerate-then-switch flow rather than a mechanical move, and `SlashProvider.SlashCommands` in `dispatchSlash`'s name-match loop, which is not worth splitting on its own while the synchronous `SlashProvider.InvokeSlash` immediately below it is still inline — the two belong in one change. Verified by extending #114's `slowAgent`, whose capability methods sleep 500ms: every rewritten call site is asserted to return from `Update` in under a tenth of that with the host's call counter still at zero, `View()` still makes provably zero host calls after each of them, and the stale-generation drop is covered per message type.
- **The syntax cache and the `/btw` modal survive a theme swap** ([#116](https://github.com/go-steer/core-tui/issues/116)). Two latent defects that only became reachable once highlighting and markdown were theme-derived. `highlightLine`'s never-evicted `sync.Map` keyed on `lang \x00 bg \x00 line`, which was complete only while the Chroma style was a package-level constant; the key now carries the style name, so a `/theme` swap cannot replay the previous palette's bytes for the rest of the process. And `refreshTheme` cleared `m.markdown` but not `m.modalMarkdown`, so swapping themes with a `/btw` answer open would have kept the modal body on the old palette until its width happened to change.
- **LiveAgent mode shows the stream while it is streaming** ([#135](https://github.com/go-steer/core-tui/issues/135)). `renderInProgress` gated the whole in-progress block on `m.state == stateStreaming`, and `stateStreaming` is assigned in exactly one place — `submitTurn`. The `LiveAgent` path ([#22](https://github.com/go-steer/core-tui/issues/22)) never calls `submitTurn`: it is driven from `applyStreamChunk`, which accumulates `m.inProgressText` and flips `m.spinnerActive` but leaves `m.state` at `stateIdle`. So the one mode whose entire purpose is watching an agent work autonomously rendered neither the streamed prose nor the spinner verb line — the operator saw an idle-looking TUI for the whole stretch and then the finished message in one lump when the commit chunk landed. The gate now asks the question it means to ask, through a `turnInFlight` predicate shared with the spinner-tick handler: something is in flight when a Run-driven turn is streaming *or* a live stretch has the spinner up. It is one predicate rather than two conditions because `renderInProgress` asks twice — once to bail out, once to emit the body — and widening only the first leaves the body skipping the text for the same invisible result. `m.state` keeps meaning "a Run-driven turn is in flight", so the nine other reads of it that gate interrupt and submit behaviour are untouched. Two changes written against this path and dead on arrival now paint: the per-stretch spinner tick chain ([#112](https://github.com/go-steer/core-tui/issues/112)) and the per-stretch elapsed readout ([#111](https://github.com/go-steer/core-tui/issues/111)), which counts from the start of the current stretch rather than inheriting the previous one's origin. The live path had no frame coverage at all, which is how this survived; it now has a `live-stretch` cell in the frame-invariant grid and a three-width golden capturing prose, spinner and elapsed suffix together, rendered through the injected clock so the corpus is not a function of when it was taken.
- **The dialog text-input caret lands on the right cell for CJK and emoji** ([#125](https://github.com/go-steer/core-tui/issues/125)). `textinput.Cursor()` in the pinned `charm.land/bubbles/v2 v2.1.0` computes its column as `m.Position() + promptWidth` — a **rune index** added to a **cell width** — so every double-width rune before the caret loses it a cell, and typing `日本語` into a text-input dialog left the terminal cursor three columns short of the glyph it belongs on. That is exactly the IME anchoring [#105](https://github.com/go-steer/core-tui/issues/105) set `tea.View.Cursor` to get right, still wrong on the one surface people compose CJK into. `textarea.Cursor()` measures `LineInfo().CharOffset` and has always been correct, which is why the chat input was unaffected. The new `textInputCursor` helper recomputes the column from `Value()` and `Position()` with `ansi.StringWidth`, and `textInputDialog.DialogCursor` goes through it. **Partial by necessity:** the same upstream function also ignores `m.offset`, its horizontal scroll position, so a value wider than the box reports a column computed against the unscrolled string and the clamp pins the caret to the right edge — reachable with pure ASCII. `m.offset` has no exported accessor, so correcting it downstream would mean reimplementing `handleOverflow`'s scroll arithmetic against state we cannot observe. `handleOverflow` zeroes the offset whenever the value fits, so the fitting case is corrected exactly and the scrolled case falls through to upstream unchanged, with a test pinning that split so it stays deliberate. The complete fix has to come from upstream, where both halves are already reported and open — [charmbracelet/bubbles#906](https://github.com/charmbracelet/bubbles/issues/906) for the rune-vs-cell measurement and [#1001](https://github.com/charmbracelet/bubbles/issues/1001) for the ignored scroll offset. `textinput.go` is byte-identical in v2.1.1, so a version bump is not it; our correction self-neutralises to zero once theirs lands.
- **The model picker opens on the model you are using** ([#110](https://github.com/go-steer/core-tui/issues/110)). `newModelPickerDialog` hardcoded `idx: 0`, so `/model` and `Ctrl+G` highlighted whichever model the host happened to list first and the operator had to find their current one before they could navigate relative to it — on a host advertising forty models, with no type-to-filter yet, that is the difference between a picker and a list you scroll. The theme picker had solved this since v0.1.0 by seeding on the active theme; the model picker now does the same. The seed lands in `applyModels` rather than the constructor because [#114](https://github.com/go-steer/core-tui/issues/114) made the list arrive asynchronously — there is nothing to seed against until the host answers. Matching is on ID first and then the display name, the same predicate `Render` already uses to paint its `(current)` tag, so the cursor and the tag cannot disagree; a model the host does not list in its own catalogue still lands on row 0.
- **The help panel is laid out to the terminal in both dimensions** ([#119](https://github.com/go-steer/core-tui/issues/119)). `renderHelpPanel` emitted the same 38 rows at every terminal size: its `width` argument reached the `<= 0` guard and the horizontal rule and nothing else, so each key row was a constant `"    " + key(padded to a hardcoded 24) + description` — 81 cells at the widest, in an 80-column terminal, and twice the terminal in a 40-column one. It also made the chrome budget wrong, because `lipgloss.Height` counts a row that visually wraps as one row. **Width** is now a derivation rather than a constant: the key column comes from the widest key actually present, capped so one 29-cell key row cannot push all 22 descriptions five columns right, and never allowed past half a narrow panel; descriptions **wrap** into the remainder with a hanging indent, and below the point where the aligned form stops being readable the panel switches to a **stacked** one — key on its own row, description full-width underneath. **Height** is pagination, on the panel's own key. `m.chrome.helpCap` is the row ceiling the budget ([#121](https://github.com/go-steer/core-tui/issues/121)) hands the panel, and laying out *to* it beats being elided *by* it, which is what the `… N more rows` marker was doing: `?` now opens the panel, walks it a page at a time, and closes it after the last page, with the title row saying which page is on screen and which key advances it. Paging on the key that opened the panel is what keeps `pgup` / `pgdn` with the chat — the panel's own Navigation section advertises them as chat scroll, and a scroll mechanism would have had to take them away and make it lie again. Pages break on section boundaries wherever they can, so a page usually comes in under the cap and the rows it does not spend go back to the chat viewport; one page always beats two, so a panel that would fit without the blank rows between sections is rendered compactly instead of split. Gated by a width × height grid asserting no rendered row exceeds its column and no page exceeds its cap, a content check that walking the pages still reaches all 22 documented keys, help-open frame goldens at 60 / 100 / 160 columns (the corpus had none — `goldenModel` never set `helpOpen`), and paged-panel cells in both the frame-invariant and the row-budget grids.
- **The input box grows again, and variable-height chrome can no longer push the frame past the terminal** ([#121](https://github.com/go-steer/core-tui/issues/121)). `syncInputHeight()` clamps the textarea to its line count between `textareaMinHeight` and `textareaMaxHeight`, and every one of its call sites follows the grow with a `resize()` — which opened with an unconditional `m.input.SetHeight(textareaMinHeight)`. The grow was computed and thrown away before it could be rendered, so the auto-growing box those doc comments describe ("multi-line paste / typed newlines grow the box visibly") survived **zero frames** and `textareaMaxHeight = 15` was unreachable dead configuration. Two adjacent gaps in the same feature go with it, both invisible while the clobber hid them: the newline arm of `handleKey`'s switch (`shift+enter` / `ctrl+j` / `alt+enter`) returns early and so never reached the reconciliation at the bottom of that function, and a bracketed paste never goes through `handleKey` at all — it falls out of `Update`'s switch to the shared forward-to-the-widgets tail. The two gestures whose entire purpose is to add rows were the two that did not grow the box, until some unrelated later keystroke reconciled the layout for them. The one-line clobber is gone, but on its own it would only have moved the damage: `resize()` had no notion of variable-height chrome yielding rows to fixed elements, so a 15-row box on a short terminal would overflow the frame exactly the way the **help panel** already did — `renderHelpPanel` emits 38 rows at every width ([#119](https://github.com/go-steer/core-tui/issues/119)), which on an 80×24 terminal composed a 48-row frame, and since `clipFrame` keeps the *first* `m.height` rows, pressing `?` clipped away the input box and the footer entirely: the operator lost the box they were typing into and the only row that says how to quit. The **palette** (`maxPaletteRows` + its own chrome) is the third instance. `resize()` now allocates the terminal's rows through an explicit chrome budget (`tui/budget.go`) instead of subtracting-and-flooring: unshrinkable chrome (footer, header, toast) is reserved off the top, then the input box's *minimum*, the chat viewport's `chatMinHeight` floor and one row per open panel, then — in priority order — the input box's *growth*, the palette, the help panel, with everything unspent going to the chat. Splitting the input box across two priorities is what resolves the conflict the issue names: a `textareaMaxHeight`-tall box wins against the palette and the help panel, but **not** against the chat floor, because watching the transcript vanish while typing is worse than typing into a box that scrolls internally past its height — which is what the textarea already does. Elements below the cut shrink rather than overflow: the palette narrows its scrolling window, and the help panel is elided with a `… N more rows` marker until #119 makes its content fit a column. Every term is still a measurement of the string `View()` will render, at the width it will render at, so `clipFrame` is back to being a safety net that does not fire — the only case left is a terminal shorter than the irreducible chrome (a 4-row pane, where the header, the input box and the footer are already taller than the screen), which the budget now reports as a number rather than discovering by accident. Two verification gaps closed with it. `assertBudgetExact` used to **skip** whenever the viewport bottomed out at `chatMinHeight` — which is exactly what the help panel causes, so every cell that would have caught the 48-row frame skipped silently; it now asserts the exhausted case as a checkable size instead. And the row-budget grid had no state in which the textarea was ever taller than three rows, because `resize()` guaranteed it could not be; it sweeps a tall textarea (alone and against the help panel) in both layouts across the full width × height matrix now. Golden-neutral: the frame corpus types nothing into the box, so its `LineCount()` is 1 and every golden is byte-identical. `BenchmarkResizeHeightOnly` and `BenchmarkResizeDrag400` are unmoved.
- **A key that jumps to the tail and resumes following the stream** ([#113](https://github.com/go-steer/core-tui/issues/113)). `ctrl+l` jumps to the top of the transcript and had no counterpart. Once following became explicit state ([#93](https://github.com/go-steer/core-tui/issues/93)), the only way back to a live stream was holding `PgDn` until `AtBottom()` re-armed the flag on its own — so an operator who had read back through a long session paid one keypress per screen to resume watching it, and on a session long enough to be worth reading back through, that is the whole cost of following in the first place. `end` now does it in one: `m.follow = true` plus `viewport.GotoBottom()`, the same pair `refreshAndScroll` uses, but without the `syncInputHeight` / `resize` that helper also runs — a jump to the tail changes no geometry, so it has no business re-resolving the layout. The binding is claimed **only while the input is empty**. bubbles' textarea binds `end` to `LineEnd`, and "end goes to end-of-line" is too strong a convention to shadow in a box the operator is composing in — the more so because `syncInputHeight` grows that box to `textareaMaxHeight` rows, where line-end is the whole point. With nothing typed there is no line to end, so the key is free and the chat takes it; with a prompt in progress it falls through to the textarea. `ctrl+e` reaches end-of-line in either state. `ctrl+d` and `ctrl+u` keep their existing shadows — recovering the viewport's half-page scroll bindings is not worth making the primary quit key scroll the transcript.

- **The help panel no longer advertises two keys that do nothing** ([#113](https://github.com/go-steer/core-tui/issues/113)). `renderHelpPanel`'s Navigation section listed `home / end` as "top / bottom". Neither key was bound anywhere: `grep -n '"home"\|"end"' tui/update.go` returned nothing, and bubbles v2's viewport binds neither — `handleKey`'s own fall-through comment said as much, a few lines below the switch that would have had to claim them. It is the same defect class as the truncated-diff marker naming `ctrl+o` ([#94](https://github.com/go-steer/core-tui/issues/94)): the one surface a new operator opens to learn the keymap was naming keys the package does not handle. `end` is bound now. `home` deliberately is **not** — `ctrl+l` already does exactly what it would, and a second binding for one action would spend the textarea's `LineStart` to buy nothing. So the rows name what exists instead: `ctrl+l` "jump to top (stops following the stream)" and `end` "jump to bottom (resumes following)". `ctrl+l`, the real goto-top key, was not listed at all before. A new test parses the rendered Navigation rows, presses every key they name, and asserts each one moves the viewport — so the section cannot quietly drift back out of sync with the switch that implements it.
- **CI no longer decides required checks by a race** ([#124](https://github.com/go-steer/core-tui/issues/124)). `ci.yml` carried `paths-ignore: ['**/*.md']` and a twin `ci-docs.yml` carried the inverse `paths: ['**/*.md']`, each emitting four **identically named** check runs. Because GitHub path filters match "any changed file", a PR touching both Go and Markdown satisfied both filters and ran both workflows — and since every PR here carries a CHANGELOG entry, that was the normal case rather than a corner case. Which of the two same-named results counted was then decided by whichever finished last, an ordering the old `ci-docs.yml` header admitted to relying on. Re-running the 3-second stub after a red pipeline produced four green required checks on a red commit. `ci.yml` now has no path filters and always reports; a `changes` job classifies the diff once and the four jobs short-circuit their expensive steps when it is docs-only. `ci-docs.yml` is deleted. The fast path also widened from `**/*.md` to include `docs/`, which the old filter missed entirely — `docs/site` carries `hugo.yaml`, `package.json`, its own `go.mod` and an `.scss`, so editing the published site's stylesheet used to run the whole Go pipeline. And `changes` now asserts the invariant the fast path rests on: no `//go:embed` may reference Markdown or `docs/`, since an embedded `.md` would let a docs-only PR skip the tests for a change that alters the built binary.
- **The context-fill ramp follows the active theme** ([#109](https://github.com/go-steer/core-tui/issues/109)). The `<used> / <size>` segment in the status header and in the sidebar's spend block is the one piece of chrome carrying real semantic weight — a three-tier ramp that shows the operator how close the context window is to overflowing before it bites — and it was the one piece that ignored the palette. `contextFillStyle` picked from three hex literals baked into the function (`#5FD787` / `#FFD75F` / `#FF5F5F`), so the ramp rendered identically across all twelve builtin themes and across the light and dark variant of each. Those three values are the *default* theme's `Success` / `Warning` / `Error`, which is why the defect was invisible on the house palette and worst everywhere else: on a light terminal the 85%-and-above tier is a pale coral on white — the tier the operator most needs to be able to read is the one that falls out of contrast. The three tiers now resolve `Theme.Success` / `Theme.Warning` / `Theme.Error` off the active theme, tokens that already existed, so no theme gained a field and no host action is required. Christmas gets pine / gold / cardinal, Google gets its brand green / orange / red, and the default palette renders byte for byte what it did before. The doc comment above the function had claimed a themed ramp all along; it is accurate now. Golden-neutral by construction — the frame corpus wires no `UsageTracker`, so neither usage summary reaches a golden.
- **A filename in a tool event no longer costs a full Chroma lexer sweep** ([#106](https://github.com/go-steer/core-tui/issues/106)). `detectLang` mapped a path to a lexer name by calling `lexers.Match` and nothing else — no memoization, on a function whose own upstream doc comment warns that it runs hundreds of `filepath.Match` calls per lookup. It is reached from four call sites on the tool-display path (`tool_preview.go` twice, `tool_preview_read.go`, `tool_preview_result.go`), which is to say once for every tool event that carries a filename, and the same handful of paths in a session re-paid the sweep every single time. Measured on this repo's usual CI hardware (AMD EPYC 7B12), one uncached lookup costs **4.89ms** for a path that matches a lexer and **2.42ms** for one that doesn't — a millisecond-scale stall on the UI goroutine per event, for an answer that cannot change. The result is now memoized in a `sync.Map` alongside the existing per-line `syntaxCache` and `lexerCache` in the same file, taking a hit to **19.8ns** and a miss to **19.5ns** (**247x** and **123x**), with zero allocations where the matcher's priority sort previously allocated on every hit. One deliberate divergence from the neighbouring `getLexer`, which does *not* cache its nil result: `detectLang` **does** cache the empty-string miss. `""` is the ordinary answer for the paths a session touches most — `README`, `LICENSE`, `Makefile`, extensionless notes, plain text — so leaving negative results out would have left the hotter half of the path uncached, on the branch that is the more expensive of the two to be wrong about at scale. There is no invalidation to get wrong: `detectLang` is a pure function of its label, so an entry stays correct for the life of the process, and the working set is bounded by the number of distinct paths one session touches. The render benchmarks are unmoved — `BenchmarkRefreshViewport` at 400 turns 6.90ms → 6.70ms, its cold-cache variant 19.1ms → 19.3ms, allocation counts identical — so nothing was borrowed from the repaint path to pay for this.
- **The thinking spinner can no longer end up running two tick chains at once** ([#112](https://github.com/go-steer/core-tui/issues/112)). `spinnerTick()` returned a bare `tea.Tick` carrying no identity — `spinnerTickMsg` was an empty struct — and the handler re-arms on every tick, so any path that armed while a chain was already live produced two independent chains, each re-arming the other's replacement forever. The visible symptom is the thinking/working verb pool rotating at 2x (3x after another overlap) for the rest of the session; the underlying one is `tea.Tick` accumulation that nothing ever reclaims. The existing level gate (`m.state != stateStreaming && (!m.liveMode || !m.spinnerActive)`) does not catch it, and cannot: it answers "should *a* spinner be running right now", not "which chain is this tick from", and the turn-chaining paths flip `m.state` back to `stateStreaming` well inside one 3s cadence — a queue drain or an auto-continue re-enters `submitTurn` from the same `turnDoneMsg` handler that just finalized the previous turn, so the superseded chain's next tick arrives to a streaming model, passes the gate and re-arms. Every tick now carries a `spinnerGen` stamp and the handler drops one that doesn't match, which terminates the superseded chain instead of doubling it. The generation is bumped where a new animation *begins* — `submitTurn` for a per-turn spinner, `applyStreamChunk`'s false→true `spinnerActive` flip for a LiveAgent stretch, which has no `submitTurn` to hang off — and all seven arming sites go through one `armSpinner()` helper so the stamp can't be forgotten at one of them. Deliberately a new per-turn counter rather than the existing `sessionGen`: that one only moves in `applySwitchTarget`, i.e. on a session switch, so the two overlapping turns *inside* one session that produce this bug would share a generation and the guard would be a no-op on the reported path. Same shape as the `resizeGen` stamp on `resizeReflowMsg` ([#104](https://github.com/go-steer/core-tui/issues/104)). No render path changed — the golden corpus is untouched.
- **The layout row budget is measured rather than guessed** ([#103](https://github.com/go-steer/core-tui/issues/103)). `resize()` sizes the chat viewport by subtracting the chrome around it from the terminal height, and three of its terms were wrong. The **header** was pinned at a literal `2 // status line + a blank row` while every sibling term called `lipgloss.Height` — but `renderHeader` word-wraps the status line, so on a 20-column terminal it occupies four rows and the frame came out a row taller than the terminal; the clipping post-pass from [#102](https://github.com/go-steer/core-tui/issues/102) then quietly ate the bottom of the footer, which is the row that tells a new operator how to quit. The **toast** had no term at all: `View()` slots the wake banner between the input box and the footer, so a visible toast pushed the frame over budget too, and only a spare row left over from an unexplained `- 2 // input top border + spacer` (there is no spacer) kept that from showing on a wide terminal. The **prompt-queue panel** was charged in the opposite direction — it is appended by `renderInProgress` into the viewport's *content*, not joined beside the viewport the way the footer, help panel and palette are, so subtracting it shrank the viewport by the panel's height and then spent that height drawing the panel inside the smaller viewport: a four-row queue cost the operator four rows of chat and left the frame four rows short of the terminal. Every term is now measured from the string `View()` will actually render, at the width it will render at, and only siblings of the viewport are charged. The composed frame is now exactly as tall as the terminal across the full width × height × layout matrix, so the height cap in `clipFrame` stops firing in normal use — which is what [#102](https://github.com/go-steer/core-tui/issues/102) said should happen once this landed. The new `tui/resize_budget_test.go` asserts that exactness directly, because the frame-invariant grid only checks that the frame does not *overflow* and is therefore satisfied by clipping.
- **The rendered frame is clamped to the terminal in both dimensions** ([#102](https://github.com/go-steer/core-tui/issues/102)). Nothing clamped it. Chrome is composed with `lipgloss.JoinVertical` / `JoinHorizontal` / `Place` and plain string concatenation, so overflow was possible at every join and nothing caught it at the end — the frame-invariant grid landing alongside this fix found 83 of its 200 cells overflowing, up to 82 columns of output in a 40-column terminal and 62 rows in a 24-row one. The height case was the nastier of the two, because Bubble Tea drops the **top** lines when a frame is too tall: the status header simply disappeared, with no indication anything had been cut. `View()` now ends with a clipping post-pass that truncates every line to the terminal width with `ansi.Truncate` — escape-aware, so an SGR sequence is never sliced in half the way byte-level cutting would — and caps the frame at the terminal's row count, keeping the *first* rows so the header is the part that survives. A frame that already fits comes back byte-identical; a not-yet-known geometry passes through untouched. This is a safety net, not a layout step: the row *budget* is [#103](https://github.com/go-steer/core-tui/issues/103), and once that lands the height cap should stop firing. It stays regardless — a compositor sizes its canvas to the union of its layer bounds, not to the terminal, so it would reproduce this same bug.
- **Dragging a terminal pane no longer freezes the UI** ([#104](https://github.com/go-steer/core-tui/issues/104)). A width-changing `tea.WindowSizeMsg` re-rendered *every* assistant message in the transcript through Glamour, synchronously, inside the message handler — and a pane drag emits a stream of those events, one per column crossed, so the cost was paid dozens of times over a single gesture while the UI sat unresponsive. The render memo made it worse: it pinned one width and dropped every entry the moment the width changed, so the re-assembly that followed the Glamour pass was fully cold too, on every event and again on the way back when the operator dragged the pane to a width already rendered at. The whole-history pass is now debounced behind a 120ms settle tick (generation-stamped, so a superseded drag's callback can never clobber a newer resize): a resize event reflows only the messages actually on screen — bounded by viewport height, not by session length — and the backlog warms after the drag stops, eight rows per tick rather than in one synchronous burst. Cache entries are keyed per `(message, width)` instead of behind a single width pin, so a row already rendered at the incoming width survives; rows off screen mid-drag are carried over from the previous width and retired by the warm pass before they can be scrolled into view. Measured with the repo's own `BenchmarkResizeWidthChange` (AMD EPYC 7B12), one width-changing event costs **3.63ms → 2.32ms** at 10 turns, **32.2ms → 3.97ms** at 100, and **126ms → 9.27ms** at 400 — and its allocation count, 47.3K / 463K / 1.84M before, is now 28.4K / 28.5K / 29.3K, i.e. flat in transcript length rather than linear in it. The `BenchmarkResizeHeightOnly` control (6.89ms → 6.84ms at 400 turns) and the steady-state repaint (`BenchmarkRefreshViewport`, 6.52ms → 6.60ms) are unmoved, so nothing was borrowed from the paths a resize is not on. Over a whole 30-event drag on richer turns (`tui/resize_drag_bench_test.go`, prose + list + fenced code): **8.48s → 0.72s** at 100 turns and **32.4s → 2.16s** at 400, with the deferred settle adding 0.30s and 1.19s respectively — 8.3x and 9.7x for the entire gesture. What remains per event is the transcript concat and `viewport.SetContent`, which are O(history) no matter what is on screen; removing those needs a windowed list, which this fix deliberately does not reach for. Follow state (#93) is untouched by any of it — a drag leaves an operator pinned to the tail pinned, and one reading scrollback where they were.
- **A permission prompt can no longer be answered by input the operator was already typing** ([#95](https://github.com/go-steer/core-tui/issues/95)). Permission requests arrive asynchronously and the modal was decision-live from the frame it appeared, so buffered keystrokes were consumed as the answer: typing `say` while prompts landed dispatched allow-session, allow-always and allow-once — three grants, one of them persistent, from a word aimed at the prompt. The six decision keys are now inert for 300ms after the modal appears, and keystrokes inside that window are routed to the prompt instead of being dropped. `esc` is exempt: it denies, which is the fail-safe direction. The elicitation modal gets the same window on the keys that dispatch a result (accept / decline / submit), while field editing and navigation stay live. New **R-PERM-8** / **R-ELIC-4** in `docs/requirements.md`.
- **Auto-follow survives a resize mid-stream** ([#93](https://github.com/go-steer/core-tui/issues/93)). Following the live tail was inferred from `viewport.AtBottom()` at repaint time, and the resize handler applied the new height *before* that sample — shrinking the terminal by a row (or typing enough to wrap the textarea onto a second line) made a pinned viewport report "not at bottom", so the re-pin was skipped and the rest of the turn streamed away below the visible region with no indication. Following is now tracked as explicit state on the model: scrolling up releases it, scrolling back to the bottom re-arms it, operator-initiated jumps (submit, slash output, session switch, `ctrl+l`) set it outright, and geometry changes leave it alone.
- **The elicitation form accepts non-ASCII input** ([#91](https://github.com/go-steer/core-tui/issues/91)). Two byte-vs-rune defects made the form ASCII-only: the append guard measured `len(stroke)` in bytes, so every printable character with a multi-byte encoding (`é`, `ü`, `日`, `😀`) was silently dropped — typing `café` yielded `caf` — and backspace sliced one *byte* off the value, leaving invalid UTF-8 in both the rendered frame and the `ElicitResult` handed to the host. Both sites are rune-aware now, and the append guard additionally rejects unprintable runes.
- **Truncated diffs no longer advertise a keybinding that doesn't exist** ([#94](https://github.com/go-steer/core-tui/issues/94)). The marker under a clipped diff read `… +N more lines · ctrl+o to expand (todo)`. `ctrl+o` is bound nowhere in the package, so the one key the transcript named was the one key that did nothing — and the note-to-self shipped to operators. The marker is now just `… +N more lines`. Row-level diff expansion needs a message cursor first; when it lands, the affordance comes back with a key behind it.
- **The scrollbar thumb no longer vanishes at the bottom of long content** ([#92](https://github.com/go-steer/core-tui/issues/92)). `Scrollbar` computed one more thumb position than it drew rows, so at maximum scroll the thumb landed one row past the end of the track: clipped short for a multi-row thumb, and gone entirely for the one-row thumb any content much longer than the viewport produces. The thumb now rests flush on the final row at maximum offset.
- **CRLF line endings no longer diff as "every line changed", and the per-line cap counts a tab as the four cells it renders as** ([#107](https://github.com/go-steer/core-tui/issues/107)). Nothing normalized line endings on the way into the diff. `computeUnifiedDiff` compared a CRLF file's contents against the model's LF replacement string, so `udiff` saw two strings that differ at the end of every line and produced a whole-file diff for a two-line edit — and each rendered row then carried its trailing `\r` **inside** the background-tinted `+` / `-` span, which is a cursor-to-column-0 with the tint still active: the row repaints over itself in the middle of the strip. CRLF is now collapsed at the three points where a payload becomes rows — the `strings.Split` in `renderDiffInline`, the one in `renderCodeInline`, and both sides of `computeUnifiedDiff` before `udiff.Unified` sees them. Normalizing before the equality short-circuit rather than after is what makes a CRLF file against a byte-identical LF string come back as **no diff at all** instead of a full rewrite. Deliberately **not** inside the per-line funnel: the `\r` sits at end-of-line and the cap can slice the body before ever reaching it. A **lone** `\r` is not a line ending and is not treated as one — it is a cursor control, and it is escaped like the rest of them. The tab half of the issue turned out to be already solved and worth **not** re-solving: lipgloss expands tabs at `tabWidthDefault = 4` on every styled path, which is why the golden corpus holds zero tab bytes despite tab-indented fixtures, so adding a second expansion at some other width would only have desynchronized the two. What was actually broken is the arithmetic. The per-line cap charged a tab one byte against a 200-byte budget while the terminal drew four cells, so a tab-indented line could render four times wider than the cap allowed and a 200-tab line — comfortably "under" the cap — was 800 columns of output. The budget is counted in cells now, with a tab costing `contentTabWidth`, and the cut lands on a rune boundary instead of mid-rune. Byte-for-byte golden-neutral on all 24 existing fixtures, which is the check that the tab decision went the right way: with tab exempt the pass is the identity function on clean ASCII, so any movement in the corpus would have been the signal that it had not.
- **Host capability methods no longer run on the Bubble Tea event loop** ([#114](https://github.com/go-steer/core-tui/issues/114)). `Update` and `View` share one goroutine, so anything slow inside either freezes the whole TUI — the spinner that is supposed to signal liveness, the cursor blink, and Ctrl+C, since those all arrive as messages the frozen loop cannot read. core-tui is a library: the capability interfaces are host-implemented, so it cannot assume any of them are fast, and roughly two dozen call sites were calling them inline. The worst were on bare keystrokes. `ModelSwapper.SwitchModel` ran on Enter in the model picker — a host that validates credentials or opens a connection there hung the UI for the whole round trip with no spinner and no way out. `AvailableModels()` and `SessionSwitcher.Sessions()` were re-pulled on *every keystroke* while their picker was open, and again from `Render`, i.e. from `View()`, which `host_snapshot.go` documents as provably never touching the host; the sidebar's `SubagentLister.Subagents()` was the third such violation. The `@` palette ran a full `filepath.WalkDir` on the `@` keypress, defaulting to the entire working directory when `PathScope` is unset, and `SlashProvider.SlashCommands()` ran on the `/` keypress. `Reloader.Reload` and `PricingController.Refresh` were the worst by contract: both take a `context.Context` — the host has been *told* it may be slow — and both were handed `context.Background()`, no deadline, no cancellation. Every one of those now returns a `tea.Cmd` following the four properties `host_snapshot.go` established (capability handle resolved before the closure, `sessionGen` captured at construction, no model state touched from the goroutine, nil Cmd when the capability is unwired), and the two ctx-taking methods get bounded contexts. The pickers pull their list **once when the dialog opens**, into a snapshot on the dialog that `Render` reads, and show a loading line while it is in flight; the `@` palette opens instantly and populates when the walk finishes. `modelSwitchedMsg` carries the generation stamp because `SwitchModel` replaces `Options.Agent`, so a reply that left under the previous session must not attach the outgoing session's agent to the incoming one — and replies route through `overlayStack.Get`, since an async reply for a dialog another modal has since covered still belongs to it. Remaining synchronous calls all sit behind an explicit `/cmd` rather than a bare keystroke (`ToolLister.Tools`, `PricingController.Set`, the `PermissionController` mutators, `SubagentLister.Subagents` from `/subagents`, and `/switch <id>`) and are tracked as a follow-up.

### Security

- **Untrusted tool output can no longer write escape sequences to the operator's terminal** ([#108](https://github.com/go-steer/core-tui/issues/108)). Tool args (the model writes them), tool responses, file content and bash stdout/stderr (the filesystem and the host write them), and tool error text (anything in the stack writes it) all reached the renderers unescaped. A file the agent was pointed at — a dependency's source, a fixture in a cloned repo, a log — could therefore emit control bytes straight at the terminal: `ESC[2J` to erase the display, `ESC]0;…` to retitle the window, cursor positioning to draw outside the row it was given, `CR` and `BS` to overwrite text that was already on screen, SGR to recolor everything after it. The last two are the interesting ones, because together they let content forge output — UI chrome, a permission prompt, a success line — that appears to come from `core-tui` itself. The escaping is one pass in one place. `sanitizeLine` (`tui/sanitize.go`) is the per-line funnel every renderer of untrusted content already routed through for length capping, so it was the natural home and needed no new call sites; `trimToolArg` is the second, rune-based funnel for arg hints and queue rows, where the caller supplies the width. Both run `ansi.Strip` from `github.com/charmbracelet/x/ansi` — no byte-level slicing — which removes CSI, OSC, DCS, SOS, PM and APC in both their 7-bit `ESC [` and 8-bit `0x9B` introducer forms, and then escape what `Strip` leaves behind to a visible `\xNN`: C0 (0x00–0x1F), DEL (0x7F), the C1 range `U+0080`–`U+009F` when it survives as a UTF-8 rune, and any byte that is not valid UTF-8. Stripping ANSI rather than escaping it is deliberate — SGR in captured build output is common and benign, and rendering it as visible litter would be worse than dropping it — and `\xNN` is chosen over the Control Pictures block because pure ASCII cannot itself need escaping. **TAB and LF are exempt**: LF is the line separator, and TAB is already expanded to four spaces by lipgloss before it reaches the terminal, so escaping it would have churned the chroma goldens to make tab-indented Go read as `\x09`. Escaping runs **before** the cap, not after, so the budget bounds what the terminal is actually asked to draw. Two paths that were not the funnel got folded in: `renderResultError` had rolled its own `errCap = 200` byte slice — the same number the shared cap already held, maintained twice and escaping nothing — and `renderDetailSection` turned out **not** to be safe behind `json.MarshalIndent` after all. The encoder escapes C0 and a short list of HTML-sensitive ASCII, but passes DEL and the entire C1 range through verbatim, and `U+009B` is the 8-bit CSI introducer that a UTF-8 terminal acts on; the marshaled body takes the same pass now. A table of hostile payloads drives every renderer, and nine new adversarial goldens under `tui/testdata/hostile_*` pin what a terminal receives when a tool hands the TUI something that is trying to draw on it. The goldens are paired with an assertion rather than trusted alone — a golden can only prove the bytes did not change, not that they are safe — so regenerating the corpus cannot quietly bless an escape sequence.

### Removed

- **The vestigial enum-driven overlay path** ([#90](https://github.com/go-steer/core-tui/pull/90), closing [#79](https://github.com/go-steer/core-tui/issues/79)). `Model` carried an unexported `overlay` enum (`overlayNone` / `overlayModelPicker`) left over from the visual-preview slice, along with the `modelPickerIdx` field, `renderOverlay`, the `case m.overlay != overlayNone` arm in `View`'s modal cascade, the matching `footerHint` case, and a second copy of the model-picker key handling in `Update`. A write-set analysis over `tui/*.go` **and** the test suite (`docs/api-audit.md` §4) found no assignment of any non-`overlayNone` value anywhere, so `m.overlay` was provably always `overlayNone` and every consumer of it was unreachable. Real picker state has lived in the `Dialog` stack since v0.1.0; `Ctrl+G` and `/model` both open `modelPickerDialog`. No exported symbol changed and **no host action is required** — this is dead-code removal ahead of the v1.0 freeze, so the paths don't become permanent maintenance obligations.

The `usageMsg` bullet on that issue was a **false positive and nothing changed for it**: `usageMsg` is not legacy, it is still fed from `Event.Usage` / `Event.Model` in `tui/agentcmd.go`, and `turnSummaryMsg` is an additional push-mode path (v0.9.0), not a replacement. Deleting it would have broken per-turn usage rendering for every pull-mode host.

## [0.19.0] — 2026-08-14

A bug-fix release with one small piece of new plug-in surface: modal windows scroll now.

### Fixed

- **Every modal scrolls** ([#75](https://github.com/go-steer/core-tui/pull/75)). A modal body taller than the terminal was clipped, and the mouse wheel never reached a modal at all — `tea.MouseWheelMsg` fell through `Update` to the chat viewport *behind* the overlay, so the wheel scrolled something the operator couldn't see. Every modal surface now scrolls with `↑`/`↓`, `PgUp`/`PgDn`, `Home`/`End` and the wheel: the `/btw` side answer, the permission overlay, the elicitation form, the tool-call and subagent detail overlays, and the theme / model / session pickers. A body that overflows grows a scrollbar column and an `↑↓ scroll` footer hint; one that fits shows neither. Four deliberate refinements: the **inline** permission layout keeps handing the wheel to the chat (that *is* the surface showing the prompt — only the centered `PermissionOverlay` layout captures it); **pickers move one row per wheel tick**, not the three-row wheel step, because a nudge that jumps three models past the one you wanted is worse than no wheel at all; the elicitation form **follows focus only when focus moves**, so scrolling away to read something else isn't yanked back on the next repaint; and the subagent log keeps its follow-the-tail pin, with wheel-up releasing it exactly as `↑` does and `End` re-pinning. No bare `j`/`k` bindings anywhere — those belong to the field being typed into.
- Two latent bugs fell out of the same work. `PgDn` had **never** worked in the tool-call or subagent overlays — bubbletea renders `KeyPgDown` as `"pgdown"`, not the `"pgdn"` they matched on. ## [0.17.0] — 2026-08-11

Hang-proof TUI event loop. Attach-mode `core-agent-tui` could wedge after sitting idle — no typing, dead Ctrl+C, and a `kill -QUIT` left the terminal garbled. Root cause: bubbletea runs Update and View on a single event-loop goroutine, so anything that blocks there freezes the whole TUI, and SIGINT/SIGTERM only arrive as messages the frozen loop can't read.

### Changed

- ⚠️ **`StatusReporter` / `UsageTracker` implementations must now be safe for concurrent, non-blocking reads.** The TUI pulls them off its event loop.
- **Non-blocking `View()`** ([#69](https://github.com/go-steer/core-tui/pull/69)). The status-header helpers (`displayModelName`, `displayProvider`, `usageSummaryOneLine`/`Stacked`) called the host's `StatusReporter`/`UsageTracker` on every paint, so a slow or wedged host froze the loop. They now read a `hostSnapshot` cache refreshed **off** the event loop via a self-perpetuating, generation-guarded cycle (kicked in `Init`, re-armed on a tick, restarted in `applySwitchTarget`). Push-mode overlays (`currentModel`/`pushedProvider`) still win where fresher, and `AutoProviderTheme` re-resolves when the cached provider changes. Precedence is otherwise unchanged; the only new behavior is a brief placeholder in the pre-first-refresh window — correct when the host is exactly the slow case this fixes.

### Added

- **SIGQUIT (`Ctrl-\`) wedge-recovery hatch.** A dedicated signal goroutine, independent of the event loop, dumps every goroutine's stack, restores the terminal (termios + ANSI resets for alt-screen, cursor, bracketed paste, mouse, SGR), and exits `128+SIGQUIT`. This replaces the Go runtime's default SIGQUIT handler, which dumps and then exits **without** restoring the TTY. No-op when stdin isn't a terminal; Windows gets a stub via build tags. Net effect: `Ctrl-\` is a reliable "unwedge and hand my shell back" key.

## [0.16.1] — 2026-07-18

### Fixed

- **Fast attach to long remote sessions** ([#67](https://github.com/go-steer/core-tui/pull/67)). Attaching to a remote session with a long history rendered oldest-to-newest and took many seconds before the tail was visible. The bottleneck was per-event `refreshViewport`: each incoming SSE event walked the whole history, concatenated every rendered message, and called `viewport.SetContent` on the ever-growing buffer — O(N) per event, **O(N²)** over catch-up, even at a 100% `listCache` hit rate. Event-driven refreshes are now coalesced: handlers flip a dirty flag instead of refreshing synchronously, and a single ~1 ms `tea.Tick` fires one `refreshViewport` for every event that landed in the window. State mutation stays synchronous (the `sessionGen` stale-drop guards continue to hold) — only the paint is deferred. Total work over an N-event catch-up drops to **O(N × batch-size)**. Applies to `streamChunkMsg`, `toolCallMsg`, `toolResultMsg`, `usageMsg`, `statusUpdateMsg`, `usageUpdateMsg`, `inboxStateMsg`, `turnSummaryMsg`, `spinnerTickMsg`, `liveStreamStartedMsg`, `liveStreamErrMsg`, and `liveStreamEndedMsg`; user-input paths and dialog handlers keep refreshing immediately.
- `WindowSizeMsg` short-circuits when the dimensions haven't changed (bubbletea can emit initial + terminal-negotiated sizes back-to-back), and skips `rerenderHistoryMarkdown` on height-only resizes since Glamour wrapping is width-pinned.

The per-turn full-text Glamour render on commit remains a smaller constant (~10 ms × M turns) and was left for a later release.

Signatures rather than palette transcriptions — `google`'s wordmark cycles B-R-Y-B-G-R in logo letter order, `gke`'s cycles the icon's clockwise quadrants and its textarea prompt is `⎈` (Unicode HELM SYMBOL), `gopher` fades Gopher Blue → Aqua from the Go brand book, `pride` cycles the flag over calm violet chrome so it reads as a signature rather than an assault.
- Two reusable mechanisms behind those themes, available to any future one: **multicolor wordmarks** via `Theme.WordmarkSequence []color.Color` (nil keeps the existing single-color path) and **themed textarea prompt glyphs** via `Theme.PromptGlyph` (empty keeps the house default `▎ `, exported as `DefaultPromptGlyph`).
- Host surface: `Options.InitialThemeName` (case-insensitive; unknown names fall back to `DefaultTheme`), `Options.PersistThemeChoice func(string) error` (mirrors `PersistModelChoice`), `ThemeChangedMsg{Name string}` for hosts with custom `Update` wrappers, `BuiltinThemes() []BuiltinTheme` for hosts building their own picker, and `ThemeByName(name, dark) Theme`. Minimum integration to get the picker is **zero lines**; persisting across restarts is two.

### Changed

- ⚠️ **`Overlay.HandleKey`'s signature changed** from `(consumed bool)` to `(consumed bool, cmd tea.Cmd)` so dialogs can emit msgs. `Overlay` is exported but is internal modal plumbing; if you call it directly, append a `_` to ignore the new return.
- `Options.Branding.AccentColor` still overrides whichever theme is active — same precedence as before.

## [0.1.0] — 2026-05-26

Initial release: `package tui` extracted from the duplicated `internal/tui` trees in [`go-steer/cogo`](https://github.com/go-steer/cogo) and [`go-steer/core-agent`](https://github.com/go-steer/core-agent), generalized so neither host is favored.

### Added

- **The plug-in surface** — the `Agent` interface and `Event` type, the §3.3 optional capability interfaces, `Options`, and the TUI-implemented `PermissionPrompter` / `Elicitor` pair. Capabilities are feature-detected by type assertion, and a missing one degrades to a "not available in this host" message rather than an error.
- **The chat loop** — streaming assistant tokens rendered incrementally through Glamour, inline tool-call rows, the per-turn footer, prompt history, `/clear` with confirmation, transcript save/`/resume`, and the `Esc`-interrupts-turn / `Ctrl+C`-quits split.
- **Prompt queueing during streaming** (R-CHAT-10) with the four-state queue panel, plus `InjectableAgent` + `MidTurnInjectionMode` (R-CHAT-11), `WakeRequester` + its toast banner (R-WAKE-1), `ContentRunner` + the `Content` type (R-CHAT-12), and `SlashResult.ModalAnswer` + the side-answer modal (R-CMD-5).
- **Live `/` and `@` palettes** (R-PAL-1/2), a real model picker and file palette, real `/mcp` `/tools` `/skills`, `/stats` with cost, `/allow` and `/deny`, `Options.PersistModelChoice` (R-MOD-3), the status header/sidebar with a persisted layout choice, the bottom-anchored help panel on `?`, and the 3-tier color context indicator.
- **Performance and terminal-fidelity work** — incremental Glamour streaming, an auto-growing textarea, hanging-indent word wrap that preserves source leading whitespace, and the viewport's `h`/`j`/`k`/`l`/arrow bindings disabled with `xOffset` pinned to 0 so a wide line can't shift the whole chat sideways.
- **The docs that govern all of it** — `docs/requirements.md`, `docs/design.md`, `docs/decisions.md`, `docs/style.md`, `docs/ui-references.md`, and `MIGRATION.md`.
